# Pandas Performance and Debugging Interview Questions

## Q1: Why is iterrows slow and what should you use instead?

**A1:** iterrows is slow because it returns each row as a Series object, which involves significant overhead in creating Series objects, type checking, and index alignment for each iteration. It's essentially a Python-level loop that doesn't leverage Pandas' vectorized operations. Instead, use vectorized operations whenever possible, use itertuples() which returns namedtuples and is much faster, use apply() with vectorized functions, or use NumPy operations directly. For row-wise operations that can't be vectorized, itertuples() is typically 10-100x faster than iterrows because it returns Python tuples without the Series overhead. The best approach is to rethink the problem in terms of vectorized operations, which can be orders of magnitude faster than any row iteration method.

## Q2: When do vectorized operations outperform apply?

**A2:** Vectorized operations almost always outperform apply because they're implemented in C/Cython and operate on entire arrays at once, leveraging CPU optimizations and avoiding Python loop overhead. Apply is faster than iterrows but still involves Python function calls for each group or row, which adds overhead. Vectorized operations work on the entire column or DataFrame simultaneously using optimized low-level code. Use vectorized operations for arithmetic, comparisons, string operations (via .str accessor), datetime operations (via .dt accessor), and aggregations. Only use apply when you have truly complex logic that can't be expressed vectorially, and even then, consider if the operation can be broken into vectorized steps. The performance difference can be 10-1000x depending on the operation and data size.

## Q3: When does eval/query improve performance?

**A3:** eval and query can improve performance for large DataFrames with complex boolean expressions because they use numexpr to evaluate expressions efficiently, avoiding intermediate array creation. They're most beneficial when you have multiple conditions combined with &, |, and ~ operators, as numexpr can optimize the evaluation order and reduce memory usage. However, for simple conditions or small DataFrames, the overhead of parsing the expression string may outweigh benefits. eval/query are typically 10-50% faster for complex expressions on large datasets (millions of rows), but may be slower for simple operations due to parsing overhead. Use them when you have complex boolean logic on large DataFrames, but test performance as the benefits vary based on expression complexity and data characteristics.

## Q4: How do you reduce DataFrame memory usage?

**A4:** Use appropriate dtypes: convert object columns to category for repeated strings, use Int8/Int16/Int32 instead of Int64 when values fit, use float32 instead of float64 if precision allows, and use StringDtype for text data. Use convert_dtypes() to automatically optimize dtypes after reading data. For numeric columns with missing values, use nullable integer types (Int64) instead of float64. Remove unused columns with drop(). Use category dtype for columns with limited unique values. Consider using sparse data structures for columns with many zeros. Read only needed columns with usecols parameter. Use chunking for very large files. Monitor memory with memory_usage(deep=True) to identify memory-heavy columns. These optimizations can reduce memory usage by 50-90% depending on your data characteristics.

## Q5: How much memory does category dtype save?

**A5:** Category dtype can save 50-90% memory compared to object dtype, depending on the ratio of unique values to total values. Category dtype stores integer codes (typically 1-4 bytes) instead of full string values, with a separate mapping of codes to categories. For a column with 10 unique values in 1 million rows, object dtype stores 1 million strings (potentially 50-100MB), while category stores 1 million integers (4-8MB) plus a small mapping table. The savings increase as the number of unique values decreases relative to total rows. Category dtype is most beneficial for columns with many repeated values, such as country codes, product categories, or status fields. However, there's overhead in the category mapping, so columns with mostly unique values may not benefit or could even use more memory.

## Q6: Why should you avoid growing DataFrames with append/concat in loops?

**A6:** Appending or concatenating in loops is inefficient because each operation creates a new DataFrame, copying all existing data plus the new data. This leads to O(n²) time complexity as the DataFrame grows. With 1000 iterations, you're copying data 1000 times, which is extremely slow and memory-intensive. Instead, collect data in a list and concatenate once at the end, or preallocate the DataFrame if you know the final size. For example, use results = [] to collect DataFrames, then pd.concat(results, ignore_index=True) once. This approach is orders of magnitude faster because it only performs one copy operation instead of many. Preallocating with np.empty() or creating the full DataFrame upfront is even better if the size is known, avoiding concatenation entirely.

## Q7: What is the chained indexing problem?

**A7:** Chained indexing occurs when you use multiple indexing operations in sequence, like df[df['A'] > 5]['B'] = 10. Pandas may return a view or copy depending on the operations, making it unclear whether the assignment modifies the original DataFrame or a temporary copy. This leads to SettingWithCopyWarning and potential bugs where modifications don't affect the intended DataFrame. The solution is to use loc for both selection and assignment: df.loc[df['A'] > 5, 'B'] = 10. This ensures you're working with the original DataFrame and makes the intent clear. Chained indexing is a common source of bugs because it's not always obvious whether you're modifying a view or copy, and the behavior can be inconsistent across different Pandas versions or data structures.

## Q8: What causes SettingWithCopyWarning and how do you fix it?

**A8:** SettingWithCopyWarning occurs when Pandas detects that you might be modifying a view instead of a copy, which could lead to unexpected behavior. Common causes include chained indexing (df[condition]['col'] = value), selecting from a DataFrame that's already a view, or ambiguous operations where it's unclear if a copy or view is returned. To fix it, use loc for both selection and assignment (df.loc[condition, 'col'] = value), explicitly create a copy if you intend to modify a subset (df_subset = df[condition].copy()), or ensure you're working directly with the original DataFrame. With Pandas 2.0's Copy-on-Write, this warning is less common, but understanding it helps write safer code. Never suppress the warning without addressing the underlying issue, as it indicates a potential logic error.

## Q9: How does Copy-on-Write work in Pandas 2.0?

**A9:** Copy-on-Write (CoW) is a mechanism where views of DataFrames don't immediately share memory with the parent. When you create a view (like df[['col']] or df.loc[0:5]), both the view and parent reference the same data, but when you modify the view, Pandas automatically creates a copy at that moment. This prevents unintended mutations of the original data while avoiding unnecessary copies when data isn't modified. CoW makes data manipulation safer by default, eliminating many SettingWithCopyWarning issues. However, it means that some operations that previously returned views now trigger copies when modified, which can have performance implications. CoW is enabled by default in Pandas 2.0 and represents a significant improvement in data safety, though it may require code adjustments in some edge cases.

## Q10: Does the inplace parameter actually save memory?

**A10:** The inplace parameter doesn't necessarily save memory in the way many users expect. When inplace=True, Pandas may still create intermediate copies during the operation, and the memory savings depend on the specific operation. For simple operations like renaming columns, inplace=True can avoid creating a new DataFrame. However, for operations that require data rearrangement or type changes, copies may still be necessary internally. The main benefit of inplace=True is cleaner code (not needing to assign back) rather than memory savings. With Copy-on-Write in Pandas 2.0, the behavior is more consistent. Generally, don't rely on inplace for memory optimization; instead, focus on proper dtype usage, removing unused columns, and avoiding unnecessary copies. The performance difference is usually negligible, so choose based on code clarity.

## Q11: How do you read very large files efficiently?

**A11:** Use chunking with chunksize parameter to read in manageable pieces, specify usecols to read only needed columns, specify dtype to avoid type inference overhead, use low_memory=False for consistent dtypes, and consider using more efficient formats like Parquet. For example, pd.read_csv('file.csv', chunksize=10000, usecols=['col1', 'col2'], dtype={'col1': 'int32'}) reads in chunks with only specified columns and types. Process each chunk independently or aggregate results. For extremely large files, consider using Dask or Polars for out-of-core processing. Parquet format is columnar and compressed, making it much faster and smaller than CSV. Reading only needed columns and specifying dtypes can reduce memory usage and reading time by 50-90% depending on your data.

## Q12: When should you use .values vs .to_numpy() for performance?

**A12:** Both .values and .to_numpy() convert to NumPy arrays with similar performance for most cases. .to_numpy() is the recommended modern approach as it provides explicit control over dtype and missing value handling. For performance-critical code, .to_numpy() with explicit dtype can be slightly faster by avoiding type inference. If you need a specific dtype, .to_numpy(dtype='float32') is more efficient than converting after. However, the performance difference is usually negligible (less than 5%), so choose based on code clarity and explicit control rather than micro-optimizations. The main performance consideration is avoiding the conversion entirely if you can work directly with Pandas structures, as the conversion itself has overhead. Use .to_numpy() when you need NumPy array operations or when passing to libraries that require arrays.

## Q13: How do you profile Pandas code?

**A13:** Use Python's cProfile module or line_profiler for line-by-line profiling, use %timeit in Jupyter for quick benchmarks, use memory_profiler to track memory usage, and use Pandas' built-in options to display operation times. For detailed profiling, use cProfile.run() or line_profiler's @profile decorator. Identify bottlenecks by profiling different operations and comparing vectorized vs non-vectorized approaches. Use df.info(memory_usage='deep') to understand memory consumption. Profiling helps identify slow operations, memory issues, and optimization opportunities. Focus optimization efforts on the slowest operations identified through profiling rather than premature optimization.

## Q14: What are common causes of unexpected NaN values?

**A14:** Index misalignment during operations (DataFrames with different indices), arithmetic operations with missing data (NaN propagates), merge operations where keys don't match, type conversions that fail, division by zero, and operations on empty groups. When performing operations between Series or DataFrames, Pandas aligns by index, and mismatched indices result in NaN. Arithmetic with NaN always produces NaN. Merges without matches create NaN in unmatched columns. Understanding index alignment is crucial for debugging unexpected NaN values. Use .isnull().sum() to identify columns with missing values, check indices before operations, and use fillna() or dropna() as appropriate. The indicator parameter in merge helps identify unmatched rows that cause NaN.

## Q15: How can merge operations multiply rows unexpectedly?

**A15:** Merge operations multiply rows when there are duplicate keys in one or both DataFrames, creating a Cartesian product of matching rows. If the left DataFrame has 2 rows with key 'A' and the right has 3 rows with key 'A', the result will have 6 rows (2 × 3) for key 'A'. This happens with inner, left, right, or outer joins when duplicates exist. To avoid this, ensure keys are unique using drop_duplicates() or validate='one_to_one' / 'one_to_many' / 'many_to_one' parameters. The validate parameter raises an error if the relationship isn't as expected, helping catch this issue early. Always check for duplicate keys before merging using duplicated().sum() or by examining value_counts(). Understanding the cardinality of your merge keys prevents unexpected row multiplication.

## Q16: How does Index alignment cause bugs?

**A16:** Index alignment automatically matches data by index labels during operations, which can cause bugs when indices don't align as expected. Operations between Series or DataFrames align by index, so values at the same index position are combined, and mismatched indices produce NaN. This can silently produce incorrect results if you assume positional operations. For example, adding two Series with different index orders or missing indices will align by label, not position, potentially giving wrong results. To avoid alignment issues, ensure indices match before operations, use .values or .to_numpy() for positional operations, reset_index() if index alignment isn't desired, or use explicit alignment with .reindex(). Understanding when alignment is helpful versus harmful is key to avoiding subtle bugs.

## Q17: Why are mixed dtypes in a column slow?

**A17:** Mixed dtypes force Pandas to use object dtype, which stores Python objects instead of efficient NumPy arrays. Object dtype requires type checking and Python function calls for each operation instead of vectorized C operations. Each value is stored as a Python object with overhead, and operations can't be vectorized efficiently. Object columns also use more memory and prevent many optimizations. Converting to appropriate dtypes (numeric, category, StringDtype) enables vectorized operations and significant performance improvements. Use convert_dtypes() or infer_objects() to optimize dtypes, or explicitly convert columns to appropriate types. Mixed types often occur when reading CSV files where Pandas can't infer a consistent type, so specifying dtype during reading or converting afterward is essential for performance.

## Q18: How do you use numba or swifter with Pandas?

**A18:** Numba provides JIT compilation for numerical functions that can accelerate apply() operations. Decorate your function with @numba.jit and use it in apply(): df['result'] = df.apply(lambda x: numba_optimized_func(x['col1'], x['col2']), axis=1). Swifter automatically decides whether to use vectorization, Dask, or numba for apply() operations: df['result'] = df.swifter.apply(func). Both tools are useful when you have complex row-wise operations that can't be easily vectorized. However, they add overhead and may not always improve performance, especially for simple operations or small datasets. The best approach is still to vectorize when possible, as vectorized operations typically outperform numba/swifter. Use these tools as a last resort when vectorization isn't feasible and performance is critical.

## Q19: What are batch processing patterns for large datasets?

**A19:** Read data in chunks using chunksize, process each chunk independently, aggregate results incrementally, and write processed chunks to avoid holding everything in memory. Use generators for memory-efficient iteration. Filter chunks early to reduce data size. Use groupby operations that can be computed incrementally. Write intermediate results to disk (Parquet format) to free memory. Use Dask for out-of-core processing of datasets larger than memory. Process and aggregate in batches rather than loading everything. Use database-like operations (filter, aggregate) before loading into Pandas when possible. These patterns allow processing datasets much larger than available RAM. The key is to avoid loading the entire dataset into memory and instead process it in manageable pieces while maintaining correctness through proper aggregation.
