# Human Preference Leaderboards

Every benchmark in files 001-005 grades a model against some notion of ground truth — a correct answer, a passing test, a harmful/benign label. Chatbot Arena (LMSYS) does something structurally different: it has no ground truth at all. It asks anonymous humans which of two model responses to the same prompt they *prefer*, and aggregates millions of these pairwise judgments into a single ranking.

This makes it, in one sense, the most direct available proxy for "which model do people actually like using" — and, in another sense, a benchmark whose validity depends entirely on properties of its voter population and prompt distribution that are much harder to audit or correct for than a wrong answer key. This file works through the actual rating mechanics (Elo updates, and the Bradley-Terry model LMSYS's production system is actually built on) in enough depth to implement, then works through the specific, well-documented critiques.

## Methodology: what actually happens when someone votes

A user visits the Chatbot Arena web interface, types a prompt, and is shown two responses side by side, each generated by a model drawn — uniformly, or via some sampling scheme designed to gather informative comparisons — from the pool of models currently in the arena.

Critically, **the user does not know which model produced which response** until after voting; anonymization is essential to the design, since without it, brand reputation rather than response quality would drive votes. The user picks a winner, a tie, or "both bad," and the vote — along with the prompt and both responses — is logged. This repeats at scale (LMSYS has reported collecting well over a million such votes across its lifetime, across dozens of participating models), and the full history of pairwise outcomes is what any rating computation operates on.

## Elo rating mechanics, precisely

### Origin

The Elo system was designed by Arpad Elo for two-player zero-sum games (originally chess), and Chatbot Arena borrowed it directly because the underlying structure — repeated pairwise contests between competitors drawn from a pool, each contest producing a win/loss/tie outcome — matches its own data exactly, with "model" standing in for "player" and "human vote" standing in for "game result."

### The expected-score formula

Given two players (models) with current ratings `R_A` and `R_B`, Elo defines the *expected score* of player A against player B as a logistic function of the rating difference:

```
E_A = 1 / (1 + 10^((R_B - R_A) / 400))
E_B = 1 - E_A = 1 / (1 + 10^((R_A - R_B) / 400))
```

The constant 400 is a scaling convention — not a universal constant, chess uses 400, other implementations sometimes use different scales — chosen so that a 400-point rating gap corresponds to the higher-rated player having roughly a 10:1 expected-score odds ratio against the lower-rated one (`E_A ≈ 0.909` when `R_A - R_B = 400`). A rating gap of 0 gives `E_A = E_B = 0.5`, as it should for two equally-rated models.

### The update rule

After an actual outcome is observed — `S_A = 1` if A wins the pairwise vote, `S_A = 0` if A loses, `S_A = 0.5` for a tie (and symmetrically `S_B = 1 - S_A`) — both ratings are updated by comparing the actual score to the expected score, scaled by a step-size constant `K`:

```
R_A' = R_A + K * (S_A - E_A)
R_B' = R_B + K * (S_B - E_B)
```

Intuitively: if A was expected to win with probability 0.7 (`E_A = 0.7`) and actually won (`S_A = 1`), the update is small and positive (`K * 0.3`) — a modest confirmation of what was already expected. If instead A was expected to win with probability 0.7 and *lost*, the update is a much larger negative adjustment (`K * (0 - 0.7) = -0.7K`) — an upset carries more information and moves the rating further.

This asymmetric, surprise-proportional update is the core mechanical idea of Elo: ratings move in proportion to how much the actual outcome violated the *current* model's expectation, which is what lets the system self-correct over repeated play without ever needing to solve a global optimization problem — each update only looks at the single game just played.

```python
def expected_score(r_a: float, r_b: float, scale: float = 400.0) -> float:
    return 1.0 / (1.0 + 10 ** ((r_b - r_a) / scale))

def elo_update(r_a: float, r_b: float, score_a: float, k: float = 32.0,
               scale: float = 400.0) -> tuple[float, float]:
    """score_a: 1.0 if A won, 0.0 if A lost, 0.5 for a tie."""
    e_a = expected_score(r_a, r_b, scale)
    e_b = 1.0 - e_a
    score_b = 1.0 - score_a
    r_a_new = r_a + k * (score_a - e_a)
    r_b_new = r_b + k * (score_b - e_b)
    return r_a_new, r_b_new

def run_sequential_elo(votes: list[tuple[str, str, float]], k: float = 32.0,
                        initial_rating: float = 1000.0) -> dict[str, float]:
    """votes: list of (model_a, model_b, score_a) processed IN ORDER."""
    ratings: dict[str, float] = {}
    for model_a, model_b, score_a in votes:
        ratings.setdefault(model_a, initial_rating)
        ratings.setdefault(model_b, initial_rating)
        ratings[model_a], ratings[model_b] = elo_update(
            ratings[model_a], ratings[model_b], score_a, k
        )
    return ratings
```

### The order-dependence problem with sequential Elo

Processing votes one at a time, in whatever order they arrived, has a real statistical weakness: the resulting ratings depend on the *order* in which games were processed, especially early on when ratings are still far from their "true" relative values and few games have been played. Two models that happened to be compared against very different opponents early in the data stream can end up with meaningfully different ratings than if the exact same set of game outcomes had been processed in a different order or all at once.

This is a known, textbook limitation of classic sequential Elo — it is an *online* estimator, updated incrementally, not a *batch* estimator computed from the full dataset at once. It is large enough in practice — especially in a setting like Chatbot Arena, where new models enter the pool continuously and comparisons between any two given models can be sparse relative to comparisons against other models — that LMSYS does not actually use naive sequential Elo for its production leaderboard.

## What LMSYS actually computes: Bradley-Terry MLE with bootstrap confidence intervals

### The Bradley-Terry model

Rather than updating ratings incrementally game-by-game, the Bradley-Terry model assigns each model a latent strength parameter `θ_i` and models the probability that model `i` beats model `j` in a single pairwise comparison as:

```
P(i beats j) = exp(θ_i) / (exp(θ_i) + exp(θ_j)) = 1 / (1 + exp(-(θ_i - θ_j)))
```

which is exactly a logistic function of the strength difference `θ_i - θ_j` — mathematically the same functional form as Elo's expected-score formula (`E_A` above is literally the Bradley-Terry win probability under a change of variables relating `θ` to `R`/400 and a base-10 versus base-`e` exponential convention).

The crucial difference is not the functional form but the **estimation procedure**: instead of updating `θ` incrementally after each observed game, Bradley-Terry strengths are estimated via **maximum likelihood over the entire observed dataset of pairwise outcomes at once** — find the `θ` vector that maximizes the likelihood of every recorded vote in the dataset simultaneously. In practice, for LMSYS's public methodology, this is done via logistic regression: encoding each pairwise comparison as a training example (a one-hot-like feature vector with +1 for the model that won, -1 for the model that lost, 0 for every other model) and fitting a logistic regression with no intercept, whose learned coefficients are exactly the Bradley-Terry strength estimates.

```python
import numpy as np
from sklearn.linear_model import LogisticRegression

def fit_bradley_terry(votes: list[tuple[str, str, float]], models: list[str]) -> dict[str, float]:
    """Fit Bradley-Terry strengths via logistic regression over pairwise outcomes.
    votes: list of (model_a, model_b, score_a) where score_a in {0.0, 0.5, 1.0}.
    Ties are typically handled by including them as two half-weighted rows
    (a win for each side) or dropped, depending on convention."""
    idx = {m: i for i, m in enumerate(models)}
    X, y, w = [], [], []
    for model_a, model_b, score_a in votes:
        if score_a == 0.5:
            # split a tie into a half-weighted "win" for each side
            for winner, loser, weight in [(model_a, model_b, 0.5), (model_b, model_a, 0.5)]:
                row = np.zeros(len(models))
                row[idx[winner]] = 1.0
                row[idx[loser]] = -1.0
                X.append(row); y.append(1); w.append(weight)
        else:
            winner, loser = (model_a, model_b) if score_a == 1.0 else (model_b, model_a)
            row = np.zeros(len(models))
            row[idx[winner]] = 1.0
            row[idx[loser]] = -1.0
            X.append(row); y.append(1); w.append(1.0)
    X, y, w = np.array(X), np.array(y), np.array(w)
    clf = LogisticRegression(fit_intercept=False, penalty=None)
    clf.fit(X, y, sample_weight=w)
    theta = clf.coef_[0]
    return {m: float(theta[idx[m]]) for m in models}

def bootstrap_confidence_intervals(votes, models, n_bootstrap: int = 100) -> dict[str, tuple[float, float]]:
    """Resample the vote log with replacement n_bootstrap times, refit Bradley-Terry
    each time, and report the 2.5th/97.5th percentile of each model's strength
    -- this is exactly how LMSYS reports leaderboard confidence intervals."""
    samples = {m: [] for m in models}
    n = len(votes)
    rng = np.random.default_rng(0)
    for _ in range(n_bootstrap):
        resampled = [votes[i] for i in rng.integers(0, n, size=n)]
        fit = fit_bradley_terry(resampled, models)
        for m in models:
            samples[m].append(fit[m])
    return {m: (float(np.percentile(v, 2.5)), float(np.percentile(v, 97.5)))
            for m, v in samples.items()}
```

### Why this is better than naive sequential Elo for a leaderboard

The MLE fit is **order-invariant** — it depends only on the multiset of observed outcomes, not the sequence in which they were collected, which directly eliminates the order-dependence problem described above. It is also more statistically efficient (a maximum-likelihood estimate over the full dataset makes better use of all available comparisons jointly, rather than only ever comparing the two ratings involved in each individual game at the moment it happened).

Critically for a public leaderboard that needs to report a "how confident are we" figure, it supports **bootstrap resampling**: refit the model on many resampled versions of the vote log and look at the spread of resulting strength estimates for each model, producing a confidence interval that reflects genuine sampling uncertainty given how many (and which) comparisons a given model has actually been part of. LMSYS reports exactly this kind of confidence interval alongside its leaderboard rankings, which is part of why the platform explicitly discourages reading small rank differences (especially between models whose confidence intervals overlap) as a meaningful capability difference — the intervals themselves are the correct signal that many adjacent-rank models are not statistically distinguishable given the current data.

### Terminology note

Despite the underlying computation being Bradley-Terry MLE rather than sequential Elo updates, LMSYS still reports results on an Elo-like numerical scale — for interpretability and continuity with the "Elo rating" framing people already associate with competitive ranking systems from chess — and the platform and most secondary coverage still colloquially call the whole system "Elo" or "Arena Elo," a real and common point of confusion.

If asked to "explain how Chatbot Arena's Elo works" in an interview setting, the mechanically correct answer distinguishes the classic sequential-update mechanism (worth understanding because it's the historically original and pedagogically simplest version, and is genuinely used in some real-time/online rating contexts) from what the actual production leaderboard computes (Bradley-Terry MLE plus bootstrap CIs), rather than describing only the sequential-update version and implying that's literally what LMSYS runs.

## Known critiques

### Voter-population bias

Votes come from whoever chooses to visit the Chatbot Arena website and use it — a self-selected population skewed toward people already interested in and knowledgeable about LLMs (AI enthusiasts, researchers, developers), not a representative sample of the general population of people who use LLM products. It is certainly not representative of, say, enterprise deployment contexts, non-English-speaking users (though LMSYS does run non-English-language leaderboard splits), or any specific vertical use case (legal, medical, customer support).

A model's Arena ranking is a statement about "which model this specific, self-selected, internet-savvy population prefers," which is a real and useful signal, but is not the same claim as "which model performs best for typical deployed use." Treating Arena rank as a universal capability ranking overextends what the underlying voter population can actually support.

### Prompt-distribution bias

Because prompts are whatever casual visitors happen to type in rather than a curated, representative task distribution, the prompt mix skews toward what people enjoy testing chatbots with informally: creative writing requests, casual conversational questions, coding snippets, roleplay, "trick" or novelty prompts, and general knowledge questions — rather than toward the kinds of tasks that dominate real high-stakes or enterprise deployment (long-document analysis, precise multi-step agentic tool use, domain-specific technical work).

A model can rank highly on Arena by being excellent at exactly the kind of prompt casual users tend to submit, while being comparatively weaker at task types the benchmark's voters rarely probe, and Arena's aggregate leaderboard number does not separate these. LMSYS has partially addressed this by publishing category-specific breakdowns (e.g., a coding-specific or longer-query-specific sub-leaderboard) precisely because the aggregate number was recognized as conflating different underlying prompt distributions.

### Style and length gaming

This is one of the most concretely documented critiques, and LMSYS's own subsequent methodology work engages with it directly. Human voters, when judging two responses to the same prompt with no other information to go on, are measurably influenced by response *style* — length, formatting (bullet points, headers, bold text), a confident and assertive tone — independent of whether the additional length or formatting reflects additional substantive correctness or usefulness.

A model specifically tuned (whether deliberately, or as a side effect of RLHF reward-model preferences, which have the same human-rater-derived susceptibility) to produce longer, more elaborately formatted, more confidently-worded responses can win a disproportionate share of pairwise votes without the underlying content being better. This is functionally a Goodhart's-law problem for human-preference optimization (see file 007's general discussion): if "what wins votes" and "what is actually more correct/useful" diverge even partially, optimizing directly against the vote signal pushes models toward the votable-but-not-necessarily-better direction.

LMSYS's response has been to publish a **style-controlled leaderboard**: a regression-based adjustment that statistically controls for response length and markdown-formatting features when estimating each model's underlying strength, aiming to isolate a "quality holding style constant" ranking distinct from the raw, style-confounded ranking. This is a genuine methodological improvement, though it depends on the specific style features chosen for the regression capturing the relevant confounds completely, which is itself an assumption rather than a guarantee.

### Other documented concerns

Potential for vote manipulation (coordinated or automated voting to favor a particular model) is a generic risk for any open, low-friction public-voting system, and LMSYS has discussed detection/mitigation measures for anomalous voting patterns without this being a fully solved problem.

The pairwise, single-turn-snapshot comparison format (most Arena votes are on a single exchange, not extended multi-turn conversations, though multi-turn variants exist) means Arena primarily measures single-response quality rather than sustained multi-turn coherence or task completion — a different capability profile from, e.g., the agentic benchmarks in file 003.

Preference votes, by construction, cannot directly measure factual calibration — a confidently stated wrong answer can beat a correctly hedged uncertain answer in a head-to-head vote if the voter cannot independently verify which is actually correct. This means Arena rankings can systematically reward confident fluency over accurate uncertainty-communication in domains where voters themselves lack the expertise to catch the error, a subtle but real distinction from every ground-truth-based benchmark in files 001-002, where confident wrongness simply scores as wrong.

## Worked numerical example: Elo vs. Bradley-Terry disagreement

To make the order-dependence claim concrete rather than purely qualitative: suppose three models A, B, C have played a sparse set of games — A beat B twice, B beat C twice, and C beat A once — a near-cyclic result set with no clear total ordering. Processing these five outcomes through sequential Elo in the order listed, versus processing the exact same five outcomes in reverse order, produces two different final rating triples, because each update depends on the *intermediate* ratings at the time it's applied, and those intermediates differ between the two processing orders. Fitting Bradley-Terry via MLE over the same five outcomes, regardless of the order they're listed in, produces exactly one answer both times, because the MLE objective is a function of the outcome multiset alone. This is exactly the property that makes Bradley-Terry the right choice for a leaderboard that must produce one canonical, reproducible ranking from a huge, continuously-growing, arbitrarily-ordered vote log rather than a running online score.

## Quick-reference comparison

| Property | Sequential Elo | Bradley-Terry MLE (what LMSYS runs) |
|---|---|---|
| Update style | Online, incremental, one game at a time | Batch, fit over entire dataset at once |
| Order-dependence | Yes — same games, different order, different result | No — depends only on the outcome multiset |
| Confidence intervals | Not natively supported | Bootstrap resampling supported |
| Statistical efficiency | Lower (each update uses only local information) | Higher (joint optimization over all data) |
| Historical role here | Pedagogical / conceptual origin | Actual production computation |

## Common interview framings worth preparing for

- **"A model ranks #1 on Chatbot Arena's overall leaderboard but #8 on its coding-specific sub-leaderboard. What does that tell you?"** — that the model's strength is concentrated in whatever the aggregate prompt distribution over-represents (likely creative writing, conversational, and general-knowledge-style prompts) rather than in coding specifically, and that a team choosing a model for a coding-heavy product should weight the category-specific breakdown far more heavily than the aggregate rank — exactly the prompt-distribution-bias critique made concrete.
- **"Why does LMSYS bother with a style-controlled leaderboard at all, if the raw leaderboard already reflects genuine human preference?"** — because "genuine human preference" and "genuine quality" are not guaranteed to be the same thing when preference judgments are made quickly, without verification, based on surface impressions; the style-controlled leaderboard is an attempt to separate a preference-relevant confound (does it look more thorough) from the underlying construct of interest (is it actually more correct/useful), which matters most for exactly the use cases (e.g., factual or technical work) where style and substance are most likely to diverge.
- **"If you had unlimited engineering budget, what would you add to Chatbot Arena's methodology to make it more useful for evaluating a model bound for an enterprise product?"** — a curated, weighted resampling of the prompt distribution toward enterprise-relevant task categories (rather than relying on the organic, casual-user-driven distribution), paired with domain-expert (rather than general-population) voters for any technical/specialized category, and an explicit factual-accuracy verification step layered on top of pure preference voting for any prompt with a checkable ground truth — acknowledging that this would make the platform more expensive and slower to scale than its current organic-traffic model, which is exactly the tradeoff that explains why it doesn't already work this way.

## How Arena-style preference data connects back to model training itself

It is worth being explicit about a connection that ties this file back to the broader post-training picture (see `../04_Post_Training_And_Alignment/`): the same pairwise-comparison structure Chatbot Arena uses to *evaluate* models is structurally identical to the pairwise-preference data RLHF-style post-training uses to *train* a reward model in the first place — both are "given two responses to the same prompt, which is preferred" judgments, aggregated across many comparisons. This is not a coincidence; Arena-style evaluation and RLHF preference-data collection are, mechanically, the same measurement instrument pointed at two different purposes (one evaluates existing models, the other trains a reward model that shapes a new one). This structural identity is exactly why the style-and-length-gaming critique in this file and the well-documented reward-model length/style bias in RLHF are the same underlying phenomenon observed twice, in two different contexts, rather than two unrelated findings — a human or human-like preference judgment is susceptible to the same surface-feature confounds whether it's being used to compute a leaderboard rank or to compute a training gradient.

## Synthesis

Chatbot Arena's real contribution is being the largest-scale, most continuously-updated human-preference signal available for comparing frontier models, and its Bradley-Terry-plus-bootstrap methodology is a legitimately more rigorous statistical treatment of pairwise comparison data than the "classic Elo" label most people associate with it suggests.

But every one of its critiques traces back to the same root property that also gives it its value: it has no ground truth, so its output is only ever as representative as its voter population and prompt distribution, and it is only as robust to gaming as its preference signal is to being decoupled from actual quality. This is precisely why it functions best as one input among several — alongside the ground-truth benchmarks in files 001-005 — rather than as a standalone measure of which model is "best," a point this file's closing synthesis shares with file 007's broader discussion of the benchmark-score-versus-real-usefulness gap.
