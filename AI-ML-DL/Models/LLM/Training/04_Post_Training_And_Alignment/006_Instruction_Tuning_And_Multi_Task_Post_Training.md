## Instruction Tuning and Multi-Task Post-Training

### 0. Scope of This File

File 001 covered SFT's mechanics treating "the SFT dataset" as a given curated set of prompt-response pairs. This file zooms into a question File 001 deliberately deferred: what should that dataset actually *contain*, across how many task types, in what proportions, and what happens when those choices are wrong? Instruction tuning -- SFT specifically framed around training on a diverse mixture of task types and instruction formats so the model generalizes to instructions it has never seen -- is a distinct concern from "SFT" as a mechanism, and the mixture-design problem it raises is one of the more underrated, high-leverage engineering problems in post-training, structurally similar to but meaningfully distinct from the pretraining-data-mixture problem covered elsewhere in this curriculum's pretraining module.

### 1. Instruction Tuning as a Distinct Concern From Single-Task SFT

**1.1 The historical lineage.** Multi-task instruction tuning as a research idea predates chat-assistant post-training by several years. FLAN (Wei et al., 2021, "Finetuned Language Models Are Zero-Shot Learners") and T0 (Sanh et al., 2021) demonstrated that fine-tuning a pretrained language model on a large collection of NLP tasks -- each reformatted into a natural-language instruction-plus-input-plus-target template -- produced a model that generalized zero-shot to *held-out task types* it had never been fine-tuned on, substantially better than the same base model prompted zero-shot without any instruction-tuning stage at all. Super-NaturalInstructions (Wang et al., 2022) pushed this further, aggregating over a thousand distinct NLP tasks under a unified instruction schema. These are academic, benchmark-task-oriented precursors to what InstructGPT-style chat-assistant SFT (File 001) does with more open-ended, conversational, human-preference-oriented data -- but the core empirical finding is the same one File 001, Section 5.2 asserts: **diversity of task type in the fine-tuning mixture is what drives generalization to unseen instructions**, not merely fine-tuning on more data of the same narrow kind.

**1.2 What "generalization to unseen instructions" actually requires, mechanically.** A model fine-tuned on only one task type (say, summarization) learns to reliably produce summaries when asked, but has no particular reason to have learned the more general skill of "parse an arbitrary natural-language instruction and produce output satisfying it" -- it may have simply learned "map any input roughly matching this task's format to output roughly matching that task's format," a narrower, more brittle pattern-matching skill than genuine instruction-following. Training across many structurally different task types -- classification, extraction, generation, transformation, multi-step reasoning, each phrased as a distinct natural-language instruction -- forces the model to learn a more general mapping from *instruction semantics* to *appropriate behavior*, because no single narrow input-output pattern-match strategy would perform well across all of them simultaneously. This is exactly analogous to the classical multi-task-learning argument in machine learning generally (a model trained on a genuinely diverse task set is pushed toward representations that capture the shared underlying structure across tasks, rather than overfitting to any single task's idiosyncrasies), applied here specifically to the space of natural-language instructions themselves.

**1.3 Terminology precision worth having ready.** "SFT" and "instruction tuning" are frequently used interchangeably in casual discussion, and in current practice they denote largely the same mechanism (File 001's masked cross-entropy loss over prompt-response pairs). The distinction worth drawing precisely in an interview: **SFT is the mechanism** (a loss function and masking convention); **instruction tuning** is a *framing/emphasis* on that mechanism specifically foregrounding the diversity and multi-task composition of the training mixture as the object of design attention, rather than any change to the loss itself. A single-task SFT run (fine-tune only on customer-support transcripts, say) uses the identical mechanism as broad instruction tuning; it is simply not attempting the generalization goal instruction tuning is specifically designed to achieve.

### 1.4 Relationship to In-Context Learning and Few-Shot Prompting

A question worth being able to answer precisely: if a strong enough pretrained base model can already perform many tasks reasonably well via few-shot in-context prompting alone (a handful of examples placed directly in the prompt, no fine-tuning at all), what does instruction tuning add beyond what good prompting already provides? The answer has several distinct parts. First, instruction tuning removes the *need* for few-shot examples in the prompt at all for a very wide range of tasks -- a well-instruction-tuned model performs the analogous task zero-shot, from a natural-language instruction alone, freeing up context-window budget and removing the burden of constructing good few-shot exemplars at inference time. Second, instruction tuning changes the model's *default* behavior and format conventions (stopping cleanly, addressing the actual request, adopting a conversational register) in ways that few-shot prompting on a non-instruction-tuned base model cannot reliably induce, since the base model's underlying document-completion prior (File 001, Section 1) keeps asserting itself around and between the few-shot examples. Third, and most relevant to this file's mixture-design focus, instruction tuning can substantially improve performance on tasks that are *not* well-suited to few-shot demonstration at all -- long, multi-step, or open-ended tasks where a handful of static examples in a prompt provide much weaker guidance than they do for short, pattern-completable tasks like simple classification. None of this means few-shot prompting becomes useless post-instruction-tuning; it means the *floor* of zero-shot instruction-following performance rises substantially, and few-shot examples become a supplementary lever for further steering an already-competent model rather than the primary mechanism for eliciting basic task competence at all.

### 2. The Task-Mixture-Balancing Problem

**2.1 Why this is a genuinely hard, not merely tedious, design problem.** Given a fixed compute/data budget for the SFT stage, a team must decide what fraction of training examples come from each task category (open QA, closed QA, summarization, code generation, creative writing, classification, extraction, multi-turn dialogue, tool use, refusal/safety edge cases, and many finer-grained subcategories within each) and, within each category, what distribution of difficulty, length, and style to include. Get this wrong in either direction and the resulting model's behavior visibly reflects it: over-representing one category produces a model unreasonably eager to respond in that category's style even to prompts that don't call for it (a direct instance of the format-leakage mechanism from File 001, Section 5.5, now considered at the mixture level rather than the single-category level); under-representing a category produces a model that handles it noticeably worse than its otherwise-similar peers, or that generalizes to it only as well as its pretraining-derived general capability allows, without any post-training-specific improvement.

**2.2 How this differs from the pretraining-data-mixture problem.** Both problems are, at a high level, "what proportion of training data should come from each source/domain," but the specifics differ enough to warrant treating them as related-but-distinct engineering problems, not the same problem at a different scale:

| Aspect | Pretraining mixture | SFT/instruction-tuning mixture |
|---|---|---|
| Data scale | Trillions of tokens, sourced largely by domain/provenance (web, code, books) | Tens of thousands to low millions of examples, curated per task type |
| What imbalance costs you | Knowledge/capability skew across domains (e.g., undertrained on a language or a technical field) | Behavioral/stylistic skew (format leakage, over- or under-eagerness for specific response types) -- File 001, Section 5.2-5.3 |
| Primary failure signal | Benchmark performance gaps on underrepresented domains | Qualitative behavioral misfires (wrong format, wrong tone, wrong level of refusal) as much as quantitative benchmark gaps |
| Cost of getting more data of an underrepresented category | Often bounded by raw supply (some domains have limited high-quality text available at all) | Often bounded by curation/labeling cost and consistency (File 001, Section 5.1's quality-over-quantity finding), not raw supply |
| Granularity of control | Coarse (domain-level sampling weights) | Fine-grained (individual task-type and sub-task proportions, often hand-tuned) |

**2.3 Negative transfer / interference between dissimilar tasks.** Beyond simple over/under-representation, genuinely dissimilar tasks trained together in one mixture can actively interfere with each other's learned behavior -- a phenomenon well documented in the classical multi-task-learning literature as **negative transfer**: gradient updates that improve performance on task A can, for a sufficiently dissimilar task B, actively degrade performance on B, because the shared parameters are being pulled in directions that serve A's objective at B's expense. In instruction-tuning mixtures, this shows up concretely as, for example, heavy representation of terse, single-fact-answer QA data pulling the model toward brevity in a way that measurably degrades its performance on tasks that genuinely require longer, more deliberative responses (multi-step reasoning, nuanced open-ended writing) -- not because the model "forgot" how to write longer responses in some absolute sense, but because the gradient signal from the terse-QA-heavy portion of the mixture has shifted its default response-length prior in a way that bleeds into other task types, exactly the kind of stylistic-tic propagation described in File 001, Section 5.3.

**2.4 Format and schema inconsistency across aggregated sources.** Production instruction-tuning mixtures are frequently aggregated from many distinct sources (in-house labelers writing to one set of guidelines, licensed or acquired datasets built to different conventions, synthetic data generated by different pipelines at different times) -- and inconsistency in surface format (how code blocks are delimited, how multi-step answers are structured, how citations or sources are represented) across these sources, even when the underlying task and quality are fine, reproduces the same "matching a moving target" problem File 001, Section 3.5 describes for demonstration inconsistency generally, now specifically at the level of cross-source formatting conventions rather than individual labeler style. A non-trivial fraction of real instruction-tuning-data engineering effort goes into normalizing formatting conventions across aggregated sources before training, for exactly this reason.

### 2.5 A Worked Illustration of a Mixture Ratio Table

Concretely, a (illustrative, not any specific lab's actual disclosed mixture) instruction-tuning mixture might be specified as a set of category weights like this:

| Category | Illustrative share of mixture | Rationale |
|---|---|---|
| Open-ended QA / knowledge | 15% | High query volume; relies mostly on pretraining knowledge, so needs less SFT volume per unit of quality |
| Coding | 20% | High product value; feeds into a later dedicated RLVR stage (File 005), but still needs solid SFT-level coverage and formatting conventions |
| Multi-step reasoning / math | 15% | Same rationale as coding; SFT establishes format and baseline competence ahead of RLVR |
| Creative and long-form writing | 10% | Lower verifiability, high stylistic sensitivity to demonstration consistency (File 001, Section 5.1) |
| Summarization / extraction | 10% | Well-defined task shape, comparatively cheap to source high-quality demonstrations for |
| Multi-turn dialogue / tool use | 15% | Increasingly high product value as agentic and tool-augmented use cases grow |
| Refusal / safety edge cases | 10% | Deliberately bounded (File 001, Section 5.6) to avoid overgeneralized refusal behavior |
| Classification / structured output | 5% | Narrow task shape, comparatively easy to saturate with a small share of the budget |

The exact numbers here are illustrative rather than any specific disclosed production mixture, but the exercise of writing such a table down, with an explicit rationale per row, and revisiting it after every ablation round (Section 3.2), is itself the actual practice -- the discipline of making mixture weights an explicit, documented, revisable artifact rather than an implicit consequence of whatever data happened to be available is a meaningful part of what separates a deliberate instruction-tuning effort from an ad hoc one.

### 3. How Mixture Ratios Are Actually Tuned in Practice

**3.1 Manual heuristics and prior experience as the starting point.** In the absence of a clean, universally agreed-upon theory for optimal mixture ratios (this remains, as with pretraining mixtures, more art-plus-empirical-iteration than settled science), teams typically start from heuristics informed by prior training runs and known product priorities -- allocate more of the budget to task categories known to be high-value or historically weak, allocate a meaningful but bounded fraction to safety/refusal edge cases (File 001, Section 5.6), and otherwise aim for at least minimal coverage across the full space of anticipated instruction types.

**3.2 Ablation studies on held-out per-task evaluation sets.** The more rigorous version of mixture tuning runs controlled ablations -- training multiple SFT variants that differ only in the relative weight of one or a few task categories, and evaluating each variant on a held-out evaluation suite broken down *per task category* (not just an aggregate score), to directly observe how shifting a given category's weight trades off against every other category's held-out performance. This per-category breakdown is important precisely because an aggregate score can mask exactly the kind of cross-task interference described in Section 2.3 -- an aggregate metric can hold roughly steady while individual categories move substantially in opposite directions.

**3.3 Dynamic and loss-based reweighting.** More sophisticated approaches adjust task weights *during* training rather than fixing them upfront, using signals like each task category's current held-out loss trajectory (upweighting categories whose loss has plateaued or is regressing, downweighting categories that are already well-learned) -- a direct analogue of dynamic data-mixture reweighting techniques explored in the pretraining-mixture literature, applied here at the task-category level. This is less universally standardized in instruction-tuning practice than static, carefully-ablated fixed mixtures, but is an active area of methodological development, particularly as instruction-tuning mixtures grow to cover hundreds of distinct fine-grained task categories where manual, per-category ablation becomes impractical to do exhaustively.

**3.4 Tracking a "capability tax" per category, not just aggregate quality.** Because File 001's forgetting risk (Section 4) and this file's negative-transfer risk (Section 2.3) are both real, a mature instruction-tuning evaluation practice tracks each task category's performance *before and after* every mixture change relative to a fixed baseline, explicitly budgeting for the possibility that improving one category costs a measurable amount on another -- treating mixture design as a genuine multi-objective optimization with visible tradeoffs, rather than searching for a mixture that improves everything simultaneously with no downside anywhere, which is rarely achievable in practice once a mixture is pushed hard toward any one high-priority category.

### 3.5 A Minimal Dynamic Reweighting Implementation

Concretely, a simple loss-based dynamic reweighting scheme (Section 3.3) for sampling task categories during training might look like this:

```python
def update_category_weights(category_losses, prev_weights, target_loss, lr=0.1):
    """
    category_losses: dict {category_name: recent held-out loss}
    prev_weights:    dict {category_name: current sampling weight}, sums to 1.0
    target_loss:     dict {category_name: a reference/floor loss value below which
                            we don't want to keep upweighting further}
    """
    new_weights = {}
    for cat, loss in category_losses.items():
        # upweight categories whose loss is still meaningfully above their target/floor;
        # downweight (but don't zero out) categories that have already converged well
        deficit = max(loss - target_loss[cat], 0.0)
        new_weights[cat] = prev_weights[cat] * (1.0 + lr * deficit)

    total = sum(new_weights.values())
    return {cat: w / total for cat, w in new_weights.items()}   # renormalize to a valid sampling distribution
```

This is a deliberately simple illustration, not a production-grade recipe -- real implementations typically add smoothing/momentum across evaluation rounds (to avoid over-reacting to a single noisy held-out loss measurement), a floor on the minimum weight any category can be pushed to (to avoid fully starving a category even if its loss looks converged), and often combine loss-based signals with product-priority-based fixed floors rather than letting the loss signal alone determine weights. But the core idea -- treat mixture weights as a variable the training process itself can adjust in response to observed per-category learning progress, rather than a value fixed once at the start of the run -- is the generalizable content worth taking away.

### 4. The Generality-Versus-Depth Tension

**4.1 Stating the tension precisely.** A model trained to be a broadly capable generalist -- handling the full, open-ended distribution of things users might ask, gracefully, across every category in Section 2's mixture -- is not automatically the strongest possible model on any *one* high-value vertical (coding, mathematical reasoning, legal or medical domain expertise) relative to a model whose entire post-training budget was instead concentrated on that one vertical. This is a direct, practical consequence of Section 2's mixture-balancing problem taken to its logical conclusion: training compute and curated-data budget are finite, and every token of budget spent broadening coverage is a token not spent deepening any single category, subject to the negative-transfer risk in Section 2.3 working against depth in the categories that receive comparatively less relative weight in a broad mixture.

**4.2 Why labs care about specific verticals disproportionately.** Coding and mathematical/quantitative reasoning receive disproportionate post-training investment at every frontier lab relative to their share of raw user-query volume, for reasons independent of pure "how often do users ask this" prioritization: these are domains with the clearest available verifiable-reward signal (File 005's entire premise), the most direct enterprise/developer commercial value, and -- specifically for coding and math -- a strong empirical case that improvements in these verticals transfer partially into improved general reasoning capability on other tasks, making them attractive as both standalone product priorities and as capability investments with broader spillover.

**4.3 How labs actually navigate the tradeoff: sequencing and layered specialization, not a single mixture ratio decision.** In practice, the tension in 4.1 is not resolved by finding one perfect global mixture ratio; it is resolved architecturally and procedurally, through several complementary strategies:

- **Broad instruction-tuning first, specialized RL/SFT stages layered on top.** A common pattern is to establish general instruction-following competence and behavioral scaffolding (File 001, Section 6's "convert a document-completer into an assistant" job) via a broad mixture first, then run additional, more heavily verticalized post-training stages -- often RLVR-based (File 005) for coding and math specifically, given the availability of verifiers in those domains -- layered on top of the same base policy, rather than trying to achieve both breadth and vertical depth from one single, uniformly-mixed stage.
- **Dedicated model variants alongside a flagship generalist.** Several labs ship separate, explicitly coding- or reasoning-optimized model variants (sometimes distinguished by name, sometimes by a "mode" or "effort" setting on an otherwise-shared model) alongside a flagship generalist assistant model, an explicit acknowledgment that a single model's post-training mixture cannot simultaneously be the single best choice for every use case, and that market segmentation by use case is a more practical answer than forcing one mixture to serve all of them optimally.
- **Mixture-of-experts architectures as a partial structural answer.** Though primarily a pretraining-architecture decision rather than a post-training one, MoE architectures (routing different inputs to different expert subnetworks) offer a structural mechanism that can reduce, though not eliminate, the generality-depth tension at the level of shared-parameter interference specifically: different experts can specialize more freely on different task distributions than a single dense model's shared weights can, without one task type's gradient updates necessarily degrading another's expert-specific parameters, subject to whatever the router's own load-balancing and routing-consistency behavior imposes as its own set of tradeoffs -- worth mentioning as a relevant architectural lever without overclaiming it as a complete solution to what remains fundamentally a data/compute-allocation problem at the mixture level, and one that architectural choices only partially mitigate rather than dissolve entirely.
- **Post-hoc merging of specialized fine-tunes.** Rather than deciding the generalist-versus-specialist tradeoff once at training time, several practical workflows train separate, more narrowly-specialized fine-tunes and combine them after the fact via model-merging techniques (File 008) -- deferring part of the tradeoff decision to a cheaper, post-training-time operation rather than requiring it be resolved entirely within a single joint training mixture.

### 4.4 The Four Navigation Strategies, Compared

| Strategy | What it trades off | Cost | Where it's most effective |
|---|---|---|---|
| Broad SFT then layered vertical RL/SFT | Sequencing risk (later stages can partially undo earlier general behavior if not carefully KL-anchored) for cleaner separation of concerns | Moderate -- an additional training stage, but reuses the same base policy | Verticals with an available verifier (coding, math) -- File 005 |
| Dedicated specialized model variants | Product/serving complexity (multiple models to maintain, route between, and keep in sync) for zero compromise on either generalist or specialist quality | High -- effectively multiplies post-training and serving cost by the number of variants | High-value verticals with distinct enough user bases to justify separate products |
| MoE architecture | Some routing/load-balancing complexity and inference-serving complexity (File 08, Inference and Serving module) for reduced shared-parameter interference | Primarily a pretraining-time architectural decision, not something adopted post-hoc | Cases where the interference in Section 2.3 is severe enough to justify an architectural rather than purely data-level fix |
| Post-hoc model merging | Some ceiling on how well-integrated the merged capabilities are (File 008 covers merging's own limits) for much lower cost than joint retraining | Low relative to a fresh joint training run | Combining several already-existing specialized fine-tunes without a fresh, expensive joint training run |

None of these four is a strictly dominant choice -- production decisions typically combine at least two of them (e.g., broad SFT plus layered RLVR for coding/math, with occasional post-hoc merging of narrower experimental fine-tunes into the next release), and being able to lay out this table rather than naming only one strategy is a good signal of staff-level breadth on this topic.

### 4.5 Evaluating Multi-Task Generalization Directly

Because the whole point of instruction tuning (Section 1.2) is generalization to *unseen* instruction types, the most direct evaluation methodology deliberately holds out entire task clusters from training -- not just held-out examples within each trained task type, but entire task *categories* the model never saw during instruction tuning at all -- and measures zero-shot performance on those held-out clusters specifically, exactly the evaluation design FLAN and T0 (Section 1.1) used to support their original generalization claims. This is a meaningfully stronger and more informative test than an aggregate held-out loss number (which mixes "did well on trained task types" with "generalized to untrained ones" into one score) or even a per-trained-category breakdown (Section 3.2), because it directly targets the specific capability -- generalization beyond the trained distribution -- that motivates the entire multi-task framing in the first place, rather than only measuring how well the model learned what it was explicitly shown.

### 5. Diagnosing Mixture Problems in Practice

A staff-level diagnostic checklist for "this model's behavior seems off in category X" that traces back to mixture design rather than a training bug:

1. **Is the issue a coverage gap or an interference effect?** Check whether category X was meaningfully represented in the mixture at all (a coverage gap, fixable by adding data) versus whether X was represented but a dissimilar, heavily-weighted category is pulling behavior away from it (an interference effect, per Section 2.3, fixable by reweighting or by examining whether the two categories' data can be made more format-consistent to reduce the interference).
2. **Is the issue format leakage from a different, overrepresented category?** Check whether the undesired behavior matches the surface conventions of a different, disproportionately large category in the mixture (File 001, Section 5.5) rather than being a capability gap at all.
3. **Is the issue actually inherited from pretraining, not introduced by the SFT mixture?** Check whether the base pretrained model (before any instruction tuning) already exhibits a related weakness on the same underlying capability -- if so, the fix may require more/better pretraining-adjacent data or a targeted capability-improvement effort, not a mixture reweighting, since instruction tuning's marginal job (File 001, Section 5.1) is behavioral shaping, not new-capability injection at scale.
4. **Would a later, verifiable-reward RL stage (File 005) be a better lever than reweighting the SFT mixture?** For math/code/structured-output categories specifically, mixture reweighting within SFT is often a weaker lever than adding or strengthening a dedicated RLVR stage, given RLVR's demonstrated advantage over pure imitation for exactly these verticals (File 005, Section 6).

### 5.1 A Worked Diagnostic Scenario

Suppose a team observes that their latest instruction-tuned model has become noticeably worse at following multi-part instructions ("do X, then Y, and format the result as Z") compared to the previous release, despite an aggregate held-out loss that looks flat or even slightly improved. Working through the checklist in Section 5: first, check whether multi-part instructions were adequately represented in the new mixture at all, or whether a recent data-refresh cycle inadvertently diluted this category's relative share while boosting others (a coverage regression, not a capability regression) -- this is common when a mixture is refreshed by adding a large new batch of data for one priority category without explicitly re-normalizing the relative shares of the categories that were not touched. Second, check whether a newly-added, heavily-weighted category (say, a large batch of short, single-instruction customer-support transcripts) is pulling the model's default behavior toward shorter, single-step responses in a way that bleeds into multi-part-instruction prompts specifically (an interference effect, Section 2.3) even though the multi-part-instruction category's own raw example count didn't change. Third, verify this against the held-out-task-cluster evaluation methodology in Section 4.5 rather than only the aggregate loss number, since aggregate loss is exactly the kind of metric that can mask this specific regression by averaging it against unrelated improvements elsewhere in the mixture. This kind of category-specific regression, invisible in an aggregate metric but real and diagnosable through the per-category and per-cluster evaluation practices this file recommends, is a recurring, realistic instruction-tuning production incident, not a contrived example.

### 5.2 Defining Task Clusters in the First Place

A prerequisite for everything in Sections 3-5 that is easy to gloss over: deciding what counts as one "task category" or "task cluster" at all is itself a nontrivial design choice, not a given. Coarse, hand-authored taxonomies (the kind implied by tables like Section 2.5's) are simple to reason about and to report on, but risk lumping together instructions that are more heterogeneous than the label suggests (e.g., "coding" spanning everything from a one-line syntax question to a multi-file refactoring task, with very different failure modes and mixture-share needs). Finer-grained, embedding-based clustering of the actual prompt distribution (grouping historical or synthetic prompts by semantic similarity rather than by a manually-assigned label) can surface a more accurate picture of where real coverage gaps and imbalances lie, at the cost of being harder to interpret and to act on directly, since an embedding cluster doesn't come with a ready-made human-readable category name or an obvious curation strategy attached to it the way a hand-authored category does. Mature instruction-tuning practice typically uses both: hand-authored categories for planning and reporting, cross-checked periodically against embedding-based clustering of real production traffic to catch coverage gaps the hand-authored taxonomy missed entirely.

### 5.3 Tool Use and Agentic Instruction-Following as a Growing, Distinct Category

Worth calling out as its own category, given how much of current post-training investment is shifting toward it: instructions that require the model to invoke external tools (search, code execution, file access, other APIs) and incorporate the results into a multi-turn plan are a structurally different instruction-tuning category from anything in the classical FLAN/T0-era task taxonomy (Section 1.1), because success depends not just on producing a good final response but on correctly deciding *when* to call a tool, *which* tool, with *what* arguments, and how to recover when a tool call fails or returns unexpected results. This category's mixture-design challenges compound Section 2's general problems in a specific way: demonstrations of good tool-use trajectories are more expensive to author than single-turn text responses (they require a working tool environment to generate realistic tool outputs against), the space of plausible failure modes is larger (malformed calls, hallucinated tool names, ignoring a tool's returned error), and under-representing this category in the mixture relative to its growing product importance is a common, live tension at labs whose product roadmaps are increasingly agent-centric. This is also a category where the RLVR lever from File 005 is increasingly applied directly (reward based on whether an agentic trajectory actually achieved a checkable end state), making it a concrete instance of Section 4.3's "layer a verifiable-reward RL stage on top of broad SFT" pattern for a rapidly growing rather than long-established vertical.

### 5.4 Multilingual Coverage as an Orthogonal Mixture Dimension

Everything in Sections 2-5 has been framed along the task-type axis, but production instruction-tuning mixtures must simultaneously balance a second, largely orthogonal axis: language coverage. A model can be well-balanced across task types within English and still exhibit sharply uneven instruction-following quality across languages, for reasons that compound rather than substitute for the task-type mixture problem -- pretraining data volume is itself highly skewed toward English and a handful of other high-resource languages, so a language's post-training ceiling is bounded by pretraining exposure exactly as File 001, Section 5.1's ceiling-effect argument describes, and on top of that, curated instruction-tuning demonstrations are typically far more available in high-resource languages, compounding the pretraining skew with an SFT-stage skew in the same direction rather than correcting for it. A mixture-design table like Section 2.5's is, in a fully rigorous treatment, actually a two-dimensional grid (task type by language) rather than a one-dimensional list, and under-resourcing this second axis is a common, easy-to-overlook way for a model to look well-balanced by an English-only evaluation suite while being substantially weaker in coverage and consistency for other languages -- worth naming explicitly as a mixture dimension distinct from, and multiplicative with, the task-type dimension this file otherwise focuses on.

### 5.5 Does Training Order Within a Mixture Matter?

A subtler question than "what proportion of each category" is "does the *order* in which task categories are encountered during training matter, given a fixed final mixture composition?" In practice, most production instruction-tuning runs shuffle the full mixture and treat order as unimportant beyond ensuring good randomization within and across categories per batch -- unlike pretraining curricula, which sometimes deliberately sequence data (e.g., easier-to-harder, or domain-staged) across training, instruction-tuning mixtures are typically small enough, and trained for few enough epochs (File 001, Section 1.2), that within-run ordering effects are a second-order concern relative to getting the overall proportions right in the first place. Where ordering does matter more is *across* discrete training stages rather than within one shuffled mixture -- for instance, whether a safety/refusal-heavy data batch is introduced early or late relative to a broad capability-establishing pass can materially affect whether refusal behavior is learned as an integrated part of the model's general judgment or as a late, more superficially-bolted-on pattern, echoing the sequencing considerations already discussed for layered vertical RL stages in Section 4.3.

### 5.6 How Mixture Design Interacts With the Downstream Preference-Tuning Stage

Everything in this file has focused on the SFT/instruction-tuning stage in isolation, but mixture design decisions here have direct, sometimes underappreciated consequences for the RLHF/DPO stage that follows (Files 002-003). A task category that is underrepresented or inconsistently formatted at the SFT stage produces an SFT/reference policy that is itself weak or inconsistent on that category -- and because that same policy serves as both the RL initialization and the KL-anchor reference distribution (File 002, Section 4.1), any weakness baked in at the instruction-tuning stage is inherited as the *starting point and the trust-region center* for the entire subsequent preference-optimization process, not merely as a capability gap that later stages might independently correct. Concretely: if multi-part instruction-following (Section 5.1's worked scenario) is weak after SFT, a downstream RLHF stage can improve it somewhat if preference data specifically covering multi-part instructions is included in RM training, but the RL policy is still exploring around, and penalized by a KL term for straying from, a reference distribution that is itself weak on this category -- making it a harder repair job at the RL stage than getting the SFT mixture right in the first place would have been. This is a concrete, mechanistic argument for why instruction-tuning mixture design deserves the same level of deliberate engineering attention as the RLHF/DPO stages that are, in casual discussion, more often treated as "where the real optimization happens" -- the SFT mixture silently sets the boundaries of what the later, more heavily-optimized stages are working with.

### 5.7 From Academic Multi-Task Benchmarks to Modern Chat Mixtures

It is worth being able to contrast the FLAN/T0/Super-NaturalInstructions era (Section 1.1) with current chat-assistant instruction-tuning mixtures directly, since the shift reflects a real change in what "task diversity" is even measuring:

| | FLAN/T0-era academic instruction tuning | Modern chat-assistant instruction tuning |
|---|---|---|
| Task definition | Discrete, benchmark-derived NLP tasks (translation, entailment, summarization, as separate labeled datasets) | Open-ended, conversational instructions without a fixed, closed task taxonomy |
| Primary evaluation | Zero-shot transfer to held-out benchmark tasks | Human or LLM-judge preference/win-rate on open-ended prompts (File 001, Section 7), plus targeted capability benchmarks |
| Data source | Repurposed existing labeled NLP datasets, reformatted into instruction templates | Purpose-written or purpose-generated demonstrations, licensed data, real product traffic (filtered), synthetic/distilled data |
| Response style | Short, benchmark-answer-shaped outputs | Long-form, conversational, stylistically varied outputs reflecting an assistant persona |
| Downstream stage | Often the terminus of training, or a precursor to task-specific fine-tuning | Almost always followed by a preference-optimization stage (Section 5.6) |

The throughline connecting the two eras is Section 1.2's core mechanism -- diversity of instruction type drives generalization -- but the object being diversified has shifted from "which discrete NLP benchmark task" to "which open-ended real-world request pattern," a genuinely harder and less crisply measurable diversification target, which is itself part of why modern mixture design (Sections 2-5) is more empirical and less benchmark-driven than the FLAN-era version of the same underlying problem.

### 6. Common Interview Traps

- **Treating "instruction tuning" and "SFT" as if they denoted different loss functions.** They denote the same mechanism (File 001); the distinction is one of framing and data-composition emphasis (Section 1.3), not mechanism.
- **Assuming more task diversity is always strictly better with no tradeoff.** Section 2.3's negative-transfer argument is the direct counterexample -- diversity helps generalization to unseen instructions but is not a free lunch against depth on any specific category, and can actively interfere with it.
- **Proposing "just balance the mixture evenly across all task types" as a solved default.** Uniform weighting ignores that different task categories have very different natural difficulty, natural data availability, and product-priority weight; naive uniform balancing is rarely the empirically best choice and is itself a design decision with tradeoffs, not a neutral baseline.
- **Not distinguishing a coverage gap from an interference effect when diagnosing a behavioral weakness.** Section 5's checklist exists because these have different, sometimes opposite, fixes (add more data of type X, versus reduce or reformat a different, dominant category Y).
- **Reaching for "just do RLVR instead" for every generality-versus-depth tension without noting RLVR's domain limitation (File 005, Section 2).** It is the right lever specifically for verifiable-outcome verticals (math, code); it is not a general answer to instruction-tuning mixture design for the large remaining space of tasks without a ground-truth verifier.

### 6.1 A Further Set of Interview Traps Worth Naming

- **Assuming instruction-tuning mixture design is a solved, checklist-driven process at frontier labs.** Public statements and the general research literature both suggest this remains substantially empirical and iterative, closer to careful craft-plus-ablation than to a settled formula -- a candidate who describes it as a solved pipeline is overstating the field's maturity here.
- **Ignoring cost-of-curation as a real constraint distinct from cost-of-compute.** Section 2.2's table makes this explicit: unlike pretraining-mixture problems, where raw data supply is frequently the binding constraint, instruction-tuning mixture problems are at least as often bound by how expensive and slow it is to *curate* enough good, consistent data for an underrepresented category, even when nothing stops you from allocating more compute budget to it.
- **Treating tool-use/agentic data as a minor addendum to a mostly-text-QA mixture.** Section 5.3 argues this is an increasingly incorrect prioritization given current product trajectories at frontier labs, and a candidate should be able to speak to why this category's mixture-design challenges are structurally harder, not just larger in volume, than classical single-turn text tasks.
- **Conflating task-cluster granularity choices with a purely cosmetic reporting decision.** Section 5.2 makes the case that how you define a "task category" materially changes what mixture problems you can even detect -- a coarse taxonomy can hide exactly the kind of regression described in Section 5.1's worked scenario.

### 5.8 Quantifying Mixture Diversity, Not Just Category Proportions

Beyond the category-proportion tables in Section 2.5, a more rigorous mixture audit measures diversity *within* categories, not only across them, since a category can be nominally well-represented by example count while still being narrow in substance -- a thousand coding examples that are all near-duplicate variations of a small number of underlying problems provide far less effective diversity than a thousand examples spanning genuinely distinct problem types, libraries, and difficulty levels. Practical proxies for this include embedding-based diversity scores (average pairwise distance, or the effective rank of the category's embedded-example covariance, among a category's examples in a semantic embedding space) and simple entropy measures over a finer-grained sub-category or cluster label distribution within the category (Section 5.2's clustering methodology, applied here as a measurement tool rather than only a taxonomy-design tool). Tracking these alongside raw example counts closes a real gap that a pure proportions table like Section 2.5's cannot: it distinguishes "this category has enough examples" from "this category has enough *effectively distinct* examples," which is the property that actually drives the generalization argument in Section 1.2.

### 6.2 One More Round of Traps, Scenario-Flavored

- **Given a report that "the model got worse at task X after we added a lot of new task Y data," jumping straight to "task Y data must be low quality."** Section 5.1's diagnostic scenario is exactly the counterexample: the more common root cause is interference or an inadvertent coverage dilution of X, not a quality defect in the newly-added Y data itself.
- **Recommending a full mixture rebalancing in response to every single-category regression.** A targeted fix (adjusting the specific interfering or under-covered category) is usually preferable to a full mixture re-derivation, which risks introducing new regressions elsewhere (Section 3.4's capability-tax tracking exists precisely to make this kind of whack-a-mole visible rather than invisible).
- **Treating the SFT mixture as fully decoupled from the downstream RLHF/DPO stage's eventual quality ceiling.** Section 5.6 is the direct rebuttal: SFT mixture weaknesses propagate forward as reference-policy weaknesses, not just as independently-correctable gaps.

### 7. Quick-Reference Summary

- Instruction tuning is SFT's mechanism (File 001) applied with deliberate emphasis on multi-task, multi-format data diversity, specifically to drive generalization to instruction types not seen during training -- a lineage traceable to FLAN, T0, and Super-NaturalInstructions predating chat-assistant post-training.
- Diversity drives generalization because it prevents the model from learning a narrow, single-task pattern-match shortcut in place of genuine instruction-following.
- The SFT/instruction-tuning mixture-balancing problem is related to, but distinct from, the pretraining-mixture problem: smaller data scale, curation-bounded rather than supply-bounded, behavioral/stylistic failure signals as much as benchmark-score failure signals, and finer-grained control.
- Negative transfer between dissimilar task categories, and cross-source format inconsistency, are two concrete, well-documented ways a poorly-designed mixture actively degrades quality rather than merely under-serving a category.
- Mixture ratios are tuned via a combination of heuristics, per-category-broken-down ablation studies, and (increasingly) dynamic loss-based reweighting -- with per-category "capability tax" tracking as the honest way to represent the resulting tradeoffs rather than searching for an illusory free-lunch mixture.
- The generality-versus-depth tension on high-value verticals (coding, math) is real and is navigated procedurally and architecturally -- layered specialized RL/SFT stages, dedicated model variants, MoE architectures, and post-hoc model merging -- rather than resolved by a single global mixture-ratio decision.
- Diagnosing a mixture-driven behavioral problem requires distinguishing coverage gaps, interference effects, pretraining-inherited weaknesses, and cases better addressed by a downstream RLVR stage than by SFT mixture reweighting at all.
- Instruction tuning raises the floor of zero-shot task competence and changes default response format/register in ways few-shot prompting on a non-instruction-tuned base model cannot reliably replicate, without making few-shot prompting obsolete as a supplementary steering tool.
- Task-cluster granularity is itself a design choice: coarse, hand-authored categories are easy to plan and report against but can hide regressions that finer-grained, embedding-based clustering of real traffic would surface.
- Language coverage is a second, largely orthogonal mixture dimension that compounds with the task-type dimension -- pretraining's language skew and SFT-data availability skew typically point in the same direction rather than correcting each other.
- Within-mixture training order is usually a second-order concern given small dataset sizes and few epochs, but ordering *across* discrete training stages (e.g., when safety data is introduced relative to broad capability training) can matter more.
- Tool-use and agentic instruction-following are a rapidly growing mixture category with structurally harder data-curation and failure-mode challenges than classical single-turn text tasks, and are increasingly handed off to a dedicated RLVR stage once a checkable end-state exists.
- Held-out task-cluster evaluation (measuring zero-shot performance on task types entirely absent from training) is the methodologically strongest way to validate that instruction tuning achieved its actual goal, as distinct from validating performance only on trained task types.
- Effective diversity within a category (measured via embedding-based dispersion or sub-cluster entropy) is a distinct property from raw example count, and a mixture audit that only tracks proportions can miss categories that are numerically well-represented but substantively narrow.
- The shift from FLAN/T0-era discrete benchmark tasks to modern open-ended conversational instructions is a shift in what "diversity" even means to measure, making current mixture design inherently more empirical and less benchmark-crisp than its academic predecessor.
- SFT mixture weaknesses are not independently correctable line items -- they propagate forward as weaknesses in the reference policy that anchors the entire subsequent RLHF/DPO trust region, making early mixture quality cheaper to get right than to repair downstream.

This file's overall throughline: instruction tuning's promise (generalization to unseen instructions via task diversity) and its central practical difficulty (balancing that diversity against depth, consistency, and cross-task interference) are two faces of the same underlying resource-allocation problem, and the engineering discipline of making that allocation explicit, measured per category and per cluster, and revisited after every change is what turns the promise into a reliably delivered property of a shipped model rather than an occasional, hard-to-reproduce result.

### 7.1 A Final Checklist for Reviewing Someone Else's Mixture Design

If asked in an interview to critique a proposed instruction-tuning mixture, a strong response works through a short, explicit list rather than reacting impressionistically to the proportions alone:

- Is there an explicit rationale documented per category, or only a set of numbers with no stated reasoning (Section 2.5)?
- Does the plan include per-category and held-out-task-cluster evaluation, or only an aggregate metric (Section 4.5)?
- Has within-category diversity been considered, or only raw example counts per category (Section 5.8)?
- Is language coverage treated as its own dimension, or silently folded into (and likely dominated by) the task-type dimension (Section 5.4)?
- Is there a plan for how this mixture's weaknesses will be visible to, and accounted for by, the downstream preference-tuning stage (Section 5.6)?
- Does the plan distinguish categories suited to a later RLVR stage from those that must rely on SFT-mixture quality alone (Section 4.3)?

A candidate who runs through a list like this is demonstrating the actual operational discipline this file argues for, rather than reciting the conceptual argument for why diversity matters without being able to show how that argument gets checked against a concrete proposal.

### 8.1 One Last Framing Worth Holding Onto

If pressed to justify why this comparatively unglamorous data-engineering topic deserves the same seriousness as the mathematically richer techniques elsewhere in this module, the honest answer is that mixture design is where a large share of a model's *actually observed* behavior originates, in a way that no amount of downstream RLHF/DPO sophistication can fully paper over if the underlying SFT mixture is poorly conceived -- Section 5.6 already makes this concrete for the preference-tuning handoff specifically. A staff engineer who can only discuss RLHF/DPO mechanics in depth, but treats "what data do we put in the SFT mixture and in what proportion" as an afterthought, is missing a component of the pipeline that is at least as consequential in practice as the more mathematically elaborate stages that follow it.
