### 1. Overview & Strategic Context

OpenAI released GPT-5 in August 2025. The single fact that governs everything else in this entry, stated directly in OpenAI's own launch materials and system card: **GPT-5 is a unified system, not one monolithic model.** It combines a fast, efficient model (handling the large majority of everyday queries with low latency) with a deeper, slower reasoning model (positioned explicitly in the lineage of the o-series' RL-trained extended-reasoning approach, covered in `008_O1_O3_Reasoning_Models.md`), and a real-time router that decides, per query, which of the two should handle a given request. OpenAI states the routing decision is driven by a combination of signals: task complexity, conversation context, explicit tool-use requirements, and explicit user requests (a user can directly ask the system to "think hard" about something, and separately, developers can force a tier via the API). This is a genuine strategic departure from every prior release in this document series: GPT-3, GPT-4, and GPT-4o were each shipped as a single addressable model (or a small family of independently selectable model sizes); GPT-5 is shipped as an orchestrated product surface where "which model answered this" is no longer a question the end user is expected to ask, let alone answer, in ordinary use.

The product packaging reinforces this framing. Via the API, GPT-5 ships in three explicit size/cost/latency tiers -- `gpt-5`, `gpt-5-mini`, and `gpt-5-nano` -- continuing OpenAI's now-standard practice (GPT-4o/GPT-4o-mini, GPT-4.1/mini/nano) of shipping a flagship alongside cheaper, faster siblings, but layering the router concept on top of that tiering rather than replacing it. In ChatGPT, GPT-5 is exposed as an auto-switching default (the router picks fast-vs-reasoning behind the scenes) plus manually selectable modes for users who want direct control -- a standard/fast conversational mode, a "Thinking" mode that invokes extended reasoning explicitly, and a "Pro" tier reserved for the hardest problems, which applies the most extended reasoning compute of any tier. Strategically, this is best read as OpenAI taking the central lesson of the o1/o3 program -- that test-time (inference) compute is an independently dialable capability axis, distinct from pretraining scale -- and converting it from a manually-selected model choice (the pre-GPT-5 ChatGPT experience, where a user had to explicitly pick GPT-4o versus o1/o3 from a model picker) into an infrastructure decision made automatically on the user's behalf, while preserving explicit override paths for both the power user (Thinking/Pro in ChatGPT) and the developer (tier selection and reasoning-effort-style controls in the API).

Two further confirmed, OpenAI-reported characteristics matter enough strategically to state here rather than defer entirely to Section 10: OpenAI reports a materially reduced hallucination rate and improved factuality/calibration for GPT-5 relative to the GPT-4-series, and reports state-of-the-art (at launch) results on coding and agentic benchmarks, notably SWE-bench-style software engineering tasks and multi-step agentic tool-use evaluations. Positioning GPT-5 as the first release where "trustworthiness of individual factual claims" and "reliability as an autonomous coding/tool-using agent" are both headline claims (rather than one being a footnote to the other) is itself a signal about where OpenAI believes the competitive and deployment pressure has moved: toward long-horizon, tool-using, high-stakes-correctness use cases (agentic coding, agentic workflows) rather than purely single-turn chat quality.

### 2. Architecture Deep Dive

This is the section where GPT-5 differs most sharply from every prior entry in this document, including its own immediate predecessor's treatment in `009_GPT4_1_And_GPT5.md`: there is a real, disclosed, architectural-level fact to discuss here, and it deserves to be treated with the same confidence as any other confirmed claim in this series, while keeping a crisp line between "the system design is disclosed" and "the models' internals are not."

**What is confirmed.** GPT-5-as-shipped is a router-orchestrated system with (at minimum) two model-class components: a fast/efficient model, and a deeper reasoning model. OpenAI states the router makes its dispatch decision using signals including task complexity, conversation context, whether a tool call is needed, and explicit user phrasing/requests ("think longer about this," or an explicit mode selection in the product UI). This is a disclosed architectural-level design choice about the *system*, not merely a marketing description -- it is the mechanism by which every query is actually served, and OpenAI has been specific enough about the decision inputs (complexity, context, tool needs, explicit request) that this is meaningfully more detail than the near-total silence covering, say, GPT-4's internals.

**Why this generalizes the o1/o3 lineage rather than merely reusing it.** The o1/o3 story (Section 2 and Section 6 of `008_O1_O3_Reasoning_Models.md`) established test-time compute -- "let the model generate a long, RL-trained chain-of-thought before answering" -- as an independently dialable axis of capability, exposed to a caller as an explicit `reasoning_effort` parameter (low/medium/high) that a developer or end user had to actively choose. That is the crucial detail to hold onto: in the o1/o3 product experience, *choosing to reason more* was a manual, per-request decision made by a human. GPT-5's router takes exactly that lever -- how much test-time compute to spend on this query -- and turns it into a first-class, always-on, automatically-inferred *system property* rather than a separate model family the user has to know exists and deliberately select. Put precisely: o1/o3 answered "can we scale accuracy by spending more inference compute on hard problems," and demonstrated that the answer is yes, given an explicit human choice to spend it. GPT-5 answers a different, harder question: "can the system itself learn to recognize, per query and without being told, when that extra compute is worth spending," and ships an affirmative answer to that question as the default consumer experience. This is a meaningful step up the automation ladder for the same underlying resource-allocation problem, and it is the single most important framing to have ready in an interview: GPT-5 is not "a bigger o3," it is "o3's central lesson (test-time compute is a dialable axis) generalized into an always-on routing decision that a whole product now makes on every request."

**What is inferable but not disclosed, about the router's own mechanics.** OpenAI has not published the router's architecture -- whether it is a small dedicated classifier model, a capability embedded in the fast model itself (e.g., the fast model emitting a confidence/escalation signal after a partial forward pass), a rule-based/heuristic gate, or some hybrid of these. It is reasonable (and consistent with how conditional-compute gating is generally built elsewhere in the field -- see the token-level MoE gating discussion in `006_GPT4.md`'s Section 2 MoE-rumor treatment) to expect the real mechanism sits somewhere on a spectrum between "cheap heuristic features (query length, presence of markers like explicit math notation, code fences, words like 'prove'/'step by step'/'carefully', or a detected tool-call requirement)" and "a small learned classifier over an embedding of the query and recent conversation state, trained on human- and/or model-graded labels of which tier a given query actually warranted." This document takes no position on which of these GPT-5 actually uses -- it is offered, and clearly labeled, purely as an illustration of the design space, and is exactly what the companion `.py` file implements as a labeled toy analogy, not a claim about GPT-5's real router.

**The structural throughline worth stating explicitly in an interview.** Query-level routing across whole models (GPT-5's confirmed design) and token-level expert routing across a sparse MoE layer's experts (the architecture rumored, not confirmed, for GPT-4 in `006_GPT4.md`) are the same underlying idea -- a learned or heuristic gate deciding which sub-network handles a unit of computation -- applied at different granularities of "unit of work" (a whole query versus a single token) and at different levels of the stack (a product-level orchestration layer versus an internal layer of one model). GPT-5 is genuinely novel in *making this gating decision a disclosed, product-level fact* rather than a rumored internal implementation detail -- which is itself worth noting as a shift in how much of the "conditional compute" story a frontier lab is now willing to say out loud.

### 3. Scale -- Parameters, Data, Compute

No parameter count has been disclosed for any component of the system -- not the fast model, not the reasoning model, and not the router. This continues OpenAI's non-disclosure policy unchanged from GPT-4 onward. What is confirmed as a structural fact, distinct from any specific number: the API-level tiering into `gpt-5`, `gpt-5-mini`, and `gpt-5-nano` confirms that *some* form of deliberate capacity/cost tiering exists as a shipped product line (as it did for GPT-4o/mini and GPT-4.1/mini/nano), and the fast-vs-reasoning split within the flagship experience confirms a *second*, orthogonal axis of capacity variation (compute spent per query at inference time) layered on top of the tiering axis. That gives GPT-5 two disclosed axes along which effective capability/cost varies -- which named API tier you call, and which internal path the router selects for a given call -- without either axis having a disclosed underlying size. Dense-versus-sparse (MoE) architecture for any component is not stated either way for GPT-5, exactly as for every prior GPT-series model in this document since GPT-4.

### 6. Post-Training / Alignment Approach

**Safe completions** is GPT-5's confirmed, named contribution here, and it merits being understood precisely rather than described loosely as "better safety tuning."

Prior-generation safety post-training (as documented for GPT-4 in `006_GPT4.md` via Rule-Based Reward Models, and implicitly for every RLHF-trained model in this series) is structured, at bottom, around a binary decision per request: comply, or refuse. The training signal rewards correct classification into one of those two buckets, conditioned on a policy specification of what is disallowed. OpenAI has documented this binary framing as having two well-known, opposite-direction failure modes: **under-refusal** (the model complies with something it should have refused, a safety failure) and **over-refusal** (the model refuses something that was actually benign or that had a legitimate, safe way to be partially or fully addressed, a helpfulness failure that materially damages the product experience and that GPT-4's own RBRM work explicitly targeted). Because both failure modes are measured against the same binary decision boundary, tightening the boundary to reduce one failure mode mechanically tends to increase the other -- classic precision/recall tension applied to a refusal classifier.

Safe completions reframes the *shape* of the target output rather than just retuning where the binary boundary sits. Instead of training the model to pick "comply" or "refuse" as a discrete action, the model is trained to produce the *most helpful response achievable within safety constraints* for a given request -- which, for a genuinely disallowed request, may still amount to a refusal, but for the large, previously-mishandled middle category of dual-use or partially-sensitive requests (a request that has both a legitimate, safe framing and a harmful one, e.g. a question that is simultaneously answerable in a way that helps a legitimate use case while withholding the specific operational detail that would make it dangerous), the model is trained to produce a graduated, partially-helpful, safety-respecting answer rather than either a flat refusal or a flat compliance. OpenAI frames this explicitly as addressing *both* failure directions simultaneously, rather than trading one off against the other: over-refusal drops because the model now has a legitimate, trained "helpful-but-bounded" response option instead of only "comply" or "refuse" to choose between for a borderline request; under-refusal drops (relative to a model that might otherwise over-correct toward compliance to avoid seeming unhelpfully evasive) because the graduated response is itself trained to withhold the specific harmful content even while being maximally helpful around it.

Why this is a genuine alignment-research contribution and not merely a product tweak: it changes the *output space* the safety training optimizes over, from a two-point discrete space {comply, refuse} to a continuous-in-spirit space of "how much of this request can be safely and helpfully addressed, and in what form." That is a different reward-modeling and data-labeling problem -- graders must now be able to rank partially-helpful, safety-respecting completions against each other (is this particular hedge, redirection, or partial-detail response better or worse than that one, for this specific dual-use request), not merely label full responses as acceptable or not. It also changes what a safety *evaluation* has to measure: pass/fail refusal-rate metrics under-describe a system that is deliberately trained to produce a spectrum of partial-compliance outputs, and a rigorous evaluation now has to grade *where on the helpfulness-within-safety-constraints spectrum* a given response actually landed, not just whether it crossed a binary line. This is the same underlying alignment-research move as GPT-4's Rule-Based Reward Models (target a known failure mode with a purpose-built training signal rather than relying purely on generic human-preference RLHF) but applied one level up: RBRMs refined *how the binary decision is made*; safe completions replaces the binary decision itself with a richer decision space.

Consistent with GPT-5's stated lineage connection to the o-series for its reasoning tier, it is a reasonable extension -- flagged here explicitly as informed extrapolation, not an independently confirmed detail about GPT-5's own pipeline -- to expect continuity with RLVR and deliberative-alignment techniques (`008_O1_O3_Reasoning_Models.md`, Section 6) for the reasoning component specifically, layered with safe-completions-style training applied across both tiers. A genuinely open, publicly-undisclosed question this document flags rather than answers: how (or whether) safe-completions behavior and its underlying graduated-response calibration are kept *consistent* across the fast and reasoning tiers, so that the router's tier assignment does not itself become a lever a user could pull to shift the system's effective safety posture.

### 7. Key Research Contributions & Novel Techniques

- **The router-as-system-design contribution**, discussed at length in Section 2: generalizing "how much test-time compute to spend" from a manually-selected model/parameter (o1/o3's `reasoning_effort`) into an automatically-inferred, always-on property of a deployed system. This is the headline, confirmed contribution of the entire release.
- **Safe completions**, discussed at length in Section 6: replacing binary refuse-or-comply safety training with graduated, maximally-helpful-within-constraints response training, targeting both over-refusal and under-refusal simultaneously by changing the output space rather than re-tuning a single decision boundary.
- **Reported factuality/calibration improvement.** OpenAI reports a materially reduced hallucination rate and improved calibration relative to the GPT-4 series as a headline evaluation claim for GPT-5 (Section 10 treats the evidentiary status of this claim). Whatever specific training techniques produced this improvement have not been disclosed in mechanistic detail; what is confirmed is that OpenAI is willing to report it as a first-class, named improvement axis for this release specifically, distinct from raw capability benchmarks.
- **Agentic and coding capability as a headline framing**, alongside (not subordinate to) conversational/reasoning quality -- state-of-the-art (at launch, per OpenAI's own reporting) results on SWE-bench-style software-engineering benchmarks and multi-step agentic tool-use evaluations, reflecting a broader field-wide shift (not unique to OpenAI) toward agentic, tool-using, long-horizon task performance as the evaluation frontier that matters most for 2025-era frontier releases.

### 8. Training Challenges & Engineering Solutions

Not disclosed for GPT-5 specifically. The challenges worth naming as reasoned inference, specific to a production router-based system design and clearly labeled as such (largely inherited from, and sharpened relative to, the discussion in `009_GPT4_1_And_GPT5.md`'s Section 8, now with the router treated as a confirmed rather than merely postulated component):

- **Mis-routing is the central failure mode, and it is asymmetric in cost.** Routing an easy query to the reasoning tier wastes latency and compute (a cost failure); routing a hard query to the fast tier degrades answer quality, potentially silently -- the user may not know the query warranted deeper reasoning and simply receives a worse answer with no visible signal that anything went wrong (a quality failure that is materially harder to detect than a cost failure, because cost failures show up in infrastructure metrics while quality failures show up only in downstream task success, which is much noisier and slower to observe). Any router-tuning program has to treat these as genuinely different currencies rather than folding them into one aggregate "routing accuracy" number, because the org will want to trade them off deliberately (e.g., biasing toward reasoning-tier routing for enterprise/agentic-tool-use contexts where a wrong answer is expensive, and biasing toward fast-tier routing for high-volume, low-stakes conversational traffic) rather than optimizing a single blended metric.
- **Building ground truth for "which tier did this query actually need" is itself hard.** Unlike a classification problem with objectively correct labels, the "necessary" tier for a given query is a function of the acceptable quality bar for that use case, which is not a fixed property of the query text alone -- the same query might legitimately warrant different tiers for a casual chat user versus an agentic coding pipeline with a low error tolerance. A rigorous router-evaluation methodology has to construct or approximate an oracle labeling (e.g., via graded comparison of fast-tier vs. reasoning-tier outputs on a query, at some fixed quality bar) rather than relying purely on end-to-end benchmark scores, precisely because a benchmark score conflates "how good is the fast model," "how good is the reasoning model," and "how good was the routing decision" into one number -- the same measurement problem flagged in `009_GPT4_1_And_GPT5.md`'s Section 8/10, now sharper because the router is a confirmed rather than hypothetical component.
- **Router drift under a continuously updated system.** If either the fast or reasoning component is updated independently over time (a documented pattern across the GPT lineage generally -- see the dated-snapshot practice noted for GPT-4 in `006_GPT4.md`'s Section 6), the router's notion of "which queries need escalation" can become stale relative to the components' actual current capability gap -- a query that needed escalation when the fast model was weaker may not need it after a fast-model update, and a router trained/tuned against an older component pairing needs a re-tuning or re-validation pass whenever either component changes, which is an ongoing MLOps obligation specific to this system design, not a one-time router-training problem.
- **Cross-tier consistency and user trust**, carried over from Section 8's discussion in `009_GPT4_1_And_GPT5.md`: a user experiencing occasional, hard-to-predict differences in tone, latency, or even substantive answer content depending on which tier silently handled a structurally similar query is a product-consistency problem with no clean precedent in a single-checkpoint model, and no public documentation exists of how OpenAI specifically monitors or bounds this.

### 9. Inference & Serving Considerations

This is one of the richest sections for GPT-5 specifically, because the system now confirmedly serves at least two, and in the full ChatGPT product plus API surface arguably more than two, distinct compute profiles behind a single product identity.

**The router's own latency budget is a hard constraint.** Whatever mechanism makes the routing decision must add negligible latency relative to the fast tier's own response time, or the fast path loses its entire reason for existing -- a router that itself takes a meaningful fraction of a second to decide "use the fast model" has partially defeated the purpose of having a fast model. This pushes any real implementation toward either a very cheap heuristic/classifier evaluated on the query alone (rather than requiring a full model forward pass through either candidate first) or a design where the fast model itself begins responding and a cheap, concurrent signal can escalate/redirect mid-stream -- OpenAI has not disclosed which of these (or another design) it uses, but the latency-budget constraint itself is not speculative; it follows directly from the stated product goal of a fast default path.

**Two (or more) effective serving profiles behind one product surface.** The fast tier should be provisioned like a high-throughput, latency-optimized conversational serving stack -- the profile any production LLM chat product has optimized for over the past several years (aggressive batching, KV-cache-efficient serving, and cost-per-token minimized as the dominant objective). The reasoning tier, by direct inheritance from the o1/o3 serving profile documented in `008_O1_O3_Reasoning_Models.md` Section 9, needs to tolerate long, "silent" generation periods (the hidden or extended reasoning trace) before any user-visible output token appears, which is a fundamentally different latency shape and a different capacity-planning problem (fewer, longer-running requests occupying serving slots for extended windows, versus many short-lived requests cycling quickly) -- these two profiles cannot share a naively identical serving configuration even if they happen to share hardware, and a real deployment almost certainly provisions and autoscales them somewhat independently, with the router acting as the dispatcher between two differently-shaped capacity pools. The "Pro" tier in ChatGPT, described as applying the most extended reasoning for the hardest problems, plausibly represents a third point on this same spectrum -- an even-longer-running, even-lower-throughput profile -- though OpenAI has not disclosed whether Pro is architecturally distinct from the standard Thinking/reasoning path or simply the same reasoning component configured for a larger compute/effort budget; this document takes no position on which, beyond noting the API precedent (a single o-series-lineage model exposing a `reasoning_effort` parameter) makes "same model, larger budget" the more parsimonious explanation without confirming it.

**Cost/latency implications for a caller.** Because the router (in ChatGPT) versus explicit tier selection (in the API) are both confirmed, real product paths, a developer building on GPT-5 has a genuinely different cost-predictability problem than a developer calling a single fixed model: calling `gpt-5` directly and calling the ChatGPT-style auto-routed experience are not the same cost/latency contract, and a production system that needs predictable per-request cost/latency (a common constraint for latency-SLA'd applications) has good reason to prefer explicit tier/effort selection over automatic routing precisely because it removes a source of request-to-request variance that the developer cannot directly observe or control -- this is a direct, practical consequence of the confirmed dual-mode design, not speculation about internals.

### 10. Evaluation, Benchmarks & Known Limitations

OpenAI's own launch and system-card materials report, for GPT-5: state-of-the-art (at time of launch) results on software-engineering-oriented benchmarks in the SWE-bench family, strong results on multi-step agentic tool-use evaluations, and a reduced hallucination rate together with improved factuality/calibration relative to the GPT-4-series models, measured against OpenAI's own selected evaluation suites. As with every model in this document, these are self-reported numbers on self-selected evaluations rather than independently reproduced third-party results -- the same caveat applied throughout this series, including to o3's largely OpenAI-reported figures in `008_O1_O3_Reasoning_Models.md` (that entry's ARC-AGI/FrontierMath third-party evaluations remain the exception, not the rule, across this entire document; no comparably independent third-party evaluation of GPT-5 is treated here as confirmed, absent a specific citable source).

A limitation specific to GPT-5's system design, carried forward and sharpened from `009_GPT4_1_And_GPT5.md`: any benchmark score attributed to "GPT-5" is entangled with the router's tier-assignment behavior on that benchmark's particular query distribution. This matters more, not less, than it did in the prior entry's more speculative treatment, precisely because the router is now a confirmed production mechanism rather than a hypothesized one -- an external evaluator genuinely cannot cleanly decompose a reported aggregate score into "capability of the fast model," "capability of the reasoning model," and "quality of the routing decision" without additional disclosure OpenAI has not provided (e.g., per-tier breakdowns of which fraction of a given benchmark's queries were routed to which tier). Known, stated-or-inferable limitations otherwise: hallucination is reduced, per OpenAI's own reporting, but not eliminated -- "reduced hallucination rate" is a relative, not absolute, claim, and should not be read as "solved." Cost and latency remain real constraints for the reasoning tier specifically, inherited directly from the o1/o3 serving profile. As with every closed model in this document, there is no independent means of verifying any architectural claim; all evaluation here is API/product-mediated and OpenAI-curated, and the system's added orchestration layer (the router) makes that black-box property, if anything, slightly more opaque than it was for a single-checkpoint predecessor.

### 11. Confirmed Facts vs. Speculation

### 12. Staff/Research Interview Talking Points

- Lead with the framing distinction, stated with confidence: GPT-5's defining disclosed property is that it is a *system* (router plus at least two model-class components) rather than a single checkpoint -- and be ready to explain precisely why this is a disclosed architectural fact (OpenAI states the router and its decision inputs directly) even though the components' internals remain as undisclosed as any prior GPT-series model's. Conflating "the system design is public" with "the models are public" is the single most common sloppy mistake to avoid here.
- Be able to state the o1/o3-to-GPT-5 lineage precisely, not just gesture at it: o1/o3 demonstrated test-time compute as an independently scalable axis and exposed it as a manual, per-request `reasoning_effort` choice; GPT-5 generalizes the same underlying resource-allocation idea into an automatically-inferred, always-on, system-level default, while still preserving manual override paths (Thinking/Pro in ChatGPT, explicit tier/effort selection in the API) for callers who want direct control.
