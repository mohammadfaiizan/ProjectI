# 007 — Seq2Seq Encoder-Decoder (Companion Notes)

Companion to `007_seq2seq_encoder_decoder.py`. This file implements the classic encoder-decoder architecture (`Encoder`, `Decoder`, `Seq2SeqModel`) and trains it on two synthetic sequence-transformation tasks built out of WikiText-2 sentences (reversing a sentence, and copying it) to demonstrate variable-length input to variable-length output mapping.

## Sequence-to-Sequence Encoder-Decoder (Sutskever et al., 2014)

### 1. What Problem It Solved

Every architecture up to this point in the series — vanilla RNN, LSTM, GRU — is naturally suited to tasks where the output has the same "shape" as the input at every position: predict the next word at each time step, tag each word with a label, and so on. But many of the most interesting language tasks don't work that way. Machine translation is the clearest example: translating an English sentence of 8 words into a French sentence of 11 words is not a position-by-position mapping — there's no rule that says "the 3rd French word corresponds to the 3rd English word." Summarization, question answering, and many other tasks share this property: the input and output are sequences, but they can be different lengths and don't align position-for-position.

Sutskever, Vinyals, and Le (2014) — the paper usually credited with popularizing this approach for neural machine translation — solved this with a two-part architecture: an **encoder** that reads the entire input sequence and compresses it into a single fixed-size vector, and a **decoder** that takes that vector and generates the output sequence, one token at a time, for as many steps as needed. Because the compression step and the generation step are decoupled, the input and output no longer need to be the same length, or aligned position-by-position at all.

### 2. Architecture — How It Works

**Intuition first.** Think of the encoder as reading the entire input sentence and writing a short summary note — a single vector capturing "here's what this sentence was about." The decoder never sees the original input sentence directly; it only ever sees that one summary note (as its starting hidden state) and then generates the output sequence word by word, using its own hidden state (initialized from that note) to keep track of what it has generated so far.

**The precise computation**, as implemented in this code. The `Encoder` is an LSTM (`embedding_dim=128`, `hidden_dim=256`, `num_layers=2`, unidirectional) that processes the padded input sequence (using `pack_padded_sequence`/`pad_packed_sequence` to efficiently skip computation on padding tokens) and returns two things: `outputs` (the hidden state at every input position) and `hidden` (the final hidden state and cell state, `(h_n, c_n)`, from the last real token of each sequence). Critically, in this file's `Seq2SeqModel.forward`, only `encoder_hidden` — the *final* hidden/cell state — is passed on to the decoder as its initial state; `encoder_outputs` is computed and returned but never actually used by the decoder. That final hidden/cell state pair, of fixed size `256` regardless of how long the input sentence was, is the **context vector** — the entire input sentence has been compressed into this one fixed-size representation.

The `Decoder` is a second, separate LSTM (same dimensions) that starts from that context vector as its initial hidden state, and then generates output tokens one at a time:

```
decoder_hidden = encoder_hidden          # the context vector "primes" the decoder
decoder_input  = <SOS>                    # start-of-sequence token
for each output step:
    decoder_output, decoder_hidden = Decoder(decoder_input, decoder_hidden)
    next_input = ground_truth_token  OR  argmax(decoder_output)   # depending on teacher forcing
```

**Teacher forcing.** During training, at each decoding step, the code makes a random choice (`teacher_forcing_ratio=0.5`, decided independently at every single time step, not once per batch): with 50% probability, feed the *actual* correct previous target token as the next input (this is "teacher forcing" — showing the decoder the right answer so it doesn't compound its own mistakes early in training); otherwise, feed the model's own predicted token back in (this matches what will happen at inference/generation time, when there is no ground truth to feed). Mixing the two during training helps the model be robust to using its own (possibly imperfect) predictions, which is exactly what it must do at generation time, when `teacher_forcing_ratio=0.0` is used unconditionally (see `evaluate_model` and `generate`).

**The information bottleneck.** This is the architecture's defining limitation, and it's a direct, structural consequence of the design described above: no matter how long the input sentence is — 5 words or 50 — the *entire* thing has to be squeezed through a single fixed-size vector (256 numbers, in this code) before the decoder can start generating. For short sentences this is rarely a problem. For long sentences, this becomes a serious information bottleneck: the encoder has to decide, while reading the sentence and without knowing yet what the decoder will need, what information is important enough to preserve in that one fixed-size vector, and any nuance that doesn't fit gets lost. This is exactly the problem that attention (the very next file in this series) was invented to solve — by letting the decoder look back at *all* of the encoder's per-position outputs (the same `outputs` tensor this file computes but throws away) instead of relying on one compressed vector.

### 3. Model Size & Parameters

The original 2014 Sutskever et al. paper used a genuinely large model for its time: a 4-layer LSTM with 1,000 hidden units per layer, an 8,000-dimension word embedding, and a vocabulary of 160,000 words on the source side and 80,000 on the target side, trained on roughly 12 million sentence pairs — this totaled in the hundreds of millions of parameters, and was considered a very large neural network for 2014, trained on a cluster of GPUs for about 10 days.

This repo's code is dramatically smaller, both because it's meant to run quickly for learning purposes and because it's demonstrating synthetic tasks rather than real translation: the `Encoder` and `Decoder` each use `embedding_dim=128`, `hidden_dim=256`, `num_layers=2`, with a vocabulary capped at 3,000 words. Working through the shapes: each of the encoder and decoder has its own embedding table (~384,000 parameters each, since they are not shared/tied), and each has a 2-layer unidirectional LSTM (~920,000 parameters, matching the LSTM calculation from file 005 at the same dimensions); the decoder additionally has an output projection layer back to the vocabulary (~770,000 parameters) which the encoder doesn't need. That comes out to roughly 1.3 million parameters for the encoder and roughly 2.1 million for the decoder, for a combined total of around **3.4 million parameters** — a tiny fraction of the original paper's scale, but enough to clearly demonstrate the encoder-decoder mechanism and its bottleneck on short synthetic sequences.

### 4. Dataset & What It Was Trained On

The original Seq2Seq paper was trained and evaluated on the WMT'14 English-to-French machine translation dataset, a large parallel corpus of sentence pairs specifically curated for translation.

This code does not have access to a real translation corpus, so it constructs two **synthetic sequence-transformation tasks** out of plain WikiText-2 sentences: a `reverse` task (the target sequence is the input sequence reversed) and a `copy` task (the target sequence is identical to the input). Sentences are extracted by splitting WikiText-2 text on periods, tokenizing with NLTK, and keeping sentences with 5-20 tokens; only small subsets are used (2,000 training sentences, 400 validation, 400 test), with a vocabulary of 3,000 words plus `<PAD>`, `<UNK>`, `<SOS>`, `<EOS>` special tokens.

Using `reverse`/`copy` instead of real translation is a reasonable teaching substitute for a specific reason: these tasks still require the model to learn a genuine sequence-to-sequence transformation (the model must actually process the whole input and generate a correctly-ordered, correctly-lengthed output — it can't cheat with a simple word-by-word copy for `reverse`), while being far easier to generate labels for (no parallel corpus needed) and far easier to score correctness on by eye. They isolate the *architecture's* behavior (does the encoder-decoder mechanism work, and where does it break down for longer sequences) from the *linguistic difficulty* of real translation.

### 5. Training Process

**Objective.** The model is trained to predict the target sequence token by token, using `nn.CrossEntropyLoss(ignore_index=0)` — the `ignore_index=0` matters here because `<PAD>` is vocabulary index 0, so padding tokens added to make batch sequences equal length don't contribute to the loss.

**Optimization.** Adam optimizer, learning rate `0.001`, batch size 32, trained for 10 epochs (the `train_model` function defaults to 15, but `main()` explicitly overrides this to 10 for the demonstration). Gradient clipping is applied with a norm threshold of `1.0`.

**Data handling.** Because input and target sequences vary in length within a batch, a custom `collate_fn` pads every sequence in a batch up to that batch's maximum length (separately for inputs and targets), and the encoder uses `pack_padded_sequence` to avoid wasting computation on the padding.

**Historical note.** The original paper trained with plain SGD (with a fixed learning rate that was halved after a certain number of epochs) rather than Adam, used much larger batches distributed across multiple GPUs, and reversed the *source* sentence's word order as an empirical trick that they found made optimization easier (a detail unrelated to this file's own `reverse` task, which reverses the *target*, not the source, as part of its synthetic task design).

### 6. Training Challenges

The headline challenge is the fixed-length context vector bottleneck described above: everything the decoder will ever know about the input has to pass through one 256-dimensional vector. Longer or more complex input sequences increase the chance that important information gets compressed away before the decoder ever sees it. This is a fundamentally different kind of training challenge than vanishing gradients — it's not that the *gradient signal* fails to reach early time steps (LSTM's gating already handles that reasonably well), it's that the *architecture itself* imposes a hard information ceiling regardless of how well it's trained.

A second, more practical challenge is **exposure bias**, which teacher forcing is a partial (imperfect) fix for: if you only ever train the decoder by feeding it ground-truth previous tokens, it never learns to recover from its own mistakes, because at generation time it has no ground truth to fall back on and any early error can compound into a badly derailed output. Randomizing teacher forcing at 50% per step (as this code does) exposes the model to some of its own predictions during training, trading off training stability (which teacher forcing helps with) against generation robustness (which needs practice using the model's own outputs).

A third, task-specific challenge visible in this code's design: the `reverse` task is deliberately a harder test of the architecture than `copy`, because reversing requires the decoder to correctly "remember" input tokens in a completely different order than it saw them (maximal need for the encoder's context vector to preserve full sentence content), whereas `copy` can partially succeed just by learning a simpler general "generate what you saw" pattern.

### 7. Performance & Evaluation

The code evaluates using validation loss (cross-entropy, ignoring padding) and additionally computes a simplified **BLEU-like score** (`calculate_bleu_score`) — note this is a simplified stand-in for real BLEU (which uses n-gram precision with a brevity penalty across n=1 to n=4); this code's version only measures 1-gram (single-word) overlap between predicted and target word sets, multiplied by a length-ratio penalty, so it should be understood as a rough proxy for generation quality rather than a rigorous BLEU implementation.

Historically, the original Sutskever et al. Seq2Seq model achieved a BLEU score of 34.8 on the WMT'14 English-French test set (and, notably, improved further when used to *rescore* the outputs of an existing phrase-based statistical machine translation system, reaching 36.5) — a genuinely competitive result against the statistical machine translation systems that were still state-of-the-art at the time, which was the paper's key claim: a purely neural, end-to-end trained system could match hand-engineered statistical translation pipelines. The paper also specifically noted that performance degraded on longer sentences, which is the empirical fingerprint of the context-vector bottleneck this file's documentation is built around.

### 8. Impact — Why It Mattered

This architecture proved that a single neural network could learn variable-length sequence transformation end-to-end, without any of the hand-built alignment models, phrase tables, or language-specific engineering that statistical machine translation systems relied on. That result reoriented the field: within roughly a year, neural sequence-to-sequence models replaced statistical MT as the dominant approach, and the same encoder-decoder pattern was applied far beyond translation — to summarization, dialogue systems, speech recognition, and image captioning (pairing a CNN encoder with an RNN decoder). Its most direct legacy in this series, though, is the bottleneck it exposed: because the whole input has to be compressed into one fixed vector, the very next architectural idea — attention (files 008 and 009) — exists specifically to let the decoder look back at every encoder position instead of relying on a single compressed summary. The encoder-decoder *framing* itself survived that change completely intact and is still exactly how modern systems (including Transformer-based translation and even many large language model use cases) are structured; what changed is *how* the decoder accesses the encoder's information.

### 9. How To Explain This In An Interview

"Before Seq2Seq, sequence models were mostly built for tasks where the output aligns position-by-position with the input, like next-word prediction or tagging. Machine translation doesn't work that way — input and output can have completely different lengths with no fixed alignment. Sutskever et al.'s 2014 fix was an encoder-decoder split: an encoder LSTM reads the whole input and compresses it into a single fixed-size context vector — in my implementation, just the encoder's final hidden and cell state — and a decoder LSTM, initialized from that vector, generates the output one token at a time, feeding each predicted token back in as the next input. I trained this on synthetic reverse and copy tasks built from WikiText-2 sentences, since I didn't have a real parallel translation corpus, specifically because those tasks still require genuine full-sequence understanding while being easy to generate labels for. I used teacher forcing at a 50% ratio during training — randomly choosing whether to feed the decoder the ground-truth previous token or its own prediction — which stabilizes early training while still giving the model practice recovering from its own mistakes, since at actual generation time there's no ground truth to fall back on. The architecture's fundamental limitation, which is really the whole point of studying it in this sequence, is the context vector bottleneck: the entire input sentence, no matter how long, gets squeezed into one fixed-size vector before the decoder ever sees it, so information gets lost on longer or more complex inputs. That bottleneck is exactly what motivated the next breakthrough — attention — which lets the decoder look back at every encoder position instead of just one compressed summary."
