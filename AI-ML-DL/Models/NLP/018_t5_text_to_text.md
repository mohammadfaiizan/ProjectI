# T5: The Text-to-Text Transfer Transformer

This file (`018_t5_text_to_text.py`) implements a small, educational version of **T5** (Text-to-Text Transfer Transformer), the 2019 Google model that reframed every NLP task — classification, translation, summarization, question answering, generation — as the exact same problem: take text in, produce text out. It builds a full encoder-decoder Transformer with T5's learned relative-position attention bias, implements T5's span-corruption pre-training objective, and demonstrates several downstream tasks expressed with T5-style task prefixes, training all of it on a small WikiText-2 subset.

Only one real, named model is covered in this file: **T5**. T5 was released in five published sizes (T5-Small through T5-11B), and the whole family is discussed below since interviewers expect you to know the concrete scaling numbers.

---

## T5 (Raffel et al. 2019)

### 1. What Problem It Solved

By 2019, pre-training (BERT, GPT-1/2) had already solved the problem of learning general-purpose language representations from unlabeled text. But there was still a second, less-discussed problem: **every downstream task needed its own architecture and its own training recipe layered on top of that pre-trained model.**

Concretely: a BERT-style classifier needs a `[CLS]` token, a pooling layer, and a brand-new linear layer sized to however many labels the task has. A BERT-style extractive QA model needs two separate span-start/span-end output heads bolted onto the token representations. A translation system typically used an entirely different encoder-decoder architecture trained with its own seq2seq loss. Summarization models were sometimes extractive (score-and-select sentences) and sometimes abstractive (generate new text), which are structurally different problems. Even though the underlying pre-trained weights could sometimes be shared, the "last mile" — how you turn hidden states into an answer, and what loss you optimize to get there — was different for every task. This meant NLP engineering was still a zoo of task-specific heads, task-specific losses, and task-specific data formats, even in the "pre-train once" era.

T5's fix was to notice that literally all of these tasks can be described as: "here is some input text, produce some output text." A classification label is just a short string ("positive"). A translated sentence is a string. A summary is a string. An extracted answer is a string. If you commit to that framing, you need exactly **one architecture** (a text-in, text-out encoder-decoder Transformer), **one loss function** (cross-entropy over output tokens, i.e., maximum likelihood text generation), and **one training procedure** for every task that exists. The only thing that changes between tasks is the text itself — specifically, a short instruction prepended to the input (a "task prefix") that tells the model which job it's doing this time.

### 2. Architecture — How It Works

**Big picture.** T5 is a standard Transformer **encoder-decoder** (the same shape as the original 2017 "Attention Is All You Need" translation model), not an encoder-only model like BERT or a decoder-only model like GPT. The encoder reads and understands the input text; the decoder generates the output text one token at a time, conditioning on both what it has generated so far and the encoder's understanding of the input (via cross-attention). This file's `T5Model` class implements exactly this shape: `encoder_layers` (a stack of `T5Layer` with `is_decoder=False`) and `decoder_layers` (a stack of `T5Layer` with `is_decoder=True`), connected by cross-attention, sharing one token embedding table (`shared_embedding`) that is also tied to the final output projection (`lm_head.weight = self.shared_embedding.weight`) — the same "tie the input and output embeddings" trick used in most Transformer language models to save parameters.

**Relative position bias, not absolute position embeddings.** Instead of adding a position vector to each token's embedding (like BERT's learned absolute positions, or the original Transformer's sinusoidal positions), T5 injects position information directly into the attention *scores*. This file's `T5RelativePositionBias` does this: for every pair of query/key positions, it computes their relative distance, buckets that distance (32 buckets by default — half reserved for small/exact distances close to zero, half for a logarithmically-scaled range covering distances up to `max_distance=128`), looks up a learned scalar bias per attention head for that bucket, and adds it straight onto the raw attention logits before the softmax (`scores += position_bias` in `T5Attention.forward`). The practical benefit: because the bias depends only on *relative* distance rather than absolute position index, the same learned biases generalize better to sequence lengths not seen during training — the model never has to see position "500" in training to handle it at position 500 at inference, because what matters is "40 tokens away," not "at slot 500." (One implementation detail worth flagging: in this file, each self-attention layer creates and owns its *own* `T5RelativePositionBias` instance rather than sharing a single bias module across all layers the way the official T5 implementation does — a simplification that doesn't change the concept but does mean the bias is learned independently per layer here.)

**Layer internals.** Each `T5Layer` does self-attention (with the relative bias above) → residual add → LayerNorm, then — if it's a decoder layer — cross-attention to the encoder's output → residual add → LayerNorm, then a feed-forward block (`Linear → ReLU → Dropout → Linear`) → residual add → LayerNorm. (Real T5 uses a bias-free, mean-subtraction-free variant of LayerNorm called "T5LayerNorm"/RMSNorm-style normalization, applied *before* each sub-block rather than after — this file uses standard `nn.LayerNorm` applied *after* the residual add, a simplification of the exact normalization recipe, though the overall encoder-decoder-with-cross-attention shape is faithful to the paper.) The decoder's self-attention is causally masked (`create_causal_mask`), so it can only attend to previously generated tokens, exactly like a GPT decoder — the encoder's self-attention is fully bidirectional, exactly like BERT.

**Task prefixes — how "everything is text" actually gets encoded.** The task is specified purely through a short prefix string prepended to the input, with no architectural change at all. This file's `T5Dataset` class builds exactly this kind of data for several tasks:

- **Classification (sentiment).** Input: `"sentiment: <sentence tokens>"`. Target: `"positive"` or `"negative"`. (In `_create_classification_examples`, the label itself is produced heuristically by counting positive/negative keyword hits in the sentence — a stand-in for a real labeled dataset.)
- **Translation.** Input: `"translate english to french: <sentence tokens>"`. Target: the sentence with a handful of common words swapped via a tiny hand-written English→French dictionary (`translation_dict`) — a toy stand-in for real machine translation.
- **Summarization.** Input: `"summarize: <sentence tokens>"`. Target: a short extractive "summary" built heuristically from the first word, the longest word, and the last word of the sentence (`_create_summarization_examples`) — again a stand-in, not a learned abstractive summary.
- **Question answering.** Input: `"question: what is mentioned? context: <sentence tokens>"`. Target: the longest word in the sentence, used as a toy "answer."

In every case, the *model* doesn't need to know or care which task it's doing — it just sees a token sequence and produces a token sequence. The prefix is the only signal that tells it "this time, behave like a translator" versus "this time, behave like a classifier."

**Span corruption — the actual pre-training objective.** This is T5's version of BERT's masked-language-modeling, and it's also implemented directly in this file (`_create_span_corruption_examples`, the default `task='span_corruption'`). The procedure: take a sentence, randomly select about 15% of its tokens to corrupt, group the corrupted positions into contiguous spans of 1–3 tokens each, and replace each *entire span* with a single unique sentinel token (`<extra_id_0>`, `<extra_id_1>`, ...). The **input** becomes the sentence with those spans blanked out and replaced by sentinels. The **target** is just the sentinels followed by the tokens they replaced — i.e., "`<extra_id_0>` [span 0 tokens] `<extra_id_1>` [span 1 tokens] ... `</s>`". The model never has to reproduce the parts of the sentence it wasn't asked about — only the missing spans — which makes the target sequence much shorter than the input, and therefore cheaper to train on than an objective that reconstructs the whole sequence. This is strictly harder than BERT's token-level masking (predicting a *span* of unknown length from a single sentinel, rather than predicting one hidden word at a time with the rest of the sentence untouched), which is part of why the T5 paper found it to be a stronger pre-training signal.

### 3. Model Size & Parameters

**Real, published T5 family (Raffel et al., 2019 — Table 2 in the paper):**

| Model | Encoder+Decoder Layers | `d_model` | `d_ff` | Attention heads | Parameters |
|---|---|---|---|---|---|
| T5-Small | 6 + 6 | 512 | 2048 | 8 | ~60 million |
| T5-Base | 12 + 12 | 768 | 3072 | 12 | ~220 million |
| T5-Large | 24 + 24 | 1024 | 4096 | 16 | ~770 million |
| T5-3B | 24 + 24 | 1024 | 16384 | 32 | ~2.8 billion (rounded up to "3B" in the name) |
| T5-11B | 24 + 24 | 1024 | 65536 | 128 | ~11 billion |

Note the pattern: from T5-Large upward, most of the parameter growth comes from widening the feed-forward dimension (`d_ff`) and the number of attention heads, not from adding more layers — `d_model` and layer count actually stay fixed at 1024 / 24+24 all the way from Large to 11B.

**What this code actually uses:** in `main()`, `T5Model` is instantiated with `hidden_size=256`, `num_heads=8`, `num_encoder_layers=4`, `num_decoder_layers=4`, `ff_size=512`, over a vocabulary capped at 3,000 tokens built from a 600-sentence WikiText-2 subset. Working through the parameter math for this configuration (embedding table tied with the output head, 4 encoder layers, 4 decoder layers each with their own per-layer relative-position-bias table, standard LayerNorms) comes out to roughly **6 million parameters** — around 10x smaller than even T5-Small's 60 million, and about 1,800x smaller than T5-11B.

**Why the gap:** the real T5 family needed that much capacity to absorb a 750GB pre-training corpus and to hold a wide-coverage SentencePiece vocabulary — capacity that would be pure overkill (and would train far too slowly for a laptop CPU demo) on a few hundred WikiText-2 sentences with a 3,000-word vocabulary. Shrinking `d_model`, layer count, and `d_ff` all together keeps the mechanics (encoder-decoder, relative bias, span corruption, task prefixes) fully intact while making the code runnable in minutes without a GPU.

### 4. Dataset & What It Was Trained On

**Real T5 pre-training data: C4 (the "Colossal Clean Crawled Corpus").** Google built C4 specifically for this paper by taking a monthly snapshot of Common Crawl (raw scraped web text) and running it through an aggressive cleaning pipeline: deduplicating pages, discarding lines without terminal punctuation, discarding pages with placeholder/boilerplate text (like "lorem ipsum" or "terms of use"), filtering out code, keeping only text detected as English, and removing offensive content via a wordlist filter. The result was roughly **750GB of cleaned text** — a figure the code itself references directly in one of its summary print statements ("Pre-training: Span corruption on C4 dataset (750GB)"), confirming it's aware of the real dataset even though it doesn't use it.

**What this code uses:** WikiText-2, a much smaller public dataset of Wikipedia articles (about 2 million tokens total). `load_wikitext2_dataset()` lowercases the text, splits on periods into pseudo-sentences, tokenizes with NLTK's `word_tokenize`, and keeps only sentences with 5–20 tokens. `main()` then takes just the first 600 sentences for training, 120 for validation, and 120 for test, and builds a 3,000-word vocabulary from that subset, augmented with T5-specific special tokens (`<PAD>`, `<UNK>`, `<EOS>`, `</s>`, `<s>`, and five sentinel tokens `<extra_id_0>` through `<extra_id_4>` — versus the real T5's 100 sentinel tokens, which caps how many spans this demo can corrupt in a single example at 5).

**The gap:** roughly six orders of magnitude in corpus size (a few hundred sentences vs. 750GB of crawled web text), whole-word vocabulary capped at 3,000 tokens versus SentencePiece subword tokenization with a ~32,000-token vocabulary that gracefully handles rare and unseen words. The demo is enough to exercise every mechanic in the pipeline (span corruption, task prefixes, teacher-forced decoding) and to see the loss go down; it is nowhere near enough data to learn transferable language understanding.

### 5. Training Process

**Real objective (pre-training):** span-corruption denoising, exactly as described in section 2 above — cross-entropy loss over the target token sequence (sentinels plus the corrupted spans), computed with teacher forcing (the decoder sees the correct previous target tokens at every step during training, not its own predictions). T5 was pre-trained for a huge number of steps over C4 (the base configuration trained for roughly 2^19 steps at a batch size that works out to about 34 billion tokens observed), and — depending on the checkpoint — sometimes with a small amount of supervised downstream-task data mixed in during pre-training itself (T5's multi-task pre-training variants). After pre-training, each downstream task is handled by **fine-tuning all of the model's parameters** (not adding a new head) on that task's labeled text-to-text data, using the same cross-entropy loss.

**This file's training loop (`train_t5`):** AdamW optimizer, learning rate `1e-4`, weight decay `0.01`, gradient-norm clipping at 1.0, batch size 4, run for 5 epochs. Each step performs teacher-forced decoding — the decoder's *input* is the target sequence shifted right by one position (`target_ids[:, :-1]`), and the decoder's *training target* is the same sequence shifted left by one (`target_ids[:, 1:]`) — and computes cross-entropy loss with `ignore_index=0` so padding tokens don't contribute to the loss. `evaluate_t5` runs the identical forward pass with gradients disabled to get a validation loss.

One detail worth being precise about: `T5Dataset` implements *five* task types (`span_corruption`, `classification`, `summarization`, `translation`, `question_answering`), but `main()` only actually calls `train_t5` on the first two of the three tasks it lists (`tasks = ['span_corruption', 'classification', 'summarization']`, then `for task in tasks[:2]`) — so this file trains and reports results for span corruption and classification, while the summarization, translation, and QA dataset-builders exist and are fully runnable but are never exercised in the demo run.

### 6. Training Challenges

- **Cost of pre-training at scale.** Building C4 itself was a significant engineering effort (cleaning 750GB out of raw Common Crawl), and pre-training the larger T5 checkpoints (especially T5-11B) required substantial TPU infrastructure — this is part of why the paper is as much a large-scale empirical study (they ran dozens of ablations on objective, architecture, and data choices) as a single model release.
- **Task interference in multi-task training.** Because T5 can mix pre-training and many downstream tasks into one text-to-text stream, the paper had to run careful ablations on *how* to mix task data (fixed proportions, temperature-scaled sampling by dataset size, etc.) — get the mixture wrong and performance on some tasks degrades relative to training on that task alone, a classic multi-task learning trade-off.
- **Generative decoding is expensive for tasks that don't need it.** Using a full autoregressive decoder to emit the single word "positive" for a classification task is a lot more expensive per example than a single linear classification head — the price T5 pays for architectural uniformity.
- **In this demo's code specifically**, the small vocabulary (3,000 words) and tiny corpus (a few hundred sentences) mean the heuristic task labels (keyword-based sentiment, extractive summaries, toy word-substitution translation) are noisy by construction, and short 5–20 token sentences sometimes barely leave enough surrounding context for span corruption to be a meaningful reconstruction problem.

### 7. Performance & Evaluation

Real, published results from the T5 paper (largely driven by the T5-11B checkpoint, the largest one tested): T5 reported **state-of-the-art results on the GLUE benchmark on most of its component tasks**, pushed **SuperGLUE performance up to roughly the human baseline** that the benchmark's own authors had established (a first for any model at the time SuperGLUE performance came that close to human-level on the aggregate score), achieved very strong **SQuAD** extractive-QA scores, and produced competitive **CNN/DailyMail summarization** (ROUGE) and **WMT translation** results without any task-specific architecture — the same encoder-decoder model, fine-tuned differently per task, was competitive with specialized systems across essentially the entire span of classic NLP benchmarks available at the time.

The demo model in this file reports its own training/validation loss curves on span corruption and classification over a few hundred WikiText-2 sentences — useful for confirming the pipeline behaves correctly (loss decreasing, generation producing plausible-looking tokens), but not comparable in any way to the paper's leaderboard numbers.

### 8. Impact — Why It Mattered

T5 established **text-to-text as a genuinely universal interface for NLP**, and that idea proved to be bigger than T5 itself. Once you accept that any task can be phrased as "text in, text out," task specification becomes just another piece of text you can vary — which is a direct conceptual ancestor of the **prompting** paradigm that GPT-3 and every subsequent large language model rely on (instead of a task prefix baked into training data, you get a free-text instruction at inference time). T5's architecture and framing also directly influenced later encoder-decoder models (BART, mT5 for multilingual text-to-text, ByT5, and instruction-tuned descendants like Flan-T5), and it helped cement the now-standard idea that a single pre-trained model, adapted only through its input and output text, can replace a whole zoo of task-specific systems.

### 9. How To Explain This In An Interview

"T5 solved a problem that pre-trained models like BERT still had: even after pre-training, every downstream task needed its own output head and its own training recipe — a classifier needed a linear layer sized to its label set, extractive QA needed span-prediction heads, translation needed a different architecture entirely. T5's insight was that every one of those tasks can be phrased as text in, text out — a classification label is just a short string, so is a translation, so is a summary. That means you only need one encoder-decoder Transformer, one cross-entropy loss over output tokens, and one training procedure for everything; the only thing that changes per task is a short prefix in the input, like `sentiment:` or `translate English to French:`. T5 is pre-trained with span corruption: it masks out contiguous spans of the input, replaces each with a sentinel token, and the target is just the sentinels plus the missing spans — cheaper to train on than reconstructing a full sequence. It also replaced absolute position embeddings with a learned relative-position bias added directly into the attention scores, which generalizes better across sequence lengths. T5 was pre-trained on C4, 750GB of cleaned Common Crawl text, and released in five sizes from T5-Small at 60 million parameters up to T5-11B at 11 billion. At scale, it hit state-of-the-art or near-human performance across GLUE, SuperGLUE, SQuAD, and summarization benchmarks using the exact same architecture for every one of them. Its biggest legacy is the text-to-text framing itself — it's a direct conceptual ancestor of prompting, where you specify a task purely through text rather than through architecture."
