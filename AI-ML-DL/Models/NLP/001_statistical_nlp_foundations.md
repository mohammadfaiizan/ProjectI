# Statistical NLP Foundations — Companion Notes

Companion to `001_statistical_nlp_foundations.py`. This file's code trains N-gram language models (2-gram, 3-gram, 4-gram) on WikiText-2 and defines a TF-IDF + Naive Bayes text classifier. It also, by design of this documentation series, covers Hidden Markov Models for part-of-speech tagging as a fourth core statistical-NLP technique from the same era — even though that technique is **not** implemented anywhere in this particular code file. Each section below calls out explicitly what is and isn't backed by actual code in this repo, so you can be precise about it in an interview.

## N-gram Language Models (1980s–2000s)

### 1. What Problem It Solved
Before statistical n-grams, most language software was rule-based: hand-written grammars and lookup tables that tried to enumerate what a "valid" sentence looked like. Language doesn't work that way — it's messy, ambiguous, full of exceptions, and it changes over time. Rule-based systems broke constantly because no one can write enough rules to cover real language. N-gram models solved this by giving up on "correct grammar" entirely and instead asking a much simpler, answerable question: given the last few words, what word is most likely to come next? That's a question you can answer just by counting how often word sequences appear in a large body of text. This shift — from hand-coded rules to counting probabilities from data — is really the beginning of statistical NLP.

### 2. Architecture — How It Works
Fundamentally, an n-gram model says: the probability of the next word depends only on the previous (n-1) words, not the entire sentence history. This simplifying assumption is called the **Markov assumption**. For a trigram (n=3) model, `P(word | w_{i-2}, w_{i-1})` is estimated as:

```
P(word | context) = count(context, word) / count(context)
```

Concretely, if the phrase "the cat sat" appears 40 times in the training text and "the cat sat down" appears 10 times, then `P(down | the cat) = 10/40 = 0.25`.

The code in this repo (`NgramLanguageModel`) builds this by sliding a window of size `n` across the token stream. It pads the start of the corpus with `(n-1)` `<START>` tokens and adds one `<END>` token, so the model can also learn what starts and ends a sequence. For every window, it splits the n-gram into "context" (the first n-1 words) and "word" (the last word), and increments a counter: `ngram_counts[context][word] += 1` and `context_counts[context] += 1`.

The raw counting approach has a big problem: if a context/word pair was never seen in training, its probability is exactly zero — and multiplying by zero anywhere kills the probability of an entire sentence, even if every other word was perfectly predictable. This is the classic **data sparsity** problem: language has effectively infinite possible sequences, and no training set covers them all. The fix used here is **add-one (Laplace) smoothing**: pretend every word appeared one extra time in every context.

```
P(word | context) = (count(context, word) + 1) / (count(context) + vocab_size)
```

Adding 1 to the numerator and `vocab_size` to the denominator guarantees every probability is non-zero and the whole distribution still sums to 1. If a context was never seen in training at all, the code falls back further to a uniform distribution (`1/vocab_size`) rather than the smoothing formula — a slightly different fallback than pure Laplace smoothing would give, but its purpose is the same: never let probability go to zero.

Once you have `P(word|context)`, generating text is straightforward: start with a seed context, look up the words that followed it in training along with their counts, sample one proportional to those counts, slide the context window forward by one word, and repeat. (Note: the code's `generate_text` samples proportionally to raw counts, not to the smoothed probability formula — smoothing is only used for perplexity scoring, not for generation.)

### 3. Model Size & Parameters
N-grams don't have "parameters" in the neural-network sense (no weight matrices trained by gradient descent). Instead, the model's "size" is the size of its probability table: one entry for every distinct `(context, word)` pair seen during training. A bigram model over a vocabulary of size V could in theory need up to `V^2` entries; a trigram up to `V^3`. In practice the table is sparse — you only store combinations that actually occurred — but it still grows fast as `n` increases, which is why classic industrial n-gram models (e.g. Google's web-scale n-gram models) needed compression and pruning to fit in memory.

In this repo's code, the "model size" reported is `len(model.ngram_counts)` — the number of distinct **contexts** observed, not the total count of `(context, word)` pairs (each context maps to a `Counter` that may hold several possible next words, so the true table is somewhat larger than this number suggests). The code trains 2-gram, 3-gram, and 4-gram models on the same WikiText-2 token stream, and the vocabulary size is derived directly from the data (`self.vocab = set(padded_tokens)`) rather than fixed by a hyperparameter — it's whatever the WikiText-2 training split contains. The point of testing multiple `n` values side by side is to make the sparsity trade-off visible: higher `n` gives the model more context to condition on (better predictions when it has seen the exact phrase before) but the table balloons and coverage drops (more phrases it has *never* seen before).

### 4. Dataset & What It Was Trained On
Classic statistical n-gram models (e.g. IBM's early speech-recognition language models, or Google's web-scale n-gram models from the 2000s) were trained on enormous corpora — hundreds of millions to trillions of words scraped from the web, news wire, or transcribed speech — specifically because n-grams need huge amounts of data to fill in their sparse tables.

This repo's code trains on **WikiText-2**, a modestly sized corpus (~2 million training tokens) built from verified "Good" and "Featured" Wikipedia articles, loaded via Hugging Face's `datasets` library (`load_dataset('wikitext', 'wikitext-2-v1')`). The text is lowercased, newlines are stripped, and it's tokenized with NLTK's `word_tokenize`. WikiText-2 is a reasonable stand-in for a learning exercise: it's clean, freely available, small enough to process on a laptop in seconds, and — crucially for this file's teaching goal — small enough that you can actually *see* the sparsity problem happen (the code deliberately evaluates perplexity on a subset of only 1,000 test tokens and 500 validation tokens to keep things fast). A production-grade n-gram model would use orders of magnitude more text.

### 5. Training Process
There's no gradient descent here — "training" an n-gram model just means counting. The code makes one pass over the (padded) training tokens, and for every window of `n` consecutive tokens, increments the corresponding context/word counter. That's it: the entire "optimization" is frequency counting, which is why n-gram models train almost instantly compared to neural networks, even on fairly large corpora.

Historically, this is also how n-gram models were trained in production systems, though industrial versions add extra steps this toy version skips: pruning rare n-grams to save memory, and using more sophisticated smoothing than add-one (see below). The evaluation loop in the code (`evaluate_statistical_models`) trains three separate models — 2-gram, 3-gram, 4-gram — each timed and memory-profiled with `psutil`, so you can directly compare how model size and training cost scale with `n`.

### 6. Training Challenges
The dominant challenge is **data sparsity**: as `n` grows, the number of distinct contexts explodes, and most of them are seen only once or never at all in training (sometimes called the "curse of dimensionality" for discrete sequences — every additional word of context multiplies the number of possible histories). A raw maximum-likelihood estimate (counts divided by counts) assigns zero probability to anything unseen, which is catastrophic for a probability model.

The classic fix — and the one implemented here — is **smoothing**: redistributing a small amount of probability mass from things you've seen onto things you haven't. Add-one (Laplace) smoothing, used in this code, is the simplest version and is known to be too aggressive (it steals too much probability from frequent events and gives too much to rare ones). More advanced historical techniques not implemented here include **Good-Turing discounting**, **Katz backoff**, and **Kneser-Ney smoothing** (generally considered the strongest classical smoothing method), which handle the frequent-vs-rare tradeoff much better. Another practical challenge is memory: storing every observed n-gram context can require gigabytes of RAM at web scale, which is why real systems prune low-count entries.

### 7. Performance & Evaluation
N-gram models are evaluated with **perplexity**, a measure of how "surprised" the model is by held-out text it wasn't trained on. Perplexity is `exp(-average log probability per token)`; lower is better, and a perplexity of `k` roughly means the model is as uncertain as if it had to guess uniformly among `k` equally likely words at each step. The code computes this directly: sum the log-probability the model assigns to every token in the test set, average it, negate it, and exponentiate.

Historically, well-smoothed n-gram models (Kneser-Ney trigrams/4-grams trained on large corpora) achieved perplexities in the double digits to low hundreds on standard benchmarks, and were the backbone of speech recognition and machine translation systems throughout the 1990s and 2000s. In this repo, with a small dataset and simple add-one smoothing, expect perplexity numbers that are considerably higher (worse) than a production Kneser-Ney model would achieve — that gap is itself an instructive result, showing why smoothing quality matters.

### 8. Impact — Why It Mattered
N-gram models established the core idea that still underlies every language model today: turn "predict the next word" into a probability distribution learned from data, and evaluate models by how well they predict held-out text (perplexity). They powered speech recognition, machine translation, and autocomplete for decades. But their fundamental ceiling — a fixed, small context window and no notion of word *meaning* (to an n-gram model, "cat" and "dog" are just two unrelated symbols, even though they behave similarly in language) — is exactly the gap that motivated neural language models: first feedforward neural LMs (Bengio et al. 2003, covered in `003_early_neural_language_models.md`), and eventually embeddings, RNNs, and transformers, all of which learn continuous representations that can generalize between similar words instead of just counting exact matches.

### 9. How To Explain This In An Interview
"N-gram models are the earliest practical language models: they assume the next word only depends on the previous n-1 words, and they estimate that probability by literally counting how often word sequences occur in a training corpus. I implemented 2-gram through 4-gram models and trained them by making a single pass over WikiText-2, counting `(context, word)` occurrences. The core challenge is data sparsity — most possible phrases never appear in training, so naive counting gives many sequences zero probability. I used Laplace smoothing to guarantee every sequence gets a non-zero probability by adding one virtual count to every possible outcome. I evaluated the models with perplexity, which measures how well the model predicts unseen text, and compared how perplexity, memory, and training time changed as I increased the context size from bigrams to 4-grams — bigger context helps prediction quality but makes the sparsity problem worse. This experiment makes concrete why the field eventually moved to neural language models: they replace this brittle counting table with dense, generalizable representations."

## Hidden Markov Model for Part-of-Speech Tagging (1980s)

### 1. What Problem It Solved
N-gram language models predict the next *word*. But many NLP tasks need to predict a *label* for each word in a sequence — for example, tagging every word in a sentence with its part of speech (noun, verb, adjective, etc.). Early rule-based POS taggers used large hand-written rule sets ("if the word ends in -ing and follows 'is', tag it VERB") which were brittle and never covered every case, especially for ambiguous words (e.g., "book" can be a noun or a verb depending on context). Hidden Markov Models solved this by treating POS tagging as a probabilistic sequence-labeling problem: figure out the most likely *sequence* of hidden tags that explains an *observed* sequence of words, using probabilities learned from a tagged corpus instead of hand-written rules.

### 2. Architecture — How It Works
The core idea: there's a hidden sequence you can't directly observe (the true part-of-speech tags) and an observed sequence you can see (the actual words). An HMM models this with two probability tables:
- **Transition probabilities**: `P(tag_i | tag_{i-1})` — how likely is a given tag to follow another tag (e.g., a determiner like "the" is very often followed by a noun or adjective).
- **Emission probabilities**: `P(word_i | tag_i)` — how likely is a given word to be generated by a given tag (e.g., "run" is more often a VERB than a NOUN).

A toy example: suppose transition `P(NOUN | DET) = 0.7` and emission `P(dog | NOUN) = 0.05`. For the two-word sequence "the dog", the model computes the joint probability of the tag sequence (DET, NOUN) generating ("the", "dog") by chaining these transition and emission probabilities together: `P(DET | <START>) * P(the | DET) * P(NOUN | DET) * P(dog | NOUN)`.

Since there are exponentially many possible tag sequences for a sentence, you can't just try all of them. The **Viterbi algorithm** solves this efficiently with dynamic programming: it works through the sentence one word at a time, and for each possible tag at each position, keeps only the *best* path that could have led there (discarding all other, provably worse, paths). This reduces what would be an exponential search to something proportional to `(number of tags)^2 * sentence length`.

### 3. Model Size & Parameters
An HMM's "size" is the size of its two probability tables: a `T x T` transition matrix (T = number of tags, typically ~12-45 depending on the tagset) and a `T x V` emission matrix (V = vocabulary size). For a 45-tag Penn Treebank tagset over a 50,000-word vocabulary, that's roughly `45*45 + 45*50,000 ≈ 2.25 million` probability entries — still tiny compared to a neural network, but larger than a bigram language model's tag-only table because of the emission matrix's dependence on vocabulary size.

**Important note on this repo's code**: `001_statistical_nlp_foundations.py` does not actually implement an HMM or POS tagger — there is no HMM class in the file at all. It's covered here because it's one of the four core statistical-NLP techniques from this same era (alongside n-grams, TF-IDF, and Naive Bayes), and it's a very common interview topic to pair with n-grams since both are "count probabilities from a corpus" techniques. If you were to add it to this codebase, a toy version would reuse the same WikiText-2 vocabulary and a small standard tagset (e.g., the 12-tag "universal" POS tagset), giving transition/emission tables on the order of tens of thousands of entries — small enough to train and query instantly, just like the n-gram model here.

### 4. Dataset & What It Was Trained On
Classic HMM POS taggers (e.g. the TnT tagger, Brants 2000) were trained on manually POS-annotated corpora — most famously the **Penn Treebank**, where linguists hand-labeled every word in roughly 1 million words of Wall Street Journal text with one of about 45 part-of-speech tags. This kind of labeled data is exactly what an HMM needs, because its transition and emission tables are estimated directly from tag/word co-occurrence counts, the same way n-gram counts are estimated from word co-occurrence.

WikiText-2 (the dataset the rest of this file uses) has **no POS tag annotations** — it's just raw article text — so it cannot be used as-is to train a supervised HMM tagger. To do POS tagging on WikiText-2 you'd either need to run an existing tagger over it first to create "silver" labels, or train unsupervised with the Baum-Welch algorithm (an EM-based method that estimates the hidden tag probabilities without any labeled data, at the cost of being much less accurate than a supervised model).

### 5. Training Process
For a **supervised** HMM (the historically common case, given labeled data like the Penn Treebank), training is just counting, exactly like n-grams: count how often each tag follows each other tag to get transition probabilities, and count how often each word appears under each tag to get emission probabilities, then normalize. Smoothing (add-one, Good-Turing, etc.) is applied the same way as for n-grams, since the same sparsity issue applies — many word/tag combinations are rare or unseen.

For **unsupervised** training (no labeled tags available), the **Baum-Welch algorithm** — a special case of the EM (Expectation-Maximization) algorithm — is used instead: it alternates between estimating the probability of each hidden tag sequence given the current parameters (E-step) and re-estimating the transition/emission tables to maximize the likelihood of the observed words given those estimated tag distributions (M-step), repeating until convergence.

### 6. Training Challenges
The same **data sparsity** problem from n-grams shows up here: many word/tag pairs are rare, especially for uncommon words, so smoothing is essential. A specific extra challenge for HMMs is handling **unknown words** at test time — words never seen during training have no emission probabilities at all under any tag, so taggers typically fall back on word-shape features (suffixes like "-ing", "-ed", capitalization) to guess a plausible tag. Computationally, exhaustively scoring every possible tag sequence is exponential in sentence length, which is why the Viterbi algorithm's dynamic-programming trick (only track the best-scoring path to each state at each time step) is essential — without it, tagging even a short sentence would be computationally infeasible.

### 7. Performance & Evaluation
HMM POS taggers are evaluated by **tagging accuracy**: the percentage of words assigned the correct tag compared to human-annotated ground truth. Supervised HMM taggers trained on the Penn Treebank historically reached roughly **95-96% per-word accuracy** (the TnT tagger reported ~96.7%), which was considered close to human-level agreement for this task at the time. Unsupervised (Baum-Welch) HMM taggers, without labeled training data, perform noticeably worse, since there's no ground truth to anchor which hidden state corresponds to which linguistic tag.

### 8. Impact — Why It Mattered
HMMs established the general framework of **probabilistic sequence labeling**: represent a sequence problem as hidden states plus observations, and use dynamic programming to find the best hidden sequence. This framework extended well beyond POS tagging to named entity recognition, speech recognition (where "hidden states" are phonemes and "observations" are audio features), and gene sequence analysis in bioinformatics. Its main limitation — the Markov assumption that a tag only depends on the previous tag (not richer context or overlapping features) — motivated **Conditional Random Fields (CRFs)**, which relaxed this restriction by allowing arbitrary features of the whole sequence. Later, this same "sequence labeling" idea was picked up by neural sequence models (BiLSTM-CRF, and eventually transformer-based taggers), which replaced hand-built emission/transition tables with learned representations.

### 9. How To Explain This In An Interview
"Hidden Markov Models frame part-of-speech tagging as inferring a hidden sequence — the true tags — from an observed sequence — the words — using two probability tables: transition probabilities between tags, and emission probabilities of words given a tag. Both tables are estimated by counting from a tagged corpus like the Penn Treebank, the same counting philosophy as n-gram language models. Because trying every possible tag sequence is exponential, you use the Viterbi algorithm, a dynamic-programming method that finds the single best tag sequence in time proportional to the square of the tag set size times the sentence length. The main challenges are the same sparsity problems n-grams face, solved with smoothing, plus handling words never seen in training, usually solved with word-shape heuristics. Classic supervised HMM taggers reached about 95-96% accuracy on Penn Treebank. HMMs matter because they established the general pattern of sequence labeling with dynamic-programming decoding, which later evolved into CRFs and then neural sequence taggers."

## Naive Bayes Text Classification (1960s theory / 1998 practical adoption)

### 1. What Problem It Solved
Before statistical classifiers, categorizing text (spam vs. not-spam, positive vs. negative review, topic A vs. topic B) required hand-written keyword rules ("if the email contains 'viagra', mark as spam"). This approach doesn't scale and is trivially gamed — spammers just avoid the exact flagged words. Naive Bayes solved this by treating classification as a probability problem: given the words that appear in a document, what's the most probable category, based on patterns learned from a training set of already-labeled examples? It replaced brittle keyword rules with a statistical model that automatically learns which words are associated with which categories, and how strongly.

### 2. Architecture — How It Works
Naive Bayes is built directly on **Bayes' theorem**: `P(class | document) ∝ P(document | class) * P(class)`. The "naive" part is a simplifying assumption: it treats every word in the document as independent of every other word, given the class. That's not literally true (words in real sentences are correlated), but it makes the math tractable and, surprisingly, still works well in practice for text classification.

Under this independence assumption, `P(document | class)` becomes just the product of the probability of each individual word appearing, given that class: `P(w_1|class) * P(w_2|class) * ... * P(w_n|class)`. Combined with the class prior `P(class)` (how common that class is overall) and normalizing, you get a probability for each candidate class, and you pick the highest one.

Concretely, if you're classifying "short vs. long" sentences (the toy task used in this repo's code — more on that below), and the word "furthermore" appears far more often in long sentences in training data than short ones, the model will learn a higher `P(furthermore | long)` than `P(furthermore | short)`, and any test sentence containing "furthermore" gets pulled toward the "long" prediction, combined with evidence from every other word in the sentence.

In this repo, Naive Bayes is used via scikit-learn's `MultinomialNB`, which is specifically designed for count-based / TF-IDF-weighted features (as opposed to `BernoulliNB`, which only looks at presence/absence of words) — a good fit since it's being fed TF-IDF vectors (see the TF-IDF section below) rather than raw word counts.

### 3. Model Size & Parameters
Naive Bayes doesn't have "parameters" in the deep-learning sense either, but it does store a compact set of statistics: one probability per (word, class) pair, plus one prior probability per class. For a vocabulary of size V and C classes, that's `V * C` conditional probabilities plus `C` priors — tiny compared to almost any neural model, and fast to estimate because, like n-grams and HMMs, "training" is just counting word frequencies per class and normalizing.

In this repo's code, `TraditionalNLPClassifier` pairs `MultinomialNB` (scikit-learn's default settings) with a TF-IDF vectorizer capped at `max_features=5000` — meaning the model only ever has 5,000 possible word features, times 2 classes (long vs. short sentence, as described below), so the entire parameter table has at most `5,000 * 2 = 10,000` conditional-probability entries. That's the "educational scale-down": a real production text classifier might use a much larger vocabulary, but the mechanism is identical.

**Note on how this is actually used in the code**: `TraditionalNLPClassifier` is fully implemented (`prepare_classification_data`, `train`, `evaluate` methods), but it is never called from `main()` in this file — `main()` only runs and evaluates the n-gram models. The classifier class is there to demonstrate the technique and is meant to be exercised separately if you want to see it run end-to-end.

### 4. Dataset & What It Was Trained On
Naive Bayes became famous historically for **spam filtering** (its use in this domain dates to the late 1990s) and was a standard baseline for **sentiment analysis** and **topic classification** benchmarks like 20 Newsgroups throughout the 2000s, typically trained on thousands to hundreds of thousands of labeled documents.

This repo's code doesn't have a natural classification label available from WikiText-2 (it's just article text, not labeled by topic or sentiment), so `prepare_classification_data` manufactures a **synthetic binary task**: label a text sample "1" if it tokenizes to more than 10 words, and "0" otherwise (i.e., "long sentence" vs. "short sentence" classification), using the first 1,000 raw text entries from the WikiText-2 training split. This is a deliberately easy, synthetic stand-in task — its purpose is purely to demonstrate the TF-IDF + Naive Bayes *mechanism* clearly, not to represent a realistic classification problem. In a real setting you'd swap in an actual labeled dataset (e.g., IMDB sentiment, AG News topics) with the identical `vectorizer.fit_transform` → `classifier.fit` pipeline.

### 5. Training Process
Training a Naive Bayes classifier means estimating `P(word | class)` and `P(class)` from labeled training data by counting. In this repo, that happens inside scikit-learn: `self.vectorizer.fit_transform(X_train)` first converts each raw text into a TF-IDF vector, and then `self.classifier.fit(X_train_tfidf, y_train)` estimates the per-class word-probability tables from those vectors. There's no gradient descent, no learning rate, no epochs — the entire "training loop" is a single pass to compute frequency-based statistics, plus a smoothing correction (scikit-learn's `MultinomialNB` applies a small Laplace-style smoothing constant, `alpha=1.0` by default, for exactly the same "never let a probability be zero" reason n-grams need smoothing).

### 6. Training Challenges
The main challenge is the same sparsity issue seen throughout this file: a word that never appeared in training for a given class would get `P(word|class) = 0` without smoothing, and multiplying by zero would wipe out the probability of the entire document regardless of other evidence — so Laplace-style smoothing is applied here too (scikit-learn does this automatically via the `alpha` parameter). A separate, well-known weakness of Naive Bayes is the **independence assumption** itself: because it treats every word as independent given the class, it can't capture that certain word *combinations* carry more signal than either word alone (e.g., "not good" vs. "good"), which is a real accuracy ceiling compared to models that can capture word interactions.

### 7. Performance & Evaluation
Naive Bayes classifiers are evaluated with standard classification metrics: **accuracy**, precision, recall, and F1 score (the code imports `accuracy_score` and `classification_report` from scikit-learn for exactly this). Historically, Naive Bayes achieved surprisingly strong results for its simplicity — often 80-90%+ accuracy on tasks like spam detection and topic classification — and it remained a hard-to-beat, fast baseline well into the era when more complex models (SVMs, then neural classifiers) started to overtake it on harder tasks. For the synthetic "long vs. short sentence" task used in this file's code, expect very high accuracy, since sentence length is a strong, almost giveaway signal that specific words (like connective words such as "however" or "furthermore") correlate with.

### 8. Impact — Why It Mattered
Naive Bayes proved that a simple, statistically-grounded model with a "wrong" simplifying assumption (word independence) could still be extremely effective and fast, and it became the default first thing to try for text classification for over a decade — it's cheap to train, needs relatively little data, and is easy to interpret (you can literally read off which words most increase or decrease the probability of a class). It also cemented the pattern of "vectorize the text, then apply a standard classifier" that persists today, just with the vectorization step now handled by learned embeddings instead of TF-IDF, and the classifier now often a neural network instead of Naive Bayes.

### 9. How To Explain This In An Interview
"Naive Bayes classifies text by applying Bayes' theorem and assuming every word is conditionally independent given the class — which isn't literally true, but makes the math tractable and works well in practice. I trained it on TF-IDF vectors using scikit-learn's `MultinomialNB`, which is designed for count-like features. Training is just counting word frequencies per class and applying Laplace smoothing so that words unseen in a given class during training don't collapse the whole document's probability to zero. In this repo, I used a synthetic long-vs-short-sentence task built from WikiText-2, since the dataset has no natural labels, specifically to demonstrate the TF-IDF-to-Naive-Bayes pipeline end to end. I'd evaluate it with accuracy and F1. Naive Bayes matters historically because it was the fast, cheap, surprisingly strong baseline for text classification for over a decade, and it established the general vectorize-then-classify pattern that's still used today, just with different vectorizers and classifiers."

## TF-IDF (Term Frequency-Inverse Document Frequency) (1972 concept / 1988 formalization)

### 1. What Problem It Solved
Simply counting how often a word appears in a document (raw term frequency) is a weak signal, because the most frequent words in almost any document are common words like "the", "is", "and" — words that appear everywhere and tell you nothing about what makes *this* document distinctive. Even after removing an explicit stopword list, plenty of moderately-common words still show up in nearly every document and dilute the signal. TF-IDF solved this by re-weighting word counts to emphasize words that are frequent *in this specific document* but rare *across the whole collection of documents* — which are exactly the words that actually characterize what a document is about.

### 2. Architecture — How It Works
TF-IDF combines two numbers for every (word, document) pair:
- **Term Frequency (TF)**: how often the word appears in this document (sometimes normalized by document length).
- **Inverse Document Frequency (IDF)**: a measure of how rare the word is across all documents, typically `log(total_documents / documents_containing_word)`.

The final score is `TF * IDF`. A word gets a high TF-IDF score if it's common in this document AND uncommon elsewhere.

A tiny worked example: suppose the word "wikipedia" appears 3 times in a 100-word document (TF = 3), and it appears in only 10 out of 10,000 documents in the whole collection. IDF = `log(10,000/10) = log(1000) ≈ 6.9`. So its TF-IDF score is roughly `3 * 6.9 ≈ 20.7` — a high score, because it's both present and distinctive. Compare that to "the", which might appear 8 times in the same document (higher TF) but shows up in essentially all 10,000 documents, giving IDF = `log(10,000/9,999) ≈ 0.0001` — an almost-zero score despite the higher raw count, because it carries almost no distinguishing information.

In this repo, TF-IDF isn't hand-implemented — it uses scikit-learn's `TfidfVectorizer(max_features=5000, stop_words='english')`. This vectorizer builds a vocabulary of (up to) the 5,000 most informative words after removing a built-in English stopword list, computes TF-IDF scores for every word in every document, and returns each document as a sparse vector of these scores — the exact input format `MultinomialNB` expects.

### 3. Model Size & Parameters
TF-IDF is not a trained/learned model at all — it's a deterministic statistical transformation, so there's no notion of "parameters" being optimized. Its "size" is simply the size of the vocabulary it tracks: one IDF value per word in the vocabulary, computed once from document-frequency statistics across the whole corpus. In this repo, that's capped at `max_features=5000`, meaning the vectorizer only keeps track of the 5,000 highest-scoring words (by term frequency across the corpus) and ignores everything else — a practical cap to keep the resulting feature vectors small and fast, chosen for the toy classification demo rather than any theoretical requirement (production TF-IDF systems can use vocabularies of hundreds of thousands of words).

### 4. Dataset & What It Was Trained On
TF-IDF itself doesn't need "training" the way a model does — you just need a large enough collection of documents to compute meaningful document-frequency statistics for the IDF part. Historically it was developed for information retrieval, used in search engines to score how relevant a document is to a query (Salton & Buckley's foundational work on term weighting dates to the late 1980s, building on Karen Spärck Jones's 1972 IDF concept), and was computed over whatever document collection was being indexed — anywhere from a few thousand documents to an entire web index.

In this repo, the "documents" fed into `TfidfVectorizer` are the first 1,000 raw text entries from WikiText-2's training split (the same ones used for the Naive Bayes classification demo). WikiText-2 works fine here because TF-IDF just needs enough documents for the "rare across the collection" half of the calculation to be meaningful — a thousand short article excerpts is plenty to compute reasonable document-frequency statistics for teaching purposes, even though real search/classification systems would use much larger collections.

### 5. Training Process
There's no optimization loop, loss function, optimizer, or epochs — that's the key thing to understand about TF-IDF. `vectorizer.fit_transform(X_train)` does two things in one call: "fit" scans the training documents once to compute vocabulary and document-frequency (and therefore IDF) statistics, and "transform" then converts each document into its TF-IDF vector using those statistics. It's a single deterministic pass over the data, not an iterative training process. At test/inference time you should only ever call `transform` (not `fit_transform`) using statistics learned from the training set — refitting on test data would leak information about the test set's word distribution, which the code correctly avoids by calling `self.vectorizer.transform(X_test)` in the `evaluate` method.

### 6. Training Challenges
Because TF-IDF isn't trained iteratively, it doesn't have the sparsity/smoothing/vanishing-gradient challenges other models in this file face. Its practical challenges are more about representation choices: how big to make the vocabulary (`max_features` — too small loses information, too large makes vectors huge and mostly zero), which stopwords to remove, whether to use raw counts vs. binary presence, and whether to apply extra normalization (e.g., L2-normalizing each document vector, which scikit-learn does by default) so that document length doesn't unfairly bias scores. There's also an inherent representational limit: TF-IDF treats every word as a completely separate, meaningless symbol — "good" and "great" get entirely unrelated columns in the vector, with zero notion that they're semantically similar. That blind spot is exactly what dense word embeddings (Word2Vec, GloVe — covered in `002_word_embeddings_evolution.md`) were built to fix.

### 7. Performance & Evaluation
TF-IDF itself isn't evaluated directly (it's a feature representation, not a predictive model) — you evaluate the *downstream* task it's feeding, whether that's search relevance ranking (using metrics like precision@k or NDCG) or, as in this repo, text classification accuracy when paired with Naive Bayes. Historically, TF-IDF-based retrieval was the dominant approach in search engines for decades before neural/embedding-based retrieval took over, and TF-IDF plus a simple classifier remains a genuinely strong, fast baseline for text classification even today.

### 8. Impact — Why It Mattered
TF-IDF gave the field a principled, purely statistical way to decide which words in a document actually matter, without any hand-crafted rules — and it required no labeled data at all, since it's computed from raw document statistics. It became the default text representation for search engines and text classification for roughly three decades, and it's still a reasonable first baseline to try today. Its core weakness — no notion of word meaning or similarity, and no way to represent word order — is precisely the gap that motivated dense, learned word embeddings, which represent words as vectors that capture semantic similarity instead of just frequency statistics.

### 9. How To Explain This In An Interview
"TF-IDF re-weights raw word counts so that words which are frequent in a specific document but rare across the whole document collection score highest — those are the words that actually characterize a document, unlike common words like 'the' that appear everywhere and carry no signal. It's computed as term frequency times inverse document frequency, where IDF is the log of total documents divided by documents containing that word. There's no training loop involved — it's a deterministic statistical transform computed in a single pass over the corpus, using scikit-learn's `TfidfVectorizer` in my case. I used it to convert raw WikiText-2 text into feature vectors, then fed those into a Naive Bayes classifier. Its biggest limitation is that it treats every word as an unrelated symbol with no notion of meaning or similarity, which is exactly the gap that motivated dense word embeddings like Word2Vec afterward."
