# Model Architecture Decisions at Pretraining Time

Architecture decisions made before a training run starts are the highest-leverage, least-reversible commitments in the entire pretraining process; this file is about how to make them as a constraint-satisfaction exercise rather than a search for a theoretically optimal mechanism.

## 0. Scope and framing

This file is deliberately not a re-derivation of attention math or MoE routing mechanics — those are worked through in full, per model, in `..\..\OpenSource\`, `..\..\GPT\`, `..\..\Claude\`, and `..\..\Gemini\` (in particular: MLA and DeepSeekMoE routing in `..\..\OpenSource\006_DeepSeek_V2.md` and `..\..\OpenSource\007_DeepSeek_V3.md`; GQA in `..\..\OpenSource\003_Llama3.md` and `..\..\OpenSource\004_Mistral7B.md`; sliding-window attention in `..\..\OpenSource\004_Mistral7B.md`; MoE routing/expert-parallelism tradeoffs in `..\..\OpenSource\005_Mixtral8x7B.md`; blank-infilling's prefix-LM attention pattern in `..\..\OpenSource\010_GLM4.md`). Read those for "how does the mechanism work." This file is about a different question, the one a staff research engineer is actually expected to answer in an interview or in a real design review: **given a set of real constraints, how does a lab decide which mechanism to commit to for the next multi-million-dollar training run** — and just as importantly, how does it decide *when a mechanism that is theoretically superior is nonetheless the wrong choice for this specific run*.

The unifying idea across every decision below: architecture choices made at pretraining time are irreversible for the lifetime of that model family (you cannot retrofit MLA onto a model pretrained with MHA without essentially retraining; you cannot cheaply give a model a longer *native* context without a dedicated extension stage — see `005_Curriculum_And_Multi_Stage_Pretraining.md`), and they are made under uncertainty about a moving target (competitor capability, hardware availability, product requirements at the time the model will actually ship, often 6–18 months after the decision is locked). This is a decision under constraint and irreversibility, not a search for the theoretically optimal point in an unconstrained design space — the framing an interviewer is checking for.

## 1. Dense vs. MoE

### 1.1 What the decision actually trades off

A dense model activates every parameter for every token; an MoE model activates a small routed subset (plus, in most modern designs, one or more always-on shared experts — see `..\..\OpenSource\007_DeepSeek_V3.md` Section 2). The naive framing — "MoE gives you more total capacity for the same inference-time compute, so it's strictly better" — is real but incomplete, and a staff-level answer has to name what MoE costs you in exchange, because those costs are exactly what determines whether a given lab, at a given point in its infrastructure maturity, should commit to it.

**What MoE buys you:**
- More total parameters (more "knowledge capacity") for the same per-token activated compute, which is the same as saying: for a fixed *inference* compute budget, MoE reaches a lower loss than a dense model constrained to the same activated-parameter count, because the routed experts let different tokens draw on different subsets of a much larger total parameter pool.
- For a fixed *training* compute budget \(C = 6ND\), if \(N\) is taken as activated parameters, an MoE model can be trained with much larger total parameter count \(N_{\text{total}} \gg N_{\text{active}}\) at the same nominal training FLOPs as a dense model of size \(N_{\text{active}}\) — though this is a simplification; MoE training also incurs router/load-balancing overhead and communication cost not captured by the dense \(6ND\) approximation (see `002_Scaling_Laws_And_Compute_Optimal_Training.md`, Section 3.3's caveat about substituting activated params for \(N\)).

**What MoE costs you, and each cost is a real engineering line item, not a footnote:**
- **Routing/load-balancing complexity.** Every generation of MoE has had to solve some version of "how do you prevent a small number of experts from being massively overloaded while others starve," and the mechanisms for solving this have themselves evolved nontrivially — from Switch-Transformer-style auxiliary balancing losses (which structurally compete with the LM loss's gradient, a real quality/balance tension) to DeepSeek-V3's auxiliary-loss-free, bias-based control-loop mechanism (`..\..\OpenSource\007_DeepSeek_V3.md`, Section 2). A lab committing to MoE for the first time is committing to owning and iterating on this subsystem, not just flipping an architecture flag.
- **Expert-parallel communication cost.** Routed tokens must be dispatched (all-to-all) to whichever devices host their selected experts and the outputs combined back — a communication pattern with no dense-model analogue, whose volume scales with token count × top-k (largely independent of *total* expert count, a subtlety worth stating precisely: going from 160 to 256 routed experts, as DeepSeek-V2 to V3, does not proportionally increase all-to-all volume, because top-k stayed roughly fixed). This makes interconnect bandwidth and topology a first-order constraint on whether MoE training is even *feasible* at a given cluster's network design, not just a matter of "buy more GPUs" — DeepSeek's custom cross-node all-to-all kernels and DualPipe schedule (`..\..\OpenSource\007_DeepSeek_V3.md`, Section 4) exist specifically because H800's reduced NVLink bandwidth made naive all-to-all communication a bottleneck.
- **Serving complexity mirrors training complexity.** The same all-to-all dispatch/combine machinery required for training is required for serving, except now latency-sensitive rather than throughput-sensitive — a lab whose serving infrastructure is built around straightforward tensor/pipeline-parallel dense-model serving has real work to do to serve an MoE model well at low latency and high concurrency.
- **Training-infrastructure maturity risk.** MoE training is empirically more prone to instability modes dense training doesn't have (router collapse, expert under-utilization, load imbalance causing effective throughput collapse under expert parallelism) — a lab with a mature MoE training stack (DeepSeek, by V3; Mistral, from Mixtral onward) can treat these as known, tractable engineering problems; a lab attempting MoE at frontier scale for the first time is taking on real execution risk on top of the scientific bet.

### 1.2 The actual decision process

A staff-level answer frames this as a function of **where the constraint actually binds**, not as a single global judgment of "MoE is good" or "MoE is bad":

- If the binding constraint is **inference cost/latency at a fixed quality bar, and the lab already has (or is willing to build) mature expert-parallel training and serving infrastructure**, MoE is the right default — this is DeepSeek's explicit bet across V2 and V3, and Mistral's bet with Mixtral.
- If the binding constraint is **training-infrastructure risk tolerance and time-to-ship** — a lab without an existing MoE training stack, under time pressure to ship a competitive model, and without headroom to debug a new class of instability — a dense model is the lower-execution-risk choice even if it is not the theoretically compute-efficient one, precisely because dense training/serving is a well-understood, extensively de-risked recipe across the entire field. This is a large part of why Llama's dense-model bet (through Llama 3/3.1, per `..\..\OpenSource\003_Llama3.md`) persisted as long as it did even as MoE's efficiency case became well-established elsewhere — dense training and serving infrastructure was Meta's existing organizational strength, and the inference-cost argument was instead met with the overtraining strategy covered in `002_Scaling_Laws_And_Compute_Optimal_Training.md`, Section 6, which is a *different* lever for the same underlying inference-cost problem that doesn't require adopting MoE at all.
- If the binding constraint is **serving diverse deployment tiers** (a single dense checkpoint has one fixed inference-cost point; an MoE model's activated-parameter count is itself sometimes a design knob, e.g., choosing top-k, though changing top-k post-training is not generally free), the calculus shifts again based on whether the product needs one well-understood cost point or flexibility.

### 1.3 A second-order decision inside "yes, MoE": granularity, expert count, and top-k

Committing to MoE is not a single binary decision — it opens a second layer of decisions that themselves have real tradeoffs, and a staff-level answer should be able to go one level deeper than "dense vs. MoE" when pressed. The two headline knobs are **granularity** (how many total experts, and correspondingly how narrow each one is) and **top-k** (how many experts are activated per token).

- **Coarse-grained MoE (few, wide experts, e.g., 8-16 total, top-1 or top-2)** is the earlier, simpler convention (Switch Transformer, and the original Mixtral 8x7B design at 8 experts / top-2 — `..\..\OpenSource\005_Mixtral8x7B.md`). It is comparatively easy to reason about, has a smaller all-to-all communication *surface* to engineer around (fewer possible destinations per token), and imposes a smaller router-design burden, but it gives each expert a coarser specialization and reaches a lower quality ceiling for a given total parameter budget than a more fine-grained design.
- **Fine-grained MoE (hundreds of narrow experts, small top-k relative to total, plus one or more always-on shared experts)** is the more recent convention DeepSeek pushed furthest (160 routed + 2 shared experts at V2, top-6; 256 routed + 1 shared at V3, top-8 — `..\..\OpenSource\006_DeepSeek_V2.md`, `..\..\OpenSource\007_DeepSeek_V3.md`). The claimed benefit is sharper per-token specialization (an enormous combinatorial routing space, e.g., roughly \(\binom{256}{8}\) combinations for V3, before even counting the shared expert) for the same activated-parameter count; the claimed cost is a harder load-balancing problem (more experts to keep uniformly utilized) and more router-design iteration to get right, which is precisely why DeepSeek's own load-balancing mechanism evolved between V2 and V3 rather than being solved once and left alone.
- **Shared experts** (always-active, alongside the routed subset) are themselves a design choice with a stated rationale: absorbing common, cross-domain computation into a fixed, always-on component so the routed experts specialize more cleanly on token-specific structure rather than each having to re-learn generic patterns independently. Whether to include them, and how many, is not free — each shared expert adds to the activated-parameter (and therefore per-token inference FLOPs) count unconditionally, unlike routed experts.
- **Top-k** directly sets the expert-parallel all-to-all communication volume (Section 1.1's point that volume scales with token count × top-k, not total expert count) — increasing top-k for quality reasons has a direct, quantifiable serving- and training-communication cost, and is exactly the kind of tradeoff that should be sized numerically (expected communication volume at target cluster topology) rather than picked by intuition or by copying a competitor's published configuration outright.

The practical decision-making implication: a lab's *first* MoE model is a poor place to bet on the more aggressive, fine-grained end of this spectrum, precisely because fine-grained MoE compounds two unproven things at once (MoE feasibility at all, plus a harder load-balancing regime) rather than one — which is consistent with why DeepSeek's own fine-grained, bias-controlled-balancing design (V3) arrived only after a full generation (V2) had already validated MoE training at frontier scale with a simpler balancing approach. This is the same staged-de-risking logic developed in `006_Pretraining_Ablations_And_Research_Methodology.md`, Section 13, applied specifically to the granularity axis.

### 1.4 "Adopt a published recipe" vs. "develop your own": a build-vs-buy framing

A related, often under-discussed decision: given that DeepSeek, Mistral, and others have published architecture and training details in enough depth to be reproducible in broad strokes, should a lab building its own MoE model closely follow a published recipe (same granularity, same top-k, a similar load-balancing mechanism) or invest in developing its own variant? The case for following a published recipe closely: it inherits someone else's validated evidence at frontier scale, which is exactly the kind of scale-transfer confidence a from-scratch ablation program cannot cheaply manufacture (`006_Pretraining_Ablations_And_Research_Methodology.md`, Section 4) — reproducing a known-working configuration is lower-risk than ablating a novel one, holding everything else about your own data/infrastructure/team constant. The case against: a published recipe was tuned against a *different* lab's data mixture, scale, cluster topology, and quality bar, and "known to work well for DeepSeek at 671B on their corpus and their H800 cluster" is not the same claim as "known to work well for us at our target scale on our corpus and our cluster" — the recipe still has to be validated in your own setting, just with a stronger prior than starting from nothing. In practice, most labs land on a hybrid: adopt the well-validated, low-risk pieces of a published recipe wholesale (e.g., GQA's group size conventions, a standard warmup/cosine schedule shape) while treating the higher-risk, more novel pieces (a new load-balancing mechanism, a new attention variant) as genuinely requiring their own proxy-scale validation before being trusted, rather than either blindly copying everything or reinventing everything from first principles.

## 2. Attention variant: MHA / GQA / MLA / sliding window

### 2.1 The one-dimensional simplification to resist

It is tempting to rank these as "MHA (worst KV-cache efficiency) → GQA → MLA (best KV-cache efficiency, most novel)" and conclude every lab should be racing toward MLA. That ranking is roughly right *for KV-cache memory efficiency at a fixed quality bar*, but KV-cache efficiency is not the only axis a real decision is made on, and treating it as the only axis is exactly the mistake a staff interview is designed to catch.

**The actual axes in tension:**

- **Target context length and expected concurrency at serving time.** KV cache size scales linearly with context length and with the number of concurrent sequences being served; if the product's target context is short (a few thousand tokens) and expected serving concurrency is modest, plain MHA's cache cost may simply never bind as the dominant serving-cost driver, and the engineering cost of adopting a more complex mechanism buys little. If the target context is 128K+ tokens served at meaningful concurrency, KV-cache memory becomes the dominant serving-cost line item almost regardless of model size, and this is precisely the regime where GQA (near-universal by 2024, see `..\..\OpenSource\003_Llama3.md` Section 9) or MLA's more aggressive compression (`..\..\OpenSource\006_DeepSeek_V2.md` Section 9) earns its keep.
- **Training-infrastructure maturity for the mechanism.** GQA is, at this point, a essentially-zero-risk default: it is a small, well-understood modification to standard multi-head attention (share K/V projections across a group of query heads), supported natively by every major training and inference framework, with no known novel instability modes. MLA is a genuinely more involved mechanism — a learned low-rank latent compression with a decoupled-RoPE component (see `..\..\OpenSource\006_DeepSeek_V2.md` Section 2 for the full derivation) — that had to be co-designed, debugged, and validated by DeepSeek across two model generations before it was fully proven at frontier scale; a lab adopting it for the first time is taking on nontrivial implementation and validation risk that GQA does not carry. Sliding-window attention (`..\..\OpenSource\004_Mistral7B.md`) sits in between in mechanism complexity but introduces its own inference-serving subtlety (rolling-buffer KV cache management, correct masking at chunk boundaries) that a team has to get right.
- **The quality-vs-compression tradeoff is not free for any of these, and the honest framing is "how much quality degradation is acceptable for how much cache savings," evaluated empirically, not assumed.** GQA's quality cost relative to full MHA at a matched group count is well-characterized across the field as small-to-negligible at typical group sizes (4:1 or 8:1); MLA's specific claim is that its *learned* compression, jointly trained with the rest of the model, avoids much of the quality cost naive K/V-head-sharing schemes would incur at comparable cache-size reduction — but validating that claim for a *new* model requires exactly the kind of proxy-scale ablation work covered in `006_Pretraining_Ablations_And_Research_Methodology.md`, because "does this compression scheme's quality tradeoff hold at our target scale" is not free to assume from another lab's published numbers on a different architecture, data mixture, and parameter count.
- **Serving-stack lock-in.** Adopting a genuinely novel attention variant (MLA) means every downstream piece of inference infrastructure — KV-cache management, speculative decoding, batching/continuous-batching schedulers — has to be adapted or rebuilt around the new mechanism's cache layout, rather than reusing the substantial ecosystem of tooling built around standard MHA/GQA (e.g., widely-used inference-serving frameworks' out-of-the-box kernel support). This is a real switching cost independent of the mechanism's theoretical merit, and is exactly the kind of cost that favors sticking with GQA even when a lab is convinced MLA is technically superior, if that lab's serving stack and engineering bandwidth are not ready to absorb the change.

### 2.2 Sliding-window attention as a distinct point in the design space

Sliding-window attention (`..\..\OpenSource\004_Mistral7B.md`) is a different kind of tradeoff from the GQA/MLA axis above: rather than compressing the *representation* stored per cached token, it bounds *how many* tokens are attended to (and therefore cached, in a rolling-buffer implementation) at all, per layer, trading long-range direct attention for depth-accumulated effective receptive field (receptive field grows as \(L \times W\) across \(L\) layers, not just \(W\) — see the Mistral doc for the full argument). The decision to adopt sliding-window attention is a bet that a fixed, bounded local window plus depth-accumulated context is an acceptable substitute for full quadratic attention *for the target use case* — a bet that is far more defensible for a model whose target deployment is dominated by moderate-length, latency-sensitive serving (Mistral 7B's explicit positioning) than for a model whose product story centers on long-document or long-conversation reasoning requiring genuinely direct long-range attention (in which case a lab is more likely to accept the full quadratic cost, mitigated by GQA/MLA-style cache compression, or a hybrid of dense-and-sliding-window layers, rather than sliding-window-everywhere). Several 2024–2025-era frontier architectures use exactly this hybrid — alternating a minority of full-attention layers with a majority of sliding-window layers — as a middle point on this tradeoff; whether a specific released model does this is model-specific and should be checked against that model's own doc rather than assumed.

### 2.3 The decision process, stated as a checklist a staff engineer would actually walk through

1. What is the **target native context length**, and separately, what is the **target maximum context length after a later extension stage** (see `005_Curriculum_And_Multi_Stage_Pretraining.md`)? Short native/short max: cache-efficiency mechanisms matter least. Short native/long max: the extension stage's behavior under whichever attention variant was chosen becomes a real validation question in its own right.
2. What is the **expected serving concurrency and latency SLA** for the primary product surface? High concurrency + tight latency SLA pushes hard toward whichever mechanism minimizes KV-cache footprint, because cache footprint is frequently the binding constraint on how many concurrent sequences a given accelerator memory budget can serve, not raw compute.
3. **Does the org already have production-grade training infrastructure for this mechanism**, or would adopting it require a dedicated infrastructure investment (custom kernels, new checkpointing/serving logic) on the critical path of the training run? If the mechanism is unproven internally, is there time and compute budget for a dedicated proxy-scale validation phase (again, `006_Pretraining_Ablations_And_Research_Methodology.md`) before committing it to the full run?
4. **What does the competitive landscape's serving-cost bar look like at the time this model will ship**, not at the time the decision is made — architecture decisions lock in 6–18+ months before shipping, so the right comparison is against where the field's serving-cost/quality frontier is expected to be at ship time, not today.
5. **What is the cost of being wrong, and is it recoverable?** A dense-vs-MoE decision or an MHA-vs-MLA decision cannot be cheaply reversed after a full pretraining run; a context-length target can be partially corrected post-hoc via an extension stage (imperfectly — native long-context training and post-hoc extension are not fully equivalent, see `005_Curriculum_And_Multi_Stage_Pretraining.md`) but the core architecture cannot.

### 2.4 Hardware constraints as a first-class input, not an afterthought

An easily underweighted point: the attention-variant decision is not made purely against an abstract "what context length and concurrency do we want" question — it is made jointly against **what hardware the lab actually has access to and its specific bandwidth/topology characteristics**. DeepSeek's specific circumstance is the clearest public illustration: training on H800 GPUs (the NVLink-bandwidth-reduced, China-market variant of H100, adopted under export-control constraints) made cross-device communication a scarcer resource than it would be on unrestricted H100 clusters, which is a direct, disclosed part of the motivation for MLA's aggressive KV-cache compression (less data to move, not just less to store) and for the custom DualPipe/all-to-all kernel investment described in `..\..\OpenSource\007_DeepSeek_V3.md`, Section 4. A lab with unrestricted H100/H200-class interconnects does not face the identical version of this constraint, and should not assume the exact same relative payoff from investing in an MLA-class compression mechanism — the *KV-cache-memory* case for compression (Section 2.1) is largely hardware-independent, but the *communication-bandwidth* case is specifically sharper on bandwidth-constrained hardware, which is a genuinely separate input into the same decision that depends on the specific cluster a lab is actually training on, not a universal constant.

### 2.5 A decision matrix, condensed

| Situation | Recommended default | Rationale |
|---|---|---|
| Short target context (<=8-16K), modest concurrency, no prior novel-attention experience | Plain GQA | Cache pressure never binds strongly enough to justify implementation risk beyond the near-zero-risk default |
| Long target context (128K+), high concurrency, mature training/serving infra | MLA (if infra maturity supports it) or aggressive GQA grouping | Cache-memory and bandwidth both become dominant serving-cost drivers; the investment in a more complex mechanism has a clear payoff to point to |
| Long target context, first attempt at a novel attention mechanism, hard deadline | GQA, deferring MLA-class investment to a future generation | Matches the dense-vs-MoE deadline logic in Section 1.2 — de-risk one axis at a time under time pressure |
| Latency-dominated, moderate-length serving as the primary product story | Sliding-window (possibly hybridized with periodic full-attention layers) | Bounds compute/cache per layer directly; defensible when genuinely long-range direct attention isn't the product's core value proposition |
| Bandwidth-constrained hardware (export-controlled or otherwise limited interconnect) | Weight compression mechanisms (MLA-class) more strongly favored than on unrestricted hardware | The communication-volume case for compression is sharper specifically when interconnect, not just cache memory, is the scarce resource (Section 2.4) |
| Broad open-weight distribution across many, heterogeneous deployment environments | GQA over MLA, absent a strong countervailing reason | Universal tooling support (Section 2.1's fourth bullet) matters more when the model will be served by many third parties with varying infrastructure, not just the releasing lab's own stack |
| Single, tightly-controlled first-party API product with full control over serving infrastructure | More room to justify a novel mechanism (MLA-class) if the cache/bandwidth math justifies it | The releasing lab owns the entire serving stack end to end, so serving-stack lock-in (Section 2.1's fourth bullet) is a cost paid once internally rather than externalized to many third-party deployers |

## 3. Target context length

### 3.1 Why this is a staged decision, not a single number

Almost no frontier model is pretrained end-to-end at its eventual maximum advertised context length. The near-universal pattern (DeepSeek-V2 pretrained at 4K then extended to 128K via YaRN; Llama 3 initially 8K then extended to 128K in the 3.1 release; Qwen2.5's YaRN-based extension to 128K on select sizes — see the respective docs in `..\..\OpenSource\`) is: **pretrain the large majority of tokens at a shorter context, then run a comparatively small, dedicated context-extension stage.** The reason this is the dominant pattern rather than training natively at the target length throughout is almost entirely a cost argument: attention's compute (and, for unsharded implementations, activation memory) scales quadratically in sequence length, so training the entire multi-trillion-token main run at, say, 128K context rather than 4-8K context would multiply the dominant cost component of the *entire* run by a large factor, for a capability (long-context utilization) that a much smaller dedicated stage can teach almost as effectively once the model already has strong short-context language competence. The mechanics of that extension stage (RoPE frequency rescaling, YaRN, NTK-aware interpolation) are covered in `005_Curriculum_And_Multi_Stage_Pretraining.md`; the point here is the *decision*, not the mechanism: choosing a native pretraining context length is a decision about where on the cost curve to do the bulk of training, made jointly with a separate decision about how much of the (much smaller) extension-stage budget to allocate to reaching the target maximum length.

### 3.2 What actually drives the target number

- **Product requirements that cannot be satisfied by retrieval/chunking workarounds** — e.g., a coding-assistant product that needs to reason over an entire large repository in one context, or a long-document-analysis product, pushes the target length up directly.
- **Serving-cost tolerance at the target length**, since (per Section 2) whichever attention variant was chosen determines how expensive it is to actually serve at that length — a target context length decision and an attention-variant decision are not independent; committing to a very long target context without a cache-efficient attention mechanism is a much more expensive commitment than the same target length with GQA/MLA already in place.
- **Diminishing evaluated utility beyond some length.** Long-context capability is not simply "supports N tokens" — it requires the model to actually *use* information anywhere in that window (validated via needle-in-a-haystack-style and long-document benchmarks, per the Evaluation section of the per-model docs), and a lab has to weigh whether pushing the target length further is worth the extension-stage compute given evidence of returns actually materializing at the longer lengths tested, versus a context length that looks good in a spec sheet but is not reliably usable throughout.

### 3.3 A survey of disclosed context-length tiers and their architecture pairings

It is useful to hold a rough map of how released models have actually paired context-length targets with attention-variant and architecture choices, not as a rule to copy mechanically but as evidence of what the field has judged to be a workable pairing at each tier:

| Model | Native pretraining context | Extended/max context | Attention variant | Dense/MoE |
|---|---|---|---|---|
| Mistral 7B | Trained with sliding window W=4096 throughout | N/A (sliding-window design, not a post-hoc extension) | Sliding-window + GQA | Dense |
| DeepSeek-V2 | 4K | 128K (via YaRN) | MLA | MoE |
| DeepSeek-V3 | Short native, extended | 128K | MLA | MoE (fine-grained, 256 routed + 1 shared) |
| Llama 3 (initial) | 8K | — | GQA | Dense |
| Llama 3.1 | 8K | 128K (via RoPE base-frequency rescaling + staged continued pretraining) | GQA (universal, including 8B) | Dense |
| Qwen2.5 (select sizes) | Shorter native | 128K (via YaRN/dynamic NTK-style scaling) | GQA | Dense |
| GLM-4 / GLM-4-9B | Not detailed to the same precision | 128K (some variants report up to 1M) | Not fully disclosed at comparable precision | Not fully disclosed for the flagship tier |

Two patterns worth naming from this table directly. First, **every model that pushes to 128K+ pairs that target with some cache- or bandwidth-conscious attention mechanism** (GQA at minimum, MLA for the MoE entrants) — none of the entries in this table combine a 128K+ target with plain, ungrouped MHA, which is exactly the joint-constraint pattern Section 4 argues for rather than an incidental correlation. Second, **the extension-stage mechanism (YaRN vs. RoPE base-frequency rescaling vs. Mistral's from-scratch sliding-window design) is itself a real design choice distinct from the attention-variant choice** — Mistral's design never needs a context-extension stage at all because sliding-window attention is trained in from the start rather than retrofitted, which is a structurally different commitment (bounded local attention from step zero) than "train short, then extend," and is a data point for a lab willing to accept the sliding-window tradeoff (Section 2.2) specifically to *avoid* needing a separate extension-stage investment (`005_Curriculum_And_Multi_Stage_Pretraining.md`) altogether.

## 3a. Organizational and talent constraints as a real input, not a soft factor

Every decision in this file has, so far, been framed against technical and product constraints. A complete staff-level answer should also name organizational constraints explicitly, because they are frequently the actual binding constraint in practice even when the technical tradeoff analysis points elsewhere:

- **Existing team expertise.** A team with deep tensor-parallel dense-model training experience and no expert-parallel systems engineers is going to execute a dense-model bet meaningfully better, on the same calendar timeline, than the same team's first MoE attempt — this is not a knock on the team, it is a direct consequence of MoE requiring a genuinely different systems skill set (Section 1.1), and a staff-level recommendation should weigh this as heavily as the abstract inference-cost case for MoE.
- **Hiring and ramp-up time.** If the technical case for a novel mechanism (MLA-class compression, a new MoE routing scheme) is strong but the org lacks in-house expertise, the realistic options are hiring (which itself takes months, and new hires still need ramp-up time on the specific codebase and cluster) or an extended internal R&D investment (`003...md` Section 1.2's "defer to next generation" pattern) — "just adopt the better mechanism" is not a costless instruction when the constraint is people, not just compute budget.
- **Prior investment and switching costs in existing tooling.** A lab with a mature, heavily-optimized dense-model serving stack has a real sunk-cost consideration (not a fallacy in this context, but a genuine asset) weighing against a switch to MoE or a novel attention mechanism — the existing tooling is itself a source of lower execution risk and faster time-to-ship that a purely technical tradeoff analysis can undervalue if it only compares mechanisms in the abstract.
- **Risk appetite set by leadership and the cost of a visible public failure.** A frontier lab whose reputation is built on reliability and safety framing may reasonably weight execution risk more heavily than a smaller or newer entrant trying to differentiate on technical novelty — this is a legitimate, if non-technical, input into the same decision process, and a staff engineer who ignores it in favor of a purely mechanism-focused recommendation is giving an incomplete answer.

## 3b. A worked scenario: synthesizing the framework end to end

To make the whole framework concrete rather than a list of separately-stated considerations, walk through a single hypothetical case. Suppose a mid-sized lab, with prior experience training dense models up to ~30B parameters (no MoE experience, standard NVLink/InfiniBand cluster with no export-control bandwidth restriction), is planning its first attempt at a frontier-class model, targeting a coding-assistant product that needs to reason over large repositories (motivating a long context target) and expects moderate, not yet massive, initial query volume.

Applying the framework: the **dense-vs-MoE** decision (Section 1) leans dense, given no in-house MoE experience and this being a first frontier attempt — the org has not yet earned the standing to take on MoE's execution risk simultaneously with everything else that's new about a first frontier run. The **attention-variant** decision (Section 2), given the long-context product requirement, leans toward GQA at minimum, with MLA considered but likely deferred (per Section 2.5's matrix) given the same "first attempt, no prior novel-mechanism experience" constraint that argues against MoE — stacking two unproven novel mechanisms (MoE and MLA) simultaneously on a first frontier run compounds risk in exactly the way `006_Pretraining_Ablations_And_Research_Methodology.md` Section 9's taxonomy warns against. The **context-length target** (Section 3) is set by the repository-reasoning product requirement, likely in the 128K-256K range depending on typical repository size, achieved via short native pretraining plus a dedicated YaRN-style extension stage rather than native long-context training throughout, consistent with the cost argument in Section 3.1. The **overtraining posture** (cross-referencing `002_Scaling_Laws_And_Compute_Optimal_Training.md`, Section 6) leans closer to Chinchilla-optimal than aggressively overtrained, given the moderate (not yet massive) projected query volume — a decision this file's framework does not itself resolve, but which interacts directly with the \(N\) chosen here, since a smaller \(N\) chosen for inference-cost reasons would in turn slightly ease the KV-cache-pressure case for MLA. The resulting configuration — dense, GQA, staged long-context extension to a moderate-large target, near-Chinchilla-optimal sizing — is a genuinely conservative bet relative to what a DeepSeek- or Mistral-style technical-novelty-maximizing configuration would look like, and that conservatism is the *correct* recommendation given this specific lab's stated constraints, not a failure to appreciate the more novel mechanisms' technical merits.

## 4. Synthesis: architecture decisions as a joint constraint-satisfaction problem, not three independent choices

The three decisions in this file are not independent, and treating them as independent is a common mistake worth calling out explicitly in an interview answer. A target context length of 128K with high expected serving concurrency all but forces a cache-efficient attention mechanism (GQA at minimum, MLA if the org has the infrastructure maturity to support it); a decision to go MoE for inference-cost reasons interacts directly with how expensive that same long-context serving becomes, since expert-parallel dispatch/combine and long-context KV-cache pressure are both live serving-cost concerns simultaneously (exactly the situation described for DeepSeek-V3 in `..\..\OpenSource\007_DeepSeek_V3.md`, Section 9); and every one of these decisions is being made against a training-infrastructure-maturity constraint that is specific to the lab making the decision, not a property of the mechanisms themselves. The staff-level skill being tested is not "know which mechanism is theoretically best" — it is being able to walk through, for a specific hypothetical product and constraint set, which combination of choices is actually executable at acceptable risk within the time and infrastructure the lab actually has, and being explicit about what is being traded away by each choice rather than presenting the final answer as costless.

## 4a. Three real resolutions of the same framework, contrasted directly

It is instructive to read three publicly-documented architecture bets side by side, not as "who chose the best mechanism" but as three different resolutions of the *same* constraint-satisfaction problem this file describes, each rational given that lab's actual situation at the time.

**Mistral 7B** (`..\..\OpenSource\004_Mistral7B.md`) bet on sliding-window attention trained in from the start, at a comparatively small 7B dense scale, with an explicit product orientation toward efficient, latency-sensitive serving rather than long-document reasoning. Given a small team (relative to the largest labs), a permissive Apache 2.0 release strategy, and no disclosed appetite for MoE or novel cache-compression research at that point in the org's history, committing to a well-understood, moderate-complexity mechanism (sliding-window + GQA) that could be trained in natively — avoiding the need for a separate context-extension stage entirely — is a coherent, low-execution-risk choice that matches Section 2.2's framing exactly: accept a bounded local window in exchange for not needing to build or validate a more complex compression or extension mechanism at all.

**DeepSeek** (V2 through V3, `..\..\OpenSource\006_DeepSeek_V2.md`, `..\..\OpenSource\007_DeepSeek_V3.md`) bet on the opposite end of the risk spectrum: a genuinely novel attention mechanism (MLA) and, by V3, a fine-grained MoE design with a novel load-balancing scheme, layered together. This is legible as rational specifically *because* of the hardware constraint named in Section 2.4 — training on bandwidth-restricted H800s under export controls made communication-and-memory efficiency a first-order strategic lever rather than an optional optimization, which changes the expected payoff of investing heavily in novel compression research relative to a lab with unrestricted interconnect access. It is also legible as a staged bet across generations exactly per Section 1.3/1.4/4a's de-risking logic: MLA appears at V2 without the more aggressive fine-grained MoE and novel balancing scheme, which arrive only at V3 once the underlying MoE/MLA training stack was already validated.

**Llama 3/3.1** (`..\..\OpenSource\003_Llama3.md`) bet on staying dense and universalizing GQA, while addressing inference-cost pressure through the overtraining lever (`002_Scaling_Laws_And_Compute_Optimal_Training.md`, Section 6) rather than through MoE or a novel attention mechanism. Given Meta's existing organizational strength in dense-model training and serving infrastructure at extreme scale, and a product strategy oriented around broad open-weight distribution across many deployment contexts (where serving-stack simplicity and universality of tooling support matter more than for a single, tightly-controlled API product), this is a coherent resolution that explicitly avoids the execution risk of MoE (Section 1.2) and the serving-stack lock-in risk of a novel attention mechanism (Section 2.1's fourth bullet), while still directly addressing inference cost through a different, lower-infrastructure-risk lever.

None of these three is "the correct architecture" in the abstract — each is the correct resolution of this file's framework *for that lab's specific hardware, team, product strategy, and risk appetite at that point in time*, which is exactly the staff-level point this file has been building toward: the framework's output is a function of the inputs, not a fixed ranking of mechanisms.

## 4b. Red flags in an architecture decision-making process

A few process-level warning signs worth naming directly, since they're common enough in practice to be worth pattern-matching against explicitly rather than only reasoning about the technical merits in isolation:

- **A decision justified purely by "competitor X uses this mechanism," with no accompanying analysis of whether this lab's constraints (Section 3a's organizational factors, Section 2.4's hardware factors) resemble competitor X's.** A mechanism's success elsewhere is real evidence, but evidence about a different lab's situation, not a substitute for this lab's own constraint analysis.
- **No explicit statement of what happens if the chosen mechanism doesn't transfer as expected** — i.e., no fallback plan, no canary-run checkpoint, no acknowledged decision-record (per `006_Pretraining_Ablations_And_Research_Methodology.md` Section 7) stating the risk being accepted. A good process names the risk even when it decides to accept it.
- **Treating context length, attention variant, and dense-vs-MoE as three separately-owned decisions made by different sub-teams without a synthesis step** — exactly the failure mode Section 4 warns against, and one that's organizationally easy to fall into when different teams naturally own different parts of the stack.
- **Anchoring on the most recently published, most technically novel mechanism as a default**, rather than starting from this lab's own constraints and asking which mechanism satisfies them — novelty bias is a real distortion in a fast-moving field, and the correct process asks "what do we need" before "what's newest."

## 5. What happens after the decision: living with it for the model's lifetime

Architecture decisions made at pretraining time don't just determine the training run's characteristics — they set a ceiling and a floor on what every later stage of this model's lifecycle can do, and it is worth tracing that forward explicitly rather than treating the pretraining decision as the end of the story.

- **Post-training and alignment work inherits the architecture wholesale.** Whatever attention mechanism, MoE configuration, and context length were chosen at pretraining time are exactly what every subsequent SFT, RLHF/RLAIF, and distillation stage has to work with — none of those later stages can retrofit a different KV-cache footprint or a different total-parameter/activated-parameter split. A staff engineer evaluating a pretraining-time architecture decision should ask not just "is this good for pretraining loss" but "does this leave the org room to do the post-training work it will need to do," e.g., an extremely aggressively-compressed attention mechanism that turned out to have subtle quality costs at instruction-following or long-multi-turn-dialogue tasks specifically (as opposed to raw next-token loss) would only surface during post-training evaluation, by which point the underlying architecture is fixed.
- **Serving-infrastructure investment amortizes over the model family's lifetime, not just one release.** A lab that invests in expert-parallel serving infrastructure for its first MoE model is paying an infrastructure cost that then applies to every subsequent MoE release in that family — which is part of why the "defer to next generation" pattern (Section 1.2, Section 1.4) is a genuinely reasonable strategy rather than merely a stopgap: the infrastructure investment made for generation N+1 is expected to keep paying off for N+2, N+3, and so on, which changes the calculus of when it's worth absorbing the one-time cost.
- **Competitive positioning drifts, and a decision that was conservative-but-correct at commit time can look either prescient or dated by ship time.** Because architecture decisions lock in 6-18 months before a model ships (Section 2.3's checklist item 4), a dense, GQA-based, conservative bet made under real constraints (Section 3b's worked scenario) may ship into a market where every competitor has since moved to MoE — this is a real risk inherent to the timeline, not a sign the original decision process was flawed, and is exactly why revisiting the framework for the *next* generation, informed by how the competitive and infrastructure-maturity landscape has actually moved, is a recurring exercise rather than a one-time decision.

## 5a. Quantifying the tradeoff rather than reasoning about it purely qualitatively

Everything in Sections 2-3 has been argued qualitatively; a staff-level treatment should also be able to put rough numbers on the tradeoff being made, since "KV-cache memory becomes the dominant serving-cost driver" is a claim that should be checkable, not just asserted. A simple first-pass model: per-sequence KV-cache bytes scale as \(2 \times L \times H_{kv} \times d_{head} \times S \times b_{\text{dtype}}\) for standard MHA/GQA (layers × KV heads × head dim × sequence length × bytes per element, times 2 for storing both K and V), while weight memory is a fixed \(\approx 2N\) bytes (bf16) independent of sequence length or concurrency.

```python
def cache_dominates_weights(n_params: float, n_layers: int, n_kv_heads: int,
                              head_dim: int, seq_len: int, concurrent_sequences: int,
                              dtype_bytes: int = 2) -> bool:
    """Rough first-pass check: at this context length and concurrency, does
    aggregate KV-cache memory across all concurrent sequences exceed weight
    memory? If so, cache -- not raw parameter count -- is the dominant serving
    memory constraint, which is exactly the regime that most strongly
    justifies investing in a cache-compressing attention mechanism."""
    weight_bytes = n_params * dtype_bytes
    per_seq_cache = 2 * n_layers * n_kv_heads * head_dim * seq_len * dtype_bytes
    total_cache = per_seq_cache * concurrent_sequences
    return total_cache > weight_bytes
```

Running this at, say, 13B parameters, 40 layers, 8 KV heads (GQA), head_dim 128, at 128K context and only 4 concurrent sequences already shows cache memory (`2*40*8*128*128000*2*4 ≈ 2.1e10` bytes, ~21GB) comparable to weight memory (`13e9*2 = 2.6e10` bytes, ~26GB) — and cache memory scales linearly with concurrency while weight memory does not, so any push toward higher concurrency at this context length flips the dominant constraint decisively toward cache, exactly the regime Section 2.5's decision matrix flags as favoring a more aggressive compression mechanism. Running the same check at a short context (say, 4K) and modest concurrency shows cache memory is a small fraction of weight memory, consistent with Section 2.1's claim that cache-efficiency mechanisms simply don't bind as a constraint in that regime — the qualitative argument and this rough quantitative check should always agree, and running a check like this for a specific candidate product's actual target numbers, rather than reasoning purely by analogy to a "128K is long, so cache matters" heuristic, is the concrete, demonstrable version of the judgment this file is trying to develop.

## 5b. Revisiting a decision mid-family: what actually changes between generations

A natural follow-up question: given that an architecture decision is locked in for a given model's training run, when does a lab actually revisit it, and what typically triggers a change between generation N and N+1 rather than N and N+0.5 (an interim point release)? The pattern visible across this collection's documented lineages is that **point releases (e.g., ChatGLM to ChatGLM2, DeepSeek-V2 to V2.5-class updates where applicable) tend to hold the core architecture fixed and iterate on data, post-training, and comparatively contained mechanism swaps** (ChatGLM2's introduction of MQA specifically, without a broader architecture overhaul, per `..\..\OpenSource\010_GLM4.md` Section 9), while **full-number generational jumps (V2 to V3, Llama 2 to Llama 3) are where the larger, riskier architecture bets change** (DeepSeek's fine-grained MoE and new balancing mechanism at V3; Llama's universal GQA adoption and 4x vocabulary expansion at Llama 3). This is consistent with the staged de-risking logic threaded throughout this file: the comparatively contained, well-scoped mechanism swap is a natural fit for an interim release with a shorter validation runway, while the larger architectural bet is reserved for a full generational cycle where there's time to run the fuller validation pipeline (proxy ablation, canary run, per `006_Pretraining_Ablations_And_Research_Methodology.md`) that a bet of that size warrants.

## 6. A closing checklist

Before finalizing any of the three architecture axes in this file for a real training run, a staff research engineer should be able to state, specifically:

1. For dense vs. MoE: what is the org's actual prior experience with expert-parallel training and serving, and does the projected inference-volume/cost case justify taking on that execution risk now versus deferring to a future generation (Section 1.2)?
2. If MoE: what granularity and top-k are being chosen, and is that choice being validated at proxy scale or copied from a published recipe with an acknowledged, undischarged risk that the recipe doesn't transfer to this org's data/scale/cluster (Section 1.3, Section 1.4)?
3. For the attention variant: what target context length and serving concurrency are actually driving the decision, stated as numbers, not adjectives like "long" or "high" (Section 2.1, Section 2.5)?
4. Is the chosen attention mechanism's quality-vs-compression tradeoff validated for this org's own architecture and data, or assumed from another lab's published numbers (Section 2.1's third bullet)?
5. What hardware-specific constraints (interconnect bandwidth, topology, export-control restrictions if applicable) does this lab actually face, and has the attention-variant decision been made with those constraints as an explicit input rather than an implicit assumption of unrestricted bandwidth (Section 2.4)?
6. For context length: what product requirement is actually driving the target number, and has it been checked against evidence that the extension stage's chosen mechanism (YaRN, NTK-aware scaling, or a from-scratch sliding-window design) is expected to deliver *usable* capability throughout that range, not just architectural support for it (Section 3.2, Section 3.3)?
7. Are the three decisions being evaluated jointly, with each one's implications for the other two made explicit, or is there a risk that they were decided independently by different sub-teams without a synthesis step (Section 4)?
8. What organizational and talent constraints (Section 3a) are actually binding here, independent of the technical merits, and has that been stated openly to whoever is approving the final commitment?
9. Is this decision being made at a full generational boundary (where a larger architecture bet is appropriate given a longer validation runway) or as part of an interim point release (where a more contained mechanism swap is the better-fitting scope, per Section 5b)?
10. Has the decision-making process been checked against Section 4b's red-flag list — competitor-mimicry without constraint analysis, no stated fallback plan, siloed sub-team ownership, or novelty-anchoring — before being finalized?

## 7. Quick-reference glossary

- **Activated parameters** — for an MoE model, the subset of total parameters actually computed for a given token (routed experts selected by the router, plus any always-on shared experts); the relevant \(N\) for inference-cost and training-FLOPs (\(6ND\)) purposes, not total parameter count.
- **Granularity (MoE)** — the tradeoff between fewer, wider experts (coarse-grained) and many, narrower experts (fine-grained) at a fixed total-parameter budget; finer granularity trades a harder load-balancing problem for sharper per-token specialization (Section 1.3).
- **Top-k** — the number of routed experts activated per token in an MoE layer; the primary driver of expert-parallel all-to-all communication volume, largely independent of total expert count.
- **Shared expert** — an always-active MoE expert (not subject to routing) intended to absorb common, cross-domain computation so routed experts can specialize more narrowly.
- **Serving-stack lock-in** — the switching cost of adapting KV-cache management, batching, and speculative-decoding infrastructure to a novel attention mechanism's specific cache layout, distinct from that mechanism's technical merit (Section 2.1).
- **Staged de-risking** — committing to a less risky configuration now (e.g., dense, or coarse-grained MoE, or GQA) with an explicit plan to adopt a more aggressive mechanism in a future generation once infrastructure maturity has been separately earned (Sections 1.2, 1.4).
- **Hardware-constrained design co-optimization** — making an architecture decision partly in response to the specific bandwidth/topology characteristics of the cluster actually available, rather than against an abstract, hardware-independent notion of mechanism quality (Section 2.4).
- **Build-vs-buy (architecture)** — the choice between closely reproducing a published lab's architecture recipe (inheriting its validated evidence, at the cost of an unproven fit to your own data/scale/cluster) versus developing a from-scratch variant (Section 1.4).
- **Generational vs. point-release architecture change** — the observed pattern that large, risky architecture bets are typically reserved for full generational jumps with a longer validation runway, while interim releases iterate on more contained, well-scoped mechanism swaps (Section 5b).
- **Novelty-anchoring** — the process failure of defaulting to the most recently published, most technically novel mechanism without first establishing that it fits this lab's own constraints (Section 4b).
- **Cache-dominance check** — the rough quantitative test (Section 5a) of whether aggregate KV-cache memory across expected concurrent sequences exceeds weight memory at a candidate context length, used to check qualitative "cache pressure matters here" claims against an actual number.

An interview answer, or a real design document, that states a preference without naming the constraint that preference is conditioned on has not yet demonstrated the judgment this file is trying to build.

## 9. Closing summary

The through-line across every section of this file is that "which mechanism is best" is an incomplete question, and the complete question — "which mechanism is best *given this lab's compute budget, infrastructure maturity, team expertise, product timeline, and hardware constraints, accepting that this decision cannot be cheaply reversed once the training run starts*" — is the one a staff research engineer is actually expected to answer. The three real-world contrasts in Section 4a exist precisely to demonstrate that equally capable organizations, applying the same underlying framework, correctly arrive at different architecture bets when their inputs differ — which is the strongest available evidence that this is genuinely a constraint-satisfaction problem rather than a search for a single universally correct answer.

This also explains why an interviewer probing this topic is rarely looking for a specific named mechanism as "the answer" — they are looking for whether the candidate reaches for the constraints (compute, infrastructure maturity, team, timeline, hardware, reversibility) before reaching for a mechanism name at all, and whether the candidate can hold two or three of these constraints in tension simultaneously (as Section 4's synthesis and Section 3b's worked scenario both require) rather than optimizing one axis in isolation and treating the others as settled.

The practical takeaway to carry into any real design review or interview setting: state the constraints first, out loud, before naming a mechanism — compute budget, infrastructure maturity, team expertise, product timeline, hardware profile, and how reversible the decision is — and only then explain which mechanism best satisfies that specific, stated combination. Answers that skip straight to a mechanism name are answering a different, easier question than the one actually being asked.

## 11. A note on what this file deliberately does not cover

Two adjacent questions are intentionally out of scope here. First, exactly how large a compute budget to commit to this model in the first place — the \((N,D)\) sizing decision that determines, among other things, how much total training-FLOPs headroom exists to "spend" on a more expensive architectural mechanism — is covered in `002_Scaling_Laws_And_Compute_Optimal_Training.md`; this file assumes a roughly fixed compute budget and asks how to spend the architectural-decision portion of it. Second, the mechanics of *how* a chosen context-extension or attention mechanism is actually validated at proxy scale before being trusted at target scale — seed counts, canary runs, decision records — is developed in full in `006_Pretraining_Ablations_And_Research_Methodology.md`; this file names when that validation is warranted (Section 9's taxonomy) without re-deriving the statistical and process machinery behind it.

## 12. One-paragraph summary

If only one idea from this file survives: name the constraints — compute, infrastructure maturity, team, timeline, hardware, reversibility — before naming a mechanism, because the same mechanism ranking that is correct for one lab's constraints is routinely wrong for another's, and the three real-world contrasts in Section 4a exist to prove that point concretely rather than abstractly.

Carrying this forward into the rest of this module: the architecture chosen here fixes the inputs every later decision has to work with — the optimizer and batch-size choices in `004_Optimizers_LR_Schedules_And_Hyperparameters.md` are tuned against this specific architecture's gradient-scaling behavior, and the staging plan in `005_Curriculum_And_Multi_Stage_Pretraining.md` inherits whatever context-length and attention-mechanism commitments were made here without the option to revisit them mid-run.

That inheritance runs in one direction only, which is worth stating plainly: nothing downstream in this module can loosen a constraint locked in here, which is precisely why this file has spent so much of its length on process — checklists, red flags, decision records — rather than on mechanism description alone. Mechanism description is available, in full depth, in the per-model docs this file repeatedly cites; what those docs cannot give a reader is the judgment for weighing one lab's disclosed choice against a different lab's different, equally defensible one, which is the gap this file exists to close.

A last, deliberately blunt way to state the same point: if a candidate's answer to "should we use MLA" or "should we go MoE" does not change depending on whether the hypothetical lab has shipped an MoE model before, has unrestricted interconnect bandwidth, or is six months from a hard deadline, that candidate has not yet demonstrated the judgment this file is built around — regardless of how technically fluent their description of the mechanism itself is.

The same test applies equally well in the other direction, as a sanity check on your own reasoning: if you find yourself recommending the same architecture regardless of which constraints you're handed, stop and ask whether you have actually engaged with the constraints at all, or have simply reached for a familiar mechanism name and worked backward to a justification.
