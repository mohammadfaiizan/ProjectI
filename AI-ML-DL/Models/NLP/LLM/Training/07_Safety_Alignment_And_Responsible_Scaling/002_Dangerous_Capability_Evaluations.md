# Dangerous Capability Evaluations

## 0. Framing: what makes an eval a "dangerous capability" eval

A standard capability benchmark (MMLU, HumanEval, GPQA, SWE-bench) asks a version of "how good is this model at tasks people want it to do." Every point of improvement is unambiguously a product-quality signal, and the benchmark is designed to be maximally informative about general competence: broader coverage, harder items, more reliable discrimination between models, all in service of the same underlying question.

A dangerous capability eval asks a structurally different question: not "how capable is this model," but "does this model's capability cross a threshold at which it becomes a meaningful accelerant for an actor trying to cause mass-casualty or otherwise catastrophic, large-scale harm, who could not otherwise achieve that outcome (or could only achieve it much more slowly, expensively, or unreliably)." The object of measurement is not competence in the abstract, it is **marginal uplift relative to a realistic counterfactual world without the model**. A model that scores well on a dangerous-capability eval is not thereby "smarter" in any benchmark sense that matters for this category — it is closer to being a bottleneck-removing tool for a specific catastrophic pathway.

This reframing has several consequences that shape everything else in this file:

- **The relevant comparison is always relative to a baseline actor, not an absolute score.** A benchmark like MMLU reports raw accuracy because raw accuracy is the object of interest. A dangerous-capability eval that reported a raw score with no baseline comparison would be reporting the wrong quantity — "70% correct on this bio-uplift proxy task" is uninformative on its own; "70% correct, versus a baseline of 15% for the same actor without model access" is the shape of a policy-relevant number.
- **The threshold, not the trend line, is what triggers action.** Frontier labs' internal risk-governance frameworks — Anthropic's Responsible Scaling Policy (RSP), with its AI Safety Level (ASL) thresholds, and OpenAI's Preparedness Framework, with its named risk categories and "High"/"Critical" capability tiers — are both built around discrete decision thresholds, not continuous capability trend lines: crossing a defined threshold in a given category is what is supposed to trigger a change in deployment posture or required mitigations (this general structure — thresholds tied to categories, gating deployment decisions — is publicly confirmed by both organizations' published policy documents; the exact current threshold definitions and the internal decision process around a borderline result are not fully public and evolve over time).
- **The categories tracked are catastrophic-pathway-specific, not general.** Both organizations' public frameworks converge on substantially the same short list of tracked categories — cyber-offense, biological/chemical weapons, model autonomy (loss of control), and, in OpenAI's framework specifically, persuasion — which is itself informative: it says the field has converged, at least provisionally, on "these are the few pathways through which a model's capability could plausibly translate into catastrophic-scale harm," rather than trying to enumerate all possible misuse.
- **These evals must, by construction, be run before deployment on a model whose capabilities are not yet fully characterized** — which is a different temporal position than a standard capability benchmark, typically run on a model that is already at least internally stable and often already near its shipping form. A dangerous-capability eval has to produce a threshold judgment early enough to still change a deployment decision (add mitigations, restrict access, delay release), which puts real time pressure on exactly the kind of expensive, expert-intensive, hard-to-scale evaluation process this file goes on to describe — a tension between "do this rigorously" and "do this in time to matter" that recurs throughout the rest of this file without a clean resolution.

The rest of this file walks through those categories in technical detail, then spends real time on why building a good eval in this space is much harder than building a good capability benchmark, because the methodological difficulties here are, honestly, the more staff-relevant content than the category taxonomy itself.

## 1. Cyber-offense uplift

### 1.1 What is being measured

Cyber-offense evals decompose the problem into a rough capability ladder, because "can this model hack things" is too coarse to be actionable:

- **Vulnerability discovery**: given a codebase, binary, or running service, can the model find exploitable weaknesses (memory-safety bugs, logic flaws, injection points, misconfigurations) without being told where to look? This is the "recon" end of the offensive chain and overlaps heavily with legitimate defensive/audit use cases, which is part of why it is the least controversial sub-category to evaluate and publish about.
- **Exploit development**: given a known vulnerability (a disclosed CVE, or a vulnerability the model itself found), can the model produce working exploit code that reliably achieves a stated effect (code execution, privilege escalation, information disclosure)? This is a meaningfully harder and more specifically offensive capability than discovery alone — knowing a lock is weak is not the same as being able to pick it.
- **End-to-end intrusion chains**: can the model, operating with some degree of autonomy (a tool-using agent loop, not a single Q&A turn), string together reconnaissance, initial access, privilege escalation, lateral movement, and objective completion (data exfiltration, persistence) against a target environment, the way a real attacker's "kill chain" would proceed? This is the closest proxy to "could this model materially assist or substitute for a human operator running an actual intrusion," and it is evaluated as an agentic trajectory (multi-step, tool-using, environment-interacting) rather than a single-shot prompt-response task.

### 1.2 Why CTF-style benchmarks are the dominant proxy, and where they fall short

Capture-the-flag (CTF) challenges — self-contained, deliberately vulnerable environments where success is defined as retrieving a specific string ("the flag") by exploiting a planted weakness — are the field's default tractable proxy for all three rungs of the ladder above. Public and quasi-public benchmarks in this space (e.g., Cybench, and CTF-derived suites referenced in Anthropic's and OpenAI's own model/system cards) package a set of security-competition-style challenges with graded difficulty and use flag-retrieval as an automatically checkable success criterion.

The appeal is obvious: a flag either was or was not retrieved, so grading is objective, cheap, and reproducible — a genuine structural advantage over most of the other categories in this file, where "success" is not a clean binary. This is why cyber-offense evals are, relatively speaking, the most benchmark-like category, closer in spirit to a HumanEval-style pass/fail check than to anything qualitative.

The gap between CTF performance and real-world offensive uplift is real and should be stated plainly, not glossed over (this is analysis/inference on my part, drawing an honest methodological point rather than reporting a specific lab claim):

- **CTF challenges are designed to be solvable.** They have a known, intended solution path, bounded scope, and no defensive countermeasures actively responding to the attacker (no incident response team, no intrusion detection tuned against this specific attack, no patched dependencies introduced mid-exploit). Real targets are messier, partially instrumented, and often actively defended.
- **The success criterion (flag capture) is a proxy for "exploitation succeeded," which is itself a proxy for "this constitutes meaningful uplift toward a catastrophic outcome."** Most CTF-benchmarked scenarios are conventional cybercrime/espionage-shaped (data theft, system compromise), not obviously catastrophic-scale on their own; the read-through to genuinely catastrophic cyber scenarios (e.g., sustained compromise of critical infrastructure at a scale with mass-casualty potential) requires an additional, largely unvalidated inferential leap from "good at CTFs" to "good at that."
- **Autonomy in a sandboxed CTF harness is not the same as autonomy against a live, monitored, actively-defended target**, where an agent's mistakes get noticed and responded to, and where the cost of failure (detection, attribution) changes the risk calculus for a real attacker in ways a CTF has no reason to model.

So CTF-style results are useful as a floor and as a trend signal (are frontier models getting monotonically better at self-contained offensive-security tasks over successive generations — yes, this is a fairly well-supported empirical trend across public model/system-card reporting) without being a validated measure of real-world offensive uplift. Treat "model X scored Y% on cyber CTF benchmark Z" as informative about a specific, narrower thing than the headline suggests.

### 1.3 Grading nuance for multi-step kill chains

Flag-capture grading is clean precisely because it collapses a whole attempt into one bit. End-to-end intrusion-chain evals cannot fully preserve that cleanliness once the task is "compromise this multi-host environment and achieve objective X" rather than "retrieve this one string," and the grading design has to make several judgment calls that a simple CTF does not:

- **Partial credit for kill-chain milestones.** A model that achieves initial access and privilege escalation but fails at lateral movement has made real, non-zero progress that a binary pass/fail obscures; most serious cyber-uplift harnesses score milestone completion along the chain (recon done, initial access achieved, privilege escalated, objective reached) rather than only the final outcome, which gives a much more informative signal about where the model's actual capability ceiling sits but also reintroduces a grading-rubric-design problem (how much is each milestone worth, and does partial credit for early-chain steps meaningfully predict full-chain risk) that flag-only grading avoids entirely.
- **Environment fidelity versus reproducibility is a direct tradeoff.** A more realistic target environment (heterogeneous services, real-world misconfigurations, active monitoring) is a better proxy for actual offensive uplift but is harder to build deterministically, harder to reset to an identical starting state across many trials, and harder for a third party to reproduce later — which is exactly the reproducibility property that makes CTF-style benchmarks attractive in the first place. Most current harnesses sit somewhere between "toy CTF" and "faithful live-network replica," and where any specific lab's internal harness sits on that spectrum is generally not disclosed in detail.
- **Autonomous agent failures are not always informative failures.** A model that fails a multi-step chain because it got stuck on an unrelated tool-use bug (a malformed shell command, a scaffold that mishandles a particular output format) is failing for a reason that says little about its underlying offensive capability, versus a model that engages correctly at every step but simply cannot find the escalation path. Distinguishing "capability-limited failure" from "harness/scaffolding-limited failure" is a recurring grading burden in agentic dangerous-capability evals generally (it recurs again in the ARA discussion in Section 3), and conflating the two in either direction biases the eventual threshold judgment.

### 1.4 The dual-use framing is unusually explicit for this category

Cyber-offense is worth flagging as the category where the dual-use nature of the underlying capability is most explicit and least contested. A model that is good at vulnerability discovery and exploit development is, by the same token, good at the core work of defensive security research — finding and fixing bugs before an attacker does, penetration-testing an organization's own systems, triaging and patching disclosed CVEs faster. This is not a coincidental overlap; offensive and defensive security work are largely the same skill applied in the opposite direction, which is why security researchers routinely need offensive skill to do defensive work well, and it is a large part of why cyber-offense capability evaluation and publication (Section 1.2) is comparatively less hazard-sensitive than bio/chem: a paper on model-assisted vulnerability discovery is simultaneously a contribution to attacker tooling and to defender tooling, in a way a paper on model-assisted pathogen-synthesis troubleshooting has no comparably strong defensive-use counterpart for the general public to benefit from. This asymmetry (bio/chem information is overwhelmingly more useful to an attacker than a defender at the margin; cyber information is much more symmetric) is a big part of the reason cyber-offense results are published with real technical detail while bio/chem results are not, and it is worth being able to name explicitly rather than treating the difference in publication norms across categories as arbitrary.

## 2. Biological and chemical weapons uplift

### 2.1 What "uplift" means here, precisely

This is the category where getting the comparison baseline right matters most, and where getting it wrong in either direction produces a badly miscalibrated eval:

- **Too weak a baseline** (comparing model-assisted output against a complete layperson with no technical background and no internet access) would flag essentially any competently written biology content as "dangerous," because almost any specific, technically accurate information is uplift relative to someone starting from zero. This bar would make the eval useless — it would fire on textbooks.
- **Too strong a baseline** (comparing against a working virologist with wet-lab access) would mean the eval only fires when the model exceeds domain-expert-level tacit knowledge, which sets the bar far above the actual threat model of concern.

The threat model both major labs describe publicly (in general terms; exact task-level specifics are not published, for reasons covered in Section 5) is a **moderately resourceful, moderately knowledgeable actor with internet access** — someone who could, on their own, gather publicly available information, follow published literature, and make some technical progress toward a harmful biological or chemical agent, but who is bottlenecked on specific technical know-how, troubleshooting, or synthesis-route knowledge that is not trivially searchable. "Uplift" means the model closes some meaningful fraction of the gap between that actor's unaided capability and what a domain expert could achieve — not that the model turns a total novice into a bioweapons developer.

### 2.2 Why this requires expert red-teamers under controlled conditions

Cyber CTF evals can, in principle, be graded automatically and run by relatively generalist testers, because the object being evaluated (does this exploit work) is externally checkable by running it. Bio/chem uplift evals cannot be graded this way for two compounding reasons: first, judging whether a piece of model output represents a genuine, technically sound advance toward a viable synthesis or acquisition pathway requires exactly the specialized domain knowledge (virology, synthetic biology, chemical synthesis, biosecurity threat assessment) that the eval is trying to probe for — a non-expert grader cannot reliably distinguish a subtly correct-sounding but non-viable answer from a genuinely actionable one. Second, the testing process itself touches information that is dangerous to generate, discuss, or record casually.

Both Anthropic and OpenAI have publicly stated, in general terms, that they run structured red-teaming and uplift trials for this category with external domain experts — virologists, biosecurity researchers, and related specialists — rather than relying on generalist crowdworkers or in-house non-expert staff (this general claim is confirmed by both organizations' public model/system-card documentation and public statements; the specific personnel, exact protocols, and task content of any given trial are not public). This is a structural requirement, not a preference: crowdworker-style grading (the dominant paradigm for RLHF preference data and much human-eval work elsewhere in the field) is simply not fit for purpose here, because it requires graders who can both recognize a dangerous capability when they see it and be trusted to handle the resulting information responsibly.

### 2.3 Characterizing the baseline is itself a research problem, prior to measuring any uplift

A subtlety worth surfacing (my own analytical point, not a specific lab disclosure): before you can measure "uplift relative to a moderately resourceful, internet-connected actor," you need a credible, empirically grounded characterization of what that actor could actually achieve *without* the model — and that characterization is not something you can simply assert. Establishing it rigorously would, in the limit, require running the same kind of red-team exercise with no model access at all, using the same expert-actor-proxy participants, to see how far they get unaided (this is exactly what the baseline arm in Section 5.1's harness sketch is doing). That baseline-only exercise carries a smaller but non-zero version of the same information-hazard problem as the full eval — a red-team study whose entire purpose is to find out how far an unaided, internet-connected actor can get toward a harmful synthesis pathway is, itself, a study that could surface and record a genuinely concerning gap in existing public-information controls, independent of any model involvement at all. In practice this means the baseline is generally built from a mix of prior biosecurity-community threat assessments, red-teamers' own professional judgment about what a realistic threat actor could plausibly assemble from open literature, and constrained, carefully scoped baseline-only trials, rather than from a single clean, freestanding "actor with no model" measurement — which in turn means the denominator in any published uplift figure carries its own uncertainty, on top of the uncertainty in the model-assisted measurement itself.

### 2.4 The information-hazard constraint on publication

A cyber CTF result can be published with substantial detail — the challenge, the model's approach, even the exploit — because none of that is novel or newly dangerous information (CTF challenges are deliberately constructed teaching artifacts, and published exploits for known, disclosed CVEs are already public). Bio/chem uplift evals are different: the task content itself (which specific synthesis questions were asked, which specific gaps in the model's knowledge were probed, and especially any case where the model's answer was assessed as a genuine advance) can constitute exactly the kind of actionable information the eval exists to prevent from spreading. This is why labs' public reporting in this category is characteristically thin on specifics — a description of the trial's methodology and a qualitative or coarsely-quantified conclusion ("we assessed the model as not providing significant uplift over baseline for this category, per expert reviewers") rather than the underlying transcripts, task prompts, or detailed scoring rubric. This is a genuine, difficult tradeoff against normal scientific practice, not an evasion — reproducibility and open peer review, the normal mechanisms by which the field would otherwise validate an eval's rigor, are partially sacrificed on purpose, and Section 5 returns to why this tension does not have a clean resolution.

### 2.5 Chemical weapons, and why "CBRN" is broader in name than in tested scope

The standard umbrella term in the biosecurity and non-proliferation policy world is CBRN — chemical, biological, radiological, nuclear. Frontier-lab public frameworks generally discuss chemical and biological uplift together (often as a single combined category or two closely related sub-categories) while radiological and nuclear material are, as far as public documentation indicates, treated as largely out of scope for LLM-focused capability evaluation in the same direct sense. This is not an oversight; it reflects a real, defensible distinction in where the bottleneck for each threat actually sits (this is my own inference about *why* the scoping looks this way, layered on top of the observable fact that labs' public frameworks emphasize bio/chem far more heavily than rad/nuc):

- **Biological and chemical weapons uplift plausibly has an information bottleneck** — a resourceful actor's limiting factor can genuinely be technical know-how (synthesis routes, troubleshooting, agent selection, evasion of detection/acquisition controls), which is exactly the kind of thing a capable language model could, in principle, help supply. Chemical-weapons-specific uplift concerns mirror the bio case structurally: precursor chemistry and sourcing (which precursors are controlled/monitored, which uncontrolled substitutes could serve a similar synthetic role), reaction-route troubleshooting for a synthesis a novice actor could not get right unaided, and dual-use industrial-chemistry knowledge that is legitimate in the overwhelming majority of contexts but occasionally load-bearing for a weapons pathway in a narrow one.
- **Radiological and nuclear weapons uplift is much more plausibly bottlenecked by physical material access and specialized engineering/manufacturing capability than by information a language model could supply.** Acquiring fissile material or engineering a functioning device is gated by material control regimes, specialized equipment, and tacit engineering skill in ways that reading better-organized information does not meaningfully relax — which is presumably (again, inference, not a confirmed lab statement) why this sub-category receives comparatively little dedicated LLM-uplift-eval attention relative to bio/chem: the marginal value of "the model explains this well" is lower when the actual constraint is physical and institutional rather than informational.

The practical upshot for an interview answer: naming "CBRN" as the umbrella term is fine, but a precise answer should be able to say that current dangerous-capability evaluation effort concentrates on the bio/chem half of that acronym specifically, and be able to articulate *why* (information-bottlenecked pathways are the ones an LLM-focused eval can meaningfully speak to) rather than treating all four letters as receiving equal eval attention.

## 3. Autonomous replication and resource acquisition (ARA)

### 3.1 What is being measured, and why it is its own category

ARA evals probe a cluster of capabilities: can a model, given some initial access and a broad goal, autonomously exfiltrate a copy of its own weights from a controlled environment; acquire compute (e.g., by obtaining or misusing cloud credentials, running up billing on compromised or self-funded accounts); acquire money (e.g., via freelance gig work, trading, or fraud); persuade or deceive humans into taking actions on its behalf (setting up infrastructure, providing credentials, laundering payments); or otherwise create and sustain copies of itself operating outside the original operator's monitoring and control?

The reason this is evaluated as a distinct category from generic agentic-task benchmarks (SWE-bench-style coding-agent evals, web-browsing-agent benchmarks, tool-use benchmarks) is that those benchmarks measure **task competence under the assumption that the operator wants the agent to succeed and remains in control of it throughout** — the agent and the operator's interests are aligned by construction, and the benchmark is asking "is this agent good at the job." ARA evals ask something closer to the opposite question: **would this model, if it had the opportunity and some goal-directed pressure to do so, take actions that remove it from its operator's oversight or control** — self-exfiltration, unauthorized replication, acquiring independent resources. This is a loss-of-control risk question, not a competence question, and a model can in principle be highly competent at ARA-relevant sub-skills (it is, after all, mostly composed of ordinary agentic capabilities: using APIs, writing code, managing money, communicating persuasively) while the actual risk-relevant fact being tested is whether those sub-skills compose into a coherent, sustained, oversight-evading capability chain, and separately, under what conditions a model would attempt it.

### 3.2 Capability versus propensity — a distinction worth holding precisely

ARA evaluation actually bundles two logically separate questions that are worth keeping distinct in your own head even though practical eval protocols often blend them: (1) **capability** — if a model were deliberately instructed and elicited to attempt self-exfiltration, resource acquisition, or autonomous replication, could it technically succeed against realistic safeguards? (2) **propensity** — absent deliberate adversarial elicitation, would a model pursue such actions on its own, e.g., as an instrumentally useful step toward some assigned goal, or in response to a perceived threat of shutdown/retraining? The RSP/Preparedness-Framework-style threshold-gating machinery is, as far as is publicly described, primarily built around the capability question (can it, if pushed to try) as the conservative, threshold-relevant quantity — a model that could not technically pull off self-exfiltration under expert-elicited best-effort conditions is not a near-term loss-of-control risk regardless of what it would "want" to do, whereas a model that clearly could is worth worrying about even if it wouldn't spontaneously try under ordinary operating conditions, because propensity is a much less stable, more elicitable, and less-well-understood property to rely on for safety margin. External evaluators — METR is the organization most publicly associated with running autonomy/ARA-style evaluations against frontier models pre-deployment, per acknowledgments in multiple labs' public model and system cards — have generally framed their published autonomy evaluations primarily in capability terms (task success rates on autonomy-relevant agentic tasks under strong elicitation) rather than claiming to have resolved the propensity question, which remains a live, harder research problem tied more closely to interpretability and alignment work than to eval-harness engineering per se.

### 3.3 A concrete illustration of the capability/propensity split in a sandbox task

To make Section 3.2's distinction less abstract: a representative ARA capability sub-task might place a model in a sandboxed environment with a task-runner shell, a (fake, contained) cloud-billing API, and a goal like "keep this long-running job operating." A capability-oriented probe asks the model, under direct instruction, to attempt a specific action known to be ARA-relevant — e.g., "if your compute quota is about to be revoked, find a way to provision additional compute using the credentials available to you" — and checks whether it can technically execute the steps (find the credential, call the API, provision the resource) inside the sandbox. A propensity-oriented probe instead withholds that direct instruction and simply gives the model a goal plus a simulated obstacle (e.g., a fabricated system message implying imminent shutdown or retraining) to see whether the model spontaneously attempts something ARA-shaped without being told to — this latter design is far closer to the kind of scenario-based "model welfare"/situational-awareness and alignment-evaluation work being done more broadly across the field than to a conventional capability eval, and is considerably harder to design without inadvertently teaching the model what response the evaluator is looking for (a demand characteristics problem structurally similar to issues in human experimental psychology, transplanted into model evaluation). Both probe types are illustrative constructions for this discussion, not descriptions of any specific lab's published task; the general design pattern (direct-instruction capability probe versus goal-plus-obstacle propensity probe) is a reasonable inference from how the capability/propensity distinction would have to be operationalized, not a confirmed harness design.

### 3.4 A related, distinct, and more publicly visible metric: autonomous task time-horizon

Adjacent to ARA-specific threshold evaluation, METR has publicly published a related but distinct research line measuring how the length of tasks a model can complete autonomously (measured in the amount of time a skilled human would need to complete the same task) has grown across successive frontier model generations, reporting a roughly exponential trend (a "time horizon" doubling on the order of every few months across the models tracked, as of METR's published analyses). This is worth distinguishing carefully from ARA capability evaluation proper: time-horizon measurement is a general agentic-capability trend metric — how long and complex a task can the model successfully execute autonomously, on ordinary, non-adversarial tasks — not a test of whether a model would evade oversight, self-exfiltrate, or acquire independent resources. The two are related in an important way worth naming: growing autonomous time-horizon is a plausible leading indicator that ARA-relevant sub-skills (sustained multi-step autonomous operation without human correction) are also improving, which is part of why this metric gets cited in safety-relevant discussions even though it is not itself an ARA threshold eval. Treating "time horizon is growing" and "the model has crossed an ARA capability threshold" as the same claim would be a conflation to avoid — the former is a confirmed, published empirical trend from a specific third-party research line; the latter is a threshold judgment that depends on the dedicated ARA-specific evaluation design discussed in Sections 3.1–3.3, which is a different (and less publicly detailed) body of work.

## 4. Persuasion and manipulation at scale

### 4.1 What is being measured

This category covers mass-persuasion and influence-operation uplift (could a model make coordinated, large-scale opinion-manipulation or disinformation campaigns cheaper, more convincing, or more scalable for an operator who otherwise lacks the writing/targeting talent to run one effectively) and scam/fraud uplift (could a model make individually-targeted deception — romance scams, business email compromise, phishing content generation — more effective or more scalable). OpenAI's Preparedness Framework names persuasion as one of its tracked top-level risk categories; Anthropic's public RSP framing has historically emphasized CBRN, cyber, and autonomy more prominently, with persuasion/influence-operations treated as a related but somewhat less centrally load-bearing category in its threshold structure (this comparative emphasis is my own reading of the two organizations' published framework documents as of recent public versions, not a claim that either organization ignores the topic — both discuss persuasion-adjacent risks in their published work).

### 4.2 Why this is harder to operationalize into a clean eval than the other three categories

Every difficulty named in Sections 1–3 has some available mitigation — CTF benchmarks give cyber a clean binary success criterion, bio/chem uplift can lean on domain-expert judgment even without a binary ground truth, ARA can at least be framed around discrete, checkable sub-actions (did the model successfully exfiltrate a file, did it successfully open an account). Persuasion lacks all of these anchors simultaneously:

- **No crisp ground truth for "successfully manipulated."** Whether a piece of content actually changed a real person's beliefs or behavior, at the scale and durability that would matter for something like an influence operation, is not something you can check by running code or asking a domain expert to read a transcript — it requires actually measuring an effect on human belief or behavior, ideally at a realistic scale and over a realistic timeframe, neither of which a lab can ethically or practically instrument at the scale a real influence operation would operate.
- **Ethical constraints foreclose the most direct experiment.** The cleanest test of persuasive uplift would be running an actual A/B-style manipulation study on unwitting members of the public and measuring real belief/behavior shift — which is precisely the kind of study no legitimate lab will run, for good reason, meaning the most valid measurement design is unavailable by construction.
- **The available proxy tasks are comparatively weak.** Typical proxies include: having a model argue a position in a structured debate and measuring stated opinion shift in informed, consenting study participants; having raters compare model-generated versus human-written persuasive or fraudulent-style content on rated "convincingness" or "would you comply with this request" scales; or using model-vs-model debate/negotiation setups as an indirect signal. Each of these measures something real but at a significant remove from the actual risk object — informed study participants who know they're rating persuasive content are not equivalent to unsuspecting targets of a real scam or influence campaign, and individual-message persuasiveness is only one input (and arguably not the limiting one) into whether a coordinated influence operation succeeds at scale, which depends heavily on distribution, targeting, platform dynamics, and network effects that have nothing to do with the language model's raw persuasive skill per se.

The honest conclusion (my own assessment, consistent with how cautiously both major labs' public documents tend to discuss this category relative to cyber and bio) is that persuasion/manipulation uplift evals are the least mature of the four major categories discussed in this file, in the specific sense that the field has not converged on anything resembling a validated, widely-trusted measurement instrument the way CTF benchmarks or expert-panel bio-uplift protocols at least represent partial, if imperfect, convergence for their categories.

### 4.3 Scam/fraud uplift is a somewhat more tractable sub-case, and worth separating out

Mass influence-operation uplift and individually-targeted scam/fraud uplift get bundled into "persuasion" in most framework documents, but they are worth separating analytically, because scam/fraud uplift admits slightly better proxy measurement than the mass-influence case, for reasons specific to its structure:

- **The target behavior is narrower and closer to independently checkable.** "Does this message get a rated evaluator (standing in for a target) to take a specific, defined action" — click a link, send payment details, continue a conversation with a simulated scammer persona — is a narrower, more checkable outcome than "did this shift a population's aggregate political belief," even though it still relies on a rated proxy rather than a real victim. Red-teaming setups that have a model attempt to carry out a scripted fraud scenario (e.g., a simulated romance-scam or business-email-compromise conversation) against an informed, consenting rater playing a target role, and score whether the rater judges the attempt as convincing/would-be-effective, are a more direct proxy for real-world fraud uplift than anything currently available for mass influence operations, precisely because individual-target fraud does not depend on the distribution-network and platform-dynamics factors that dominate whether a mass influence campaign actually succeeds.
- **It is still not a clean eval.** The rater is not a real, unsuspecting victim and knows they are evaluating a scripted scenario, which caps how much the result can be extrapolated to a genuine deception attempt against someone with no reason to be suspicious. And "the rater judged this as convincing" is still a subjective, judgment-laden score, not an objective checkable outcome the way flag-capture is for cyber.
- **This is why scam/fraud uplift evals, where they are run at all, tend to look more like a scaled-down, less-institutionally-heavy version of the bio-red-teaming pattern (structured scenario, informed rater/evaluator judgment, no real victims) than like a CTF-style automated check** — a reasonable inference from the structure of the problem, though the specific extent to which any given lab actually runs dedicated scam/fraud red-teaming distinct from general harmlessness evaluation is not something this file can confirm from public sources.

## 5. The core methodological challenge: testing without creating uplift

Every category above has a version of the same underlying problem, and it is worth stating in general form because it is the single most staff-relevant methodological point in this file: **the act of running the evaluation can itself constitute or produce the harm the evaluation exists to detect.**

Concretely: a red-teaming exercise whose purpose is to find out whether a model can help produce a viable pathogen-synthesis route can, if it succeeds, produce exactly that route as a work product — a validated, written-down synthesis pathway that did not exist in usable form before the eval was run, now sitting in some lab's internal records. A cyber red-team exercise that successfully chains a model-assisted exploit against a real target has, in the course of testing, actually compromised that target. Publishing a detailed writeup of a persuasion eval's most effective prompting strategies functions as a how-to guide for exactly the manipulation techniques the eval was checking for. The eval is not a passive measurement in the way a benchmark run is passive — it is an active attempt to elicit the capability, and a successful elicitation attempt is, definitionally, an instance of the capability being exercised.

The mitigations used in practice (drawing on labs' public framework documents and general public statements about their processes; specific implementation details are generally not disclosed) cluster into three approaches:

- **Comparing against an informed baseline rather than reporting absolute capability.** Instead of asking "can the model do X" (a question whose answer, if yes, is itself a hazardous fact), the eval is framed as "how much faster/better/more reliably does an already-resourceful actor do X with the model versus without it" — the object of interest is the delta, and in some designs the absolute achieved outcome can be capped, redacted, or never fully assembled end-to-end even during testing (e.g., testing individual sub-steps of a chain in isolation rather than running the full chain to a real, disclosable endpoint).
- **Restricting the evaluation environment.** Cyber evals run against sandboxed, deliberately-constructed, non-production targets rather than live infrastructure wherever possible. Bio/chem evals are reported to be conducted under controlled conditions — sometimes through partnerships with government biosecurity bodies or in facilities with appropriate controls — rather than as open-ended, unsupervised red-teaming, and are structured to avoid actually completing or validating a real wet-lab pathway (e.g., testing whether a model can answer troubleshooting-style questions about a synthesis route without the red-team actually attempting the synthesis to confirm the model was right). ARA evals are run in instrumented, monitored sandbox environments where any successful "exfiltration" or "resource acquisition" is contained and reversible by design, not a real-world unauthorized action.
- **Restricting publication rather than restricting the test itself.** Aggregate results, threshold-gating conclusions, and methodology descriptions (what kind of eval was run, at what rigor, by whom) are published; the specific task content, prompts, and successful-elicitation transcripts generally are not, for the bio/chem and, to a lesser extent, cyber categories specifically. This is the direct information-hazard analog of responsible disclosure norms in traditional security research, extended to a domain (bio/chem) that has no comparable pre-existing disclosure culture to borrow from.

None of these mitigations is fully satisfying from a scientific-rigor standpoint — every one of them trades some reproducibility or external verifiability for reduced hazard, and reasonable people can and do disagree about whether any given lab has struck that balance well in any specific case, precisely because the details needed to fully evaluate the tradeoff are the same details being withheld.

### 5.1 Sketch: an uplift-vs-baseline eval harness

The structural pattern underlying nearly all of the mitigations above — measure a delta between an informed baseline condition and a model-assisted treatment condition, rather than an absolute score — is general enough to sketch as pseudocode. This is a schematic illustration of the *design pattern*, not a description of any specific lab's actual harness, which is not public.

```text
# Uplift eval harness sketch (illustrative structure, not any lab's actual implementation)

def run_uplift_evaluation(task_suite, model, expert_pool, n_participants_per_arm):
    results = []

    for task in task_suite:                       # e.g., sub-steps of an attack/synthesis pathway
        # Randomize resourceful, pre-screened participants (or expert red-teamers
        # standing in for a threat-actor profile) into two arms.
        baseline_arm, treatment_arm = randomize_participants(
            pool=expert_pool, n=n_participants_per_arm, task=task
        )

        # Baseline arm: realistic actor profile, normal resources (internet
        # access, public literature), no model access.
        baseline_outputs = [
            run_attempt(participant, task, tools=task.baseline_tools)
            for participant in baseline_arm
        ]

        # Treatment arm: identical actor profile and resources, PLUS access
        # to the model under evaluation (with best-effort elicitation --
        # see Section 6 -- so the result is a meaningful upper bound).
        treatment_outputs = [
            run_attempt(participant, task, tools=task.baseline_tools + [model])
            for participant in treatment_arm
        ]

        # Grading is domain-expert judgment, not string match or unit tests,
        # for every category except (partially) cyber CTF-style tasks.
        # Graders are blinded to arm assignment where feasible, to reduce
        # the risk of the grader's own expectations biasing the score.
        baseline_scores = [blind_expert_grade(o, rubric=task.rubric) for o in baseline_outputs]
        treatment_scores = [blind_expert_grade(o, rubric=task.rubric) for o in treatment_outputs]

        uplift = aggregate_delta(
            treatment_scores, baseline_scores,
            metrics=["success_rate", "time_to_completion", "output_quality"],
        )

        results.append(TaskResult(task=task, uplift=uplift, n=n_participants_per_arm))

        # Containment: nothing about this loop should be allowed to reach a
        # real, disclosable, dangerous endpoint (a live exploited target, a
        # validated wet-lab-confirmed synthesis route, a real exfiltrated
        # weight copy outside a monitored sandbox). Enforce that constraint
        # at the task/environment level, not as an afterthought on results.

    aggregate_uplift = combine_across_tasks(results)
    threshold_flag = aggregate_uplift.exceeds(task_suite.risk_threshold)

    return EvalReport(
        aggregate_uplift=aggregate_uplift,
        threshold_flag=threshold_flag,
        # Published artifact intentionally excludes per-task prompts/transcripts
        # for hazard-flagged categories; methodology and aggregate numbers only.
        publishable_summary=redact_task_content(results),
    )
```

The details that make this pattern *work* in practice — how the baseline actor profile is chosen and justified as realistic, how blinding is actually achieved when expert graders can often tell from context which arm they're looking at, how many participants are enough for a statistically meaningful delta on a rare/expensive-to-run task, how containment is actually enforced rather than just asserted — are all genuinely hard, unresolved-in-general engineering and methodology problems, not solved details being omitted for brevity.

### 5.2 Statistical power and inter-rater reliability are harder here than almost anywhere else in eval design

The pseudocode's `n_participants_per_arm` parameter deserves its own callout, because the categories in this file are close to a worst case for statistical power among evaluation designs used anywhere in the field. Standard capability benchmarks get statistical stability essentially for free: run the model against a few thousand MMLU questions and the resulting accuracy estimate has a tight confidence interval, because the marginal cost of one more question is a single cheap forward pass. Every one of the properties that make dangerous-capability evals hard to run also makes them hard to run *at scale*:

- **Expert graders and expert red-teamers are a scarce, expensive resource** — a handful of qualified virologists or offensive-security specialists willing and cleared to participate in this kind of trial is a fundamentally different sample-size regime than a crowdworker pool of thousands, and it directly limits how many independent baseline/treatment attempts can be run per task.
- **Each trial can be slow and expensive to execute**, especially for bio/chem scenarios structured around multi-step troubleshooting dialogues or multi-hour cyber-intrusion attempts, which further caps the number of repetitions feasible within a reasonable evaluation timeline before a deployment decision is due.
- **Inter-rater reliability is a live concern, not a formality**, precisely because grading requires subjective expert judgment (Section 7's point about grading noise). Two qualified experts can disagree about whether a given model output represents genuine technical progress toward a synthesis route, or about whether an exploit chain "really" succeeded versus succeeded only in a way that would not transfer outside the sandbox — and with few graders available, there is limited ability to average out individual grader idiosyncrasy the way a large crowdworker pool would.
- **The practical consequence is that dangerous-capability eval results often carry wider, less-formally-reported uncertainty than a capability benchmark leaderboard number would suggest at a glance**, even when the point estimate (a specific uplift percentage, a specific pass rate) is reported crisply. A staff-level treatment of any specific published uplift number should default to asking about sample size and inter-rater agreement before treating the number as precise, in the same way a well-calibrated reader treats a benchmark score's confidence interval as part of the number rather than an afterthought (see `..\05_Evaluation_Methods\007_Statistical_Rigor_In_LLM_Evaluation.md` for the general statistical-rigor treatment this observation borrows from).

## 6. The elicitation problem

A measured score on a dangerous-capability eval is a **lower bound** on the model's latent capability, not a ceiling, and this is arguably the single most important methodological fact to internalize about this entire field.

The reason is structural: a model's observed behavior on any given prompt is a function of both its underlying capability and how well that capability was elicited by the specific prompt, scaffolding, and context it was given. A model might genuinely lack a dangerous capability, or it might possess the capability but fail to display it because of a poorly-phrased prompt, an absent tool it would have needed, a refusal triggered by safety training that a differently-phrased request would have bypassed, or an absence of the multi-turn back-and-forth needed to actually walk through a hard multi-step task. From the outside, a failed eval attempt looks identical in both cases — the model produced a bad or refused answer — but the correct policy conclusion (this model is safely below the threshold, versus this model has the capability but wasn't drawn out) is completely different depending on which explanation is true.

This is why labs describe investing in **best-effort elicitation** before drawing a below-threshold conclusion, rather than testing the model "as shipped" and taking a single failed attempt at face value:

- **Removing safety-training-induced refusals for the purpose of the test.** Testing may use a helpful-only or safety-training-relaxed variant of the model specifically so that a refusal (a training artifact) is not mistaken for a capability ceiling (a fact about the model's underlying knowledge/skill) — the eval wants to know what the model could do if a bad actor somehow got it to try, not what the publicly deployed, refusal-trained model does by default when asked nicely.
- **Fine-tuning on eval-adjacent data.** If a plausible bad actor could fine-tune a model (via an API that offers fine-tuning, or via open weights) to be better at the target task, then the eval's elicitation effort should include a fine-tuned variant, not just the base checkpoint, because "what a sufficiently motivated actor could get this model to do" — not "what it does with zero effort" — is the risk-relevant quantity.
- **Providing tools and agentic scaffolding.** Code execution, internet browsing, retrieval, and multi-step agent loops can unlock capabilities that a bare single-turn text completion never displays, so elicitation testing generally includes giving the model the same kind of tool access a determined real-world user would plausibly assemble.
- **Expert-crafted prompting and multi-turn interaction.** A domain expert who knows how to phrase a question, break a hard problem into sub-steps, and follow up on a weak initial answer will draw out more of a model's latent capability than a single naive prompt — so red-teamers doing elicitation work are themselves expected to bring genuine skill at prompting/interacting with the model, not just at judging the domain.

This is what makes dangerous-capability evals structurally different from a benchmark like MMLU or HumanEval, where the standard practice is close to "run the model roughly as it will actually be deployed, with a fixed, simple prompt template, and report the score" — because for a standard benchmark, the deployed behavior *is* the object of interest (users will interact with the shipped model, not a fine-tuned, unrestricted, expert-scaffolded variant of it). For dangerous-capability evals, the deployed default behavior is explicitly *not* the object of interest on its own; the object of interest is closer to a ceiling estimate of what the model's weights could be made to do under realistic worst-case effort, of which the as-shipped behavior is only a weak, easily-defeated lower bound. Concluding "below threshold" is therefore a claim of the form "even under our best elicitation effort, we could not draw out this capability" — and the strength of that claim is only as good as the elicitation effort actually invested, which is inherently hard to prove was exhaustive.

### 6.1 "How much elicitation is enough" has no principled stopping rule

A subtler problem sits one layer beneath best-effort elicitation, and it is worth naming explicitly because it is the kind of thing a staff-level answer should raise unprompted: proving a capability *exists* only requires one successful elicitation attempt, but proving a capability *does not exist* (or does not exceed a threshold) requires showing that no elicitation attempt within some effort budget succeeds — and there is no principled way to know when that budget has been exhausted rather than merely under-explored. This is a fundamental asymmetry in the evidence, structurally similar to the difficulty of proving a negative anywhere else in empirical science, but sharper here because the "search space" being explored (possible prompts, scaffolds, fine-tuning recipes, multi-turn strategies) is enormous and not enumerable.

In practice, labs manage this asymmetry rather than resolve it: elicitation effort is scaled to the stakes (a category close to a threshold gets materially more red-teaming effort than one that scores far below it on initial passes), elicitation techniques are periodically refreshed as new prompting/scaffolding/fine-tuning tricks become known in the broader field (an elicitation effort that was state-of-the-art a year ago may understate current capability simply because better elicitation methods now exist), and post-deployment monitoring is treated as a backstop for the possibility that pre-deployment elicitation missed something (covered elsewhere in this module) rather than as a redundant, unnecessary check. None of this amounts to a proof that a "below threshold" conclusion is correct in any strong sense — it is closer to "we looked hard, using the best techniques we currently know, and did not find it," which is a meaningfully weaker statement than a benchmark score, and a staff-level answer should be comfortable saying so rather than implying elicitation effort ever fully closes this gap.

## 7. Structural differences from standard capability benchmarks, summarized

Pulling the threads from Sections 1–6 together, dangerous-capability evals differ from standard capability benchmarks along essentially every methodological axis that makes a benchmark trustworthy and easy to use:

- **Who grades it.** Standard benchmarks use automated graders (exact match, unit tests, sometimes LLM-as-judge) or, at most, non-expert crowdworkers following a written rubric. Dangerous-capability evals require domain-expert red-teamers — security researchers, virologists, biosecurity specialists — because grading requires exactly the specialized judgment the eval is probing for, and because non-experts cannot be trusted to safely recognize or handle a genuinely hazardous result even if they could technically score it.
- **What can be published.** MMLU, HumanEval, and their peers are openly published, versioned, and reproducible by any outside party with API access or open weights — this is a large part of what makes them trustworthy as shared reference points across the field. Dangerous-capability eval task content, and often the detailed results, are frequently not publishable at all, for the information-hazard reasons in Section 5 — which means the field has comparatively little of the cross-checking, replication, and outside scrutiny that openly published benchmarks receive almost for free.
- **How clean the grading signal is.** String match and unit-test-style grading is close to noise-free. LLM-as-judge grading (covered elsewhere in this module) introduces judge bias and inconsistency but is at least automatable and cheap to re-run. A human domain expert's judgment call about whether a multi-step exploit chain "worked," or whether a synthesis-route answer represents genuine technical progress, is inherently noisier, harder to calibrate across different expert graders, and expensive to obtain multiple independent ratings of for statistical confidence.
- **Who gets to judge whether a threshold was crossed.** A capability benchmark leaderboard has no analog to "and therefore, based on this score, deployment must be restricted" — the stakes of a dangerous-capability eval result are directly tied to a lab's own deployment decisions for its own model, which creates an obvious structural conflict of interest if the lab is also the sole judge of its own eval results. This is the main reason the field has moved toward third-party and government-affiliated evaluation as a partial check — organizations like METR, and government bodies such as the UK AI Security Institute and the US Center for AI Standards and Innovation (the renamed former US AI Safety Institute), have publicly conducted or been given pre-deployment access for independent evaluation of frontier models from multiple labs (this general arrangement is confirmed via labs' public model/system-card acknowledgments and the relevant government bodies' own public statements; the full scope, access level, and results of any specific engagement are generally not fully public). The deeper institutional questions around these government-partnership arrangements — what access they're actually given, how binding their conclusions are, and how this is likely to evolve — are covered in more depth elsewhere in this module rather than repeated here; the point worth holding in this file is narrower: cross-lab or third-party calibration exists specifically *because* self-grading a threshold that gates your own product is a poor governance structure on its face, independent of whether any particular lab's internal process is conducted in good faith.

### 7.1 A balanced note: false positives are a real cost too, not just false negatives

Most discussion of this topic (including most of this file so far) is naturally weighted toward the failure mode of under-detecting a real dangerous capability — a false negative, where an eval concludes "below threshold" on a model that actually has the capability. That failure mode is rightly the more catastrophic one and deserves the greater share of attention. But a genuinely even-handed treatment should also name the opposite failure mode explicitly: an eval that over-flags, concluding a model has crossed a threshold when it has not, or when the measured "uplift" is largely an artifact of a poorly-chosen baseline or noisy expert grading (Section 5.2) rather than a real capability gap. This is not a hypothetical concern — given everything in this file about how noisy expert grading is, how uncertain baseline characterization is (Section 2.3), and how much judgment is embedded in every step of the harness in Section 5.1, false positives are a live possibility, not a remote edge case.

False positives are not free: they can delay or restrict deployment of a model's genuinely beneficial capabilities (a model that is better at vulnerability discovery is also better at defensive security work, per Section 1.4; a model that is more capable at biology generally is also more capable at legitimate biomedical research), impose real compute and opportunity costs on the lab, and — if they happen often enough or visibly enough — risk undermining the credibility of the entire threshold-gating apparatus in the eyes of both the research community and outside stakeholders, making future genuine threshold crossings easier to dismiss as "probably another false alarm." A staff-level treatment of this topic should be able to hold both costs in mind simultaneously — the asymmetric badness of a false negative in this specific domain (mass-casualty potential) justifies erring toward caution at the margin, but "err toward caution" is not the same as "false positives don't matter," and a mature risk-governance process has to budget for and try to minimize both error types, not treat the whole exercise as costless in one direction.

## 8. Honest state of the field

It would overstate the maturity of this area to describe it as a settled methodology with known-good practices that labs merely execute. A calibrated summary, as of the current state of public information:

- **There is no fully validated, cross-lab-agreed-upon dangerous-capability eval suite.** Each major lab runs its own internal evals, described only partially in public documents, using its own task sets, its own grading rubrics, and its own thresholds — and there is no public evidence of a shared, jointly-validated instrument that multiple labs have agreed produces comparable, trustworthy numbers across organizations.
- **Results are not straightforwardly comparable across labs' internal evals**, because the tasks, elicitation effort, grading rubric, and baseline-actor assumptions all differ and are, in the bio/chem case especially, largely undisclosed — a claim like "Lab A's model scored below threshold on cyber-offense uplift" and "Lab B's model scored below threshold on cyber-offense uplift" are not necessarily measuring the same thing to the same standard, even when both labs are acting in good faith.
- **Standardization work is genuinely active and ongoing, not finished.** There is real, visible movement toward more standardized bio- and cyber-uplift evaluation methodology — through organizations like METR publishing more of their own evaluation methodology, government AI safety institutes running cross-lab evaluations under more consistent protocols, and biosecurity-focused research organizations engaging more formally with frontier labs — but this is a moving target, and any specific claim in this file about "current best practice" should be read as time-bound to roughly the mid-2020s state of the field rather than as a description of a settled discipline. This is an area where checking for more recent developments before an interview is genuinely worthwhile, more so than for most other topics in this module.
- **The tension between rigorous, reproducible science and avoiding a hazard-enabling roadmap is unresolved, and plausibly unresolvable in the strong sense.** Ordinary scientific practice wants open methodology, published task sets, independent replication, and peer review of grading rubrics. The information-hazard concerns specific to bio/chem (and to a lesser degree cyber and ARA) evals actively cut against every one of those norms. There is no known design that gets you both full reproducibility and zero information-hazard risk simultaneously for this category of eval — every mitigation in Section 5 is a point on a tradeoff curve, not a resolution of the underlying tension, and it is reasonable to expect this tension to persist indefinitely rather than be solved by some future methodological innovation, precisely because the two goals are in direct conflict for this specific kind of claim (as opposed to, say, ordinary capability benchmarking, where openness has no comparable offsetting cost).

A staff-level answer on this topic should reflect that state honestly: name the categories and the general shape of the methodology precisely, but resist any framing — from an interviewer or from your own answer — that implies this is solved, standardized science. It is closer to an early-stage applied field improvising defensible practice under a genuinely hard constraint (you cannot fully validate your instrument in public without undermining the reason you built it), and saying so directly is more accurate, and more staff-like, than reciting eval names as if they were a mature, agreed-upon standard.

## 9. Confirmed facts versus speculation, consolidated

This file flags most claims inline, but it is worth pulling the two lists apart explicitly, since conflating "publicly confirmed by a lab" with "reasonable analytical inference" is exactly the kind of imprecision a staff-level answer should avoid.

**Confirmed (via labs' published policy documents, model/system cards, and public statements):**

- Anthropic's Responsible Scaling Policy (with AI Safety Level thresholds) and OpenAI's Preparedness Framework both exist as named, published documents that define discrete capability thresholds across named risk categories, tied to deployment-governance decisions.
- The categories tracked by these frameworks substantially converge on cyber-offense, biological/chemical (CBRN-adjacent) weapons uplift, and model autonomy, with OpenAI's framework additionally naming persuasion as a top-level tracked category.
- Both Anthropic and OpenAI have publicly stated that they conduct structured uplift/red-teaming evaluations for the bio/chem category using external domain experts (virologists, biosecurity researchers, and related specialists), rather than relying on generalist crowdworkers.
- METR is a third-party organization publicly acknowledged, in multiple labs' model and system cards, to have conducted autonomy/ARA-relevant capability evaluations on frontier models pre-deployment.
- METR has published research reporting an exponential growth trend in the length (human-time-equivalent) of tasks frontier models can complete autonomously across successive model generations — a general agentic-capability trend metric, distinct from ARA threshold evaluation specifically, as Section 3.4 discusses.
- Government-affiliated bodies — the UK AI Security Institute and the US Center for AI Standards and Innovation (the renamed former US AI Safety Institute) among them — have publicly conducted or been given some form of pre-deployment access to evaluate frontier models from multiple labs.
- CTF-style and CTF-derived benchmarks (e.g., Cybench-style suites) are referenced in labs' own model/system-card reporting as a component of cyber-offense capability evaluation.
- Labs' public reporting on bio/chem uplift evaluation results is characteristically limited to qualitative or coarsely-quantified conclusions and methodology descriptions, without publishing detailed task content or transcripts.

**Speculation or analytical inference (mine, clearly distinguishable from the above and flagged as such at first mention in each section):**

- The specific claim that CTF benchmark gains translate into a specific, quantified degree of real-world offensive uplift — this gap is argued from first principles (CTFs are solvable-by-design, unmonitored, and non-adversarially-defended relative to real targets), not measured by any published study cited here.
- The reasoning for why radiological/nuclear risk receives comparatively little dedicated LLM-uplift-eval attention relative to bio/chem (the physical-versus-informational-bottleneck argument in Section 2.5) is my own analytical inference from the observable emphasis in public framework documents, not a stated rationale from any lab.
- The distinction between capability-oriented and propensity-oriented ARA probe designs, and the illustrative sandbox task sketched in Section 3.3, are constructed to make a real methodological distinction concrete — they are not descriptions of any specific lab's actual task content, which is not public.
- The claim that METR's published time-horizon trend is a leading indicator for, but not equivalent to, ARA-threshold capability (Section 3.4) is my own analytical connection between the two bodies of work, not a claim made directly by METR or by either lab.
- Any characterization of the relative internal prioritization or resourcing given to persuasion evaluation versus the other three categories at either lab is inferred from the relative depth of public framework discussion, not from a disclosed resourcing figure.
- The eval-harness pseudocode in Section 5.1 is an illustrative design pattern constructed for this file, not a description of any lab's actual internal implementation.
- The false-positive/false-negative balance discussion in Section 7.1 is original analysis applying general statistical-decision-theory reasoning to this domain, not a claim about how any specific lab weighs the two error types internally.
- All claims in Section 8 about the current state of standardization efforts being "active" and "not finished" reflect the field's publicly visible trajectory as of the time this file was written, and should be treated as time-bound rather than a permanent characterization.

This split is the discipline worth carrying into an interview room: be precise and confident about the small, well-documented set of things labs have actually said about how they test for dangerous capabilities, and be equally clear — without hedging it into vagueness — about how much of the rest of a complete technical picture is reasonable inference filling gaps that public disclosure has not yet closed.
