# Training Objectives and Pretraining

## The causal language modeling objective

Everything a base LLM knows before any fine-tuning is a consequence of a single, almost embarrassingly simple training objective: given some text, predict the next token. What makes this worth a deep treatment is not the objective's complexity — it has essentially none — but the fact that optimizing it at sufficient scale, over sufficiently broad data, turns out to produce behavior (translation, arithmetic, code synthesis, multi-step reasoning) that nothing in the objective explicitly asked for. Before getting to that emergence question, it's worth being precise about the objective itself, because the mechanics matter for understanding things like why training is so parallelizable, what "teacher forcing" means, and why loss is reported in the units it is.

### The chain rule factorization

A sequence of tokens `x_1, x_2, ..., x_T` has some true joint probability `P(x_1, ..., x_T)` under the real distribution of language. This joint distribution is intractable to model directly — there is no way to parameterize a function over arbitrary-length sequences of joint probabilities directly — but the chain rule of probability lets us factorize it exactly, with no approximation, into a product of conditional next-token probabilities:

```
P(x_1, x_2, ..., x_T) = P(x_1) * P(x_2 | x_1) * P(x_3 | x_1, x_2) * ... * P(x_T | x_1, ..., x_{T-1})
                       = product_{t=1}^{T} P(x_t | x_1, ..., x_{t-1})
```

This factorization is the entire architectural justification for a decoder-only, causally-masked transformer: if you can build a model `f_theta` that outputs a good estimate of `P(x_t | x_1, ..., x_{t-1})` for every position `t` in a single forward pass — which is exactly what causal (autoregressive) masking inside self-attention achieves, by construction preventing position `t` from attending to any position after it — then that single model, applied autoregressively at inference time (feed its own sampled output back in as the next input), defines a full generative model over arbitrary-length sequences. Nothing about the architecture needs to change between training and generation; the causal mask simply guarantees that the "prediction for position `t`" that comes out of the model during training never had access to information from position `t` or later, so it is a mathematically honest estimate of the conditional the chain rule calls for. (The architectural reasoning for *why* decoder-only causal transformers became the standard generative architecture, as opposed to encoder-decoder or other designs, is covered in the architecture-focused files in this folder — this file assumes that choice and focuses on the training objective built on top of it.)

### Cross-entropy loss and teacher forcing

Training turns this factorization into a concrete loss function. At every position `t`, the model outputs a probability distribution over the entire vocabulary (via a final linear projection to vocabulary size followed by softmax), and we compare that distribution to the actual next token that appeared in the training data, using cross-entropy loss. Averaged over a sequence of length `T`, the per-sequence loss is:

```
L = - (1/T) * sum_{t=1}^{T} log P_theta(x_t | x_1, ..., x_{t-1})
```

This is simply the negative log-likelihood the model assigns to the real, observed continuation, averaged per token — and it is also, up to a constant factor of `ln(2)`, the same quantity commonly reported as **perplexity** (`perplexity = exp(L)`), which is why perplexity and cross-entropy loss are used almost interchangeably when discussing pretraining progress.

The practical trick that makes this trainable efficiently is **teacher forcing**: rather than generating a token, feeding it back into the model, generating the next one, and so on (which would make training sequential and horrifically slow, and would also mean early mistakes compound and corrupt every later target), the model is instead always shown the true, ground-truth previous tokens as its input context at every position, regardless of what it would have predicted itself. Concretely, given an input sequence, you construct the training example by shifting it by one position: the model's input at position `t` is `x_1...x_t`, and its target label for that position is `x_{t+1}`. Because causal masking already guarantees position `t`'s output only depends on `x_1..x_t`, this shifting means a *single* forward pass over an entire sequence simultaneously produces a training signal for predicting every token in that sequence from its true prefix — you get `T` next-token prediction training examples for the computational cost of one forward pass, which is a huge efficiency win and the reason pretraining throughput scales as well as it does on modern hardware.

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

def causal_lm_loss(model, input_ids, pad_token_id=-100):
    """
    Minimal illustration of the shifted-target cross-entropy setup used to
    train a decoder-only causal LM.

    input_ids: (batch, seq_len) token ids for a batch of training sequences
    """
    # Teacher forcing: the model sees the true tokens 1..T-1 as input...
    inputs = input_ids[:, :-1]
    # ...and its targets are simply those same tokens shifted one position right.
    targets = input_ids[:, 1:]

    logits = model(inputs)                       # (batch, seq_len-1, vocab_size)
    logits = logits.reshape(-1, logits.size(-1))  # (batch*(seq_len-1), vocab_size)
    targets = targets.reshape(-1)                 # (batch*(seq_len-1),)

    # ignore_index lets us mask out padding tokens so they contribute no loss
    loss = F.cross_entropy(logits, targets, ignore_index=pad_token_id)
    return loss


def training_step(model, optimizer, batch_input_ids):
    optimizer.zero_grad()
    loss = causal_lm_loss(model, batch_input_ids)
    loss.backward()
    optimizer.step()
    return loss.item()
```

Notice there is nothing in this loop that resembles a labeled dataset in the traditional supervised-learning sense — the "labels" are just the input text itself, shifted by one position. This is what makes causal language modeling **self-supervised**: every token of raw text you can obtain is simultaneously an input and a label, which is precisely why it scales to internet-scale corpora in a way that any objective requiring human-annotated labels never could.

### Why this objective won over alternatives

It is worth briefly contrasting this with masked language modeling (MLM), the BERT-style objective where a small fraction of tokens in a sequence are hidden and the model must predict them using context from *both* directions (encoder-style, bidirectional attention). MLM produces excellent contextual representations for understanding tasks — this is why BERT and its descendants dominated the "encode text into a representation for classification/retrieval" niche — but it is a fundamentally awkward fit for open-ended generation, for a structural reason: an MLM has no natural, well-defined way to generate a variable-length sequence token by token, because its training never taught it a left-to-right, causally-consistent generative process at all; it only ever learned to fill in the blanks in an already-complete sequence. Causal LM, by contrast, directly trains the exact inference-time behavior it will be asked to perform (predict the next token given everything so far, then repeat), which is why decoder-only causal architectures became the standard for general-purpose generative LLMs, while encoder-style MLM objectives remain more common in the embedding/retrieval space than in generation. This distinction is also why the field converged on "decoder-only, causal LM" as essentially the default LLM recipe (GPT, Llama, Mistral, Claude, and effectively every other current-generation general-purpose model) rather than the encoder-decoder designs (like the original T5) that were still common in the earlier transfer-learning era.

## The pretraining data pipeline

The objective above is what the model optimizes, but what it actually *learns* is overwhelmingly determined by the data it is optimized against — and building that dataset is, in practice, one of the largest engineering efforts behind any frontier model, arguably rivaling the modeling work itself. The pipeline below describes the stages nearly every serious pretraining corpus goes through, in roughly the order they're typically applied.

### Web-scale crawling

The base layer of virtually every large pretraining corpus is **Common Crawl**, a public, continuously updated archive of raw web page snapshots totaling many petabytes, going back to 2008. Common Crawl on its own is extremely noisy — it includes boilerplate, spam, machine-generated text, adult content, non-natural-language content, and enormous amounts of low-information text — so essentially no serious pretraining run uses it directly; it is always the starting point for the filtering pipeline described next, not the end product. Some model builders supplement or replace parts of Common Crawl with their own targeted crawling, but the general shape — start from a broad, noisy web crawl and progressively refine it — is close to universal.

### Quality filtering

Because raw web text is dominated by low-value content, every serious pipeline applies quality filters to bias the corpus toward text that looks like it will actually help the model. Two techniques dominate. The first is **classifier-based filtering**: train a lightweight classifier (often a simple linear or small neural model over n-gram or embedding features) to distinguish "reference-quality" text — commonly text sampled from Wikipedia, curated book collections, or other high-editorial-standard sources — from generic web text, and then apply that classifier across the crawl, keeping only documents that score highly, or using the score to weight how heavily a document is sampled during training. This is the technique behind GPT-3's filtering of Common Crawl (using a classifier trained against WebText-like and Wikipedia-like positive examples) and is a standard component of most subsequent pipelines. The second is **perplexity filtering**: score each candidate document under a smaller, already-trained language model (often trained specifically on a small high-quality reference corpus), and discard documents that receive either extremely high perplexity (typically nonsensical, boilerplate-heavy, or non-linguistic text that no reasonable language model fits well) or, in some pipelines, suspiciously low perplexity (which can indicate degenerate, highly repetitive text). Both techniques are proxies for the same underlying goal — approximate "does this document resemble the kind of text we want the model to learn its distribution from" without requiring humans to read the whole corpus — and most production pipelines combine several such filters (quality classifiers, perplexity filters, plus simple heuristic rules on things like average line length, symbol-to-word ratio, or the presence of boilerplate phrases) rather than relying on just one.

### Deduplication

Raw web crawls contain an enormous amount of duplicate and near-duplicate content — the same article mirrored across many domains, boilerplate templates repeated across thousands of pages, quoted text reproduced verbatim across forums, and so on. Duplicate data hurts pretraining in two distinct ways worth separating clearly. First, it is simply a waste of compute and an opportunity cost: every token spent re-training on content the model has already seen many times is a token not spent on new information, and papers studying this (notably work from Lee et al., "Deduplicating Training Data Makes Language Models Better") have shown measurable perplexity and downstream-quality improvements from deduplication at fixed compute budget. Second, and more concerning, heavily duplicated content is strongly correlated with **memorization** — a model is far more likely to be able to regurgitate a passage verbatim if it appeared many times in training, which creates both a privacy/IP concern and a benchmark-contamination risk (see decontamination below).

Deduplication is applied at two granularities. **Exact deduplication** removes documents (or chunks) that are byte-for-byte identical, typically implemented efficiently via hashing (compute a hash of each document or chunk and drop exact hash collisions). **Fuzzy (near-duplicate) deduplication** is the harder and more consequential half of the problem, since it needs to catch documents that are almost but not exactly identical — reformatted, partially edited, or reproduced with minor boilerplate differences. The standard technique here is **MinHash combined with Locality-Sensitive Hashing (LSH)**: represent each document as a set of overlapping n-grams (shingles), compute a compact MinHash signature that approximates the Jaccard similarity between any two documents' shingle sets, and then use LSH to efficiently bucket documents so that only likely-similar pairs (those falling in the same LSH bucket) need to be compared directly, rather than requiring an intractable all-pairs comparison across a corpus with hundreds of billions of documents. Documents whose estimated similarity exceeds a chosen threshold are treated as near-duplicates, and all but one (or a sampled few) are dropped.

```python
def minhash_signature(shingles, num_hashes, hash_fns):
    """
    Conceptual illustration of a MinHash signature: for each of `num_hashes`
    independent hash functions, the signature stores the MINIMUM hash value
    observed across all shingles in the document. Two documents that share
    many shingles will, with high probability, agree on many of these minima --
    this is what lets MinHash approximate Jaccard similarity without ever
    computing the full set intersection directly.
    """
    signature = []
    for hash_fn in hash_fns[:num_hashes]:
        min_hash = min(hash_fn(shingle) for shingle in shingles)
        signature.append(min_hash)
    return signature


def estimated_jaccard_similarity(sig_a, sig_b):
    matches = sum(1 for a, b in zip(sig_a, sig_b) if a == b)
    return matches / len(sig_a)
```

### Toxic content and PII filtering

Alongside filtering for general quality, pretraining pipelines run a separate pass targeting content that is harmful or sensitive for reasons that have nothing to do with how well-written it is. Toxicity filtering uses classifiers (often similar in spirit to the quality classifiers above, but trained specifically on labeled examples of hate speech, harassment, and extreme content) or keyword/pattern heuristics to identify and remove text the labs do not want the base model absorbing as a "normal" statistical pattern to imitate — with content sexualizing minors treated as an absolute, non-negotiable exclusion in every credible pipeline, not a tunable threshold. Separately, and for a different reason, pipelines run PII (personally identifiable information) detection and scrubbing — pattern-matching and named-entity techniques that find and redact things like email addresses, phone numbers, government ID-like number formats, and home addresses. The concern here is concrete rather than tonal: a model that sees a real person's phone number or address often enough (or, in some documented cases, even just once, if the text is otherwise unusual enough to be memorized) can regurgitate it verbatim to a user at inference time, which is a privacy failure with real legal exposure, not just an aesthetic one. It's worth keeping this pretraining-time filtering conceptually separate from the behavioral safety alignment applied later via instruction tuning and RLHF/DPO (covered in later chapters in this series): this stage controls what the base model is ever statistically exposed to as "normal" text, while alignment training later controls how the already-pretrained model chooses to *behave* when asked something sensitive — the two are complementary, not substitutes for each other, and a model can be perfectly aligned at the behavioral layer while still having absorbed some undesirable statistical associations from imperfectly filtered pretraining data, which is part of why this filtering step is treated as a serious, dedicated stage of the pipeline rather than an afterthought.

### Data mixture design

Once a filtered, deduplicated pool of candidate text exists, pretraining teams make deliberate decisions about the **mixture** — what fraction of training tokens comes from which domain (general web text, Wikipedia, books, academic papers/arXiv, code repositories, forum/QA data like Stack Exchange or Reddit, multilingual text, and so on) — rather than simply training on whatever the natural proportions in a raw crawl would give you. These mixture weights are one of the most consequential and most heavily ablated design choices in pretraining, since domains vary enormously in information density and downstream usefulness per token. A widely cited and fairly well-established finding is that upweighting **code** data, even for a model whose primary intended use is natural language, measurably improves the model's general reasoning ability on non-code tasks — the leading hypothesis is that code's strict logical structure, explicit variable dependencies, and requirement for exact multi-step correctness teaches the model compositional and algorithmic reasoning patterns that transfer to reasoning-heavy natural-language tasks like multi-step word problems, even though the surface form looks completely different. Books and long-form academic writing are typically upweighted for the long-range coherence and discourse structure they contain relative to short web snippets, while low-value web boilerplate is downweighted or capped even after quality filtering, simply to avoid one abundant but low-information domain crowding out everything else. Mixture ratios are usually tuned empirically via smaller-scale ablation training runs (train on candidate mixture A vs. B at small scale, measure downstream benchmark performance, extrapolate) rather than derived from first principles, which ties directly back to the scaling-law methodology described elsewhere in this folder.

### Decontamination

Because pretraining corpora are scraped from the open internet, and because that same internet contains discussion of, solutions to, and sometimes verbatim copies of, popular evaluation benchmarks, there is a real risk that a model's impressive benchmark score partly reflects having seen the benchmark's actual test questions (or very close paraphrases) during pretraining, rather than genuine generalization. **Decontamination** is the practice of explicitly searching the training corpus for text that overlaps with known evaluation benchmarks (typically via n-gram overlap matching between benchmark question/answer text and training documents) and removing matching or near-matching documents before training. This is now considered a baseline responsibility for any lab reporting benchmark numbers, and most major model releases (GPT-4, Llama, Claude, and others) explicitly document a decontamination step in their reported methodology, precisely because undisclosed contamination is one of the most common and most damaging ways benchmark comparisons between models become unreliable.

### Curriculum and data ordering

A more actively debated question is whether the *order* in which training data is presented matters, beyond just the final mixture proportions. Classic curriculum-learning intuition (start easy, progress to hard) has an intuitive appeal, and some pretraining pipelines do apply a form of it — for instance, phased or annealed training schedules where the mixture is deliberately shifted over the course of training, often by increasing the proportion of higher-quality, more curated data (and sometimes decreasing raw web text) in a final phase of training, after the bulk of training has already been done on the broader, larger mixture. This is sometimes justified by an analogy to learning-rate annealing: the coarse, broad statistical structure of language is learned early from abundant, if lower-quality, general data, while a smaller quantity of very high-quality, carefully curated data in the final stretch of training sharpens the model's outputs toward the target distribution more efficiently than mixing it in uniformly throughout. That said, the pretraining community does not have the kind of settled consensus on curriculum ordering that it has on, say, deduplication being beneficial — results are more mixed and more architecture/scale-dependent, and a fair amount of what is publicly known comes from indirect disclosures in model technical reports rather than from controlled, widely-replicated ablation studies, so it is reasonable to treat "does data ordering matter, and how much" as a genuinely open and actively researched question rather than settled practice.

## Why next-token prediction produces emergent capabilities

This is the question that separates people who can recite the training objective from people who actually understand why it matters, and it is worth treating with real care because it is one of the most commonly asked "so what" questions in an LLM interview: if all a model is trained to do is guess the next word, why does it end up able to translate, do arithmetic, write code, and follow multi-step chains of reasoning — none of which were ever directly specified as a training target?

### Compression implies prediction implies understanding

The cleanest version of the argument, sometimes attributed informally to the "compression is intelligence" line of thinking that predates modern LLMs (with roots in information-theoretic arguments made by researchers like Marcus Hutter and popularized in the LLM era by figures like Ilya Sutskever), goes like this: predicting the next token *well*, across an enormous and maximally diverse corpus of human-generated text, is an extraordinarily demanding compression problem. To assign high probability to the correct next token across the full range of contexts present in internet-scale text — a math derivation, a piece of dialogue between characters with different knowledge states, a legal contract, a function in Python, a chemistry explanation — the model cannot get away with memorizing surface statistics; the search space of "what word comes next" is so vast and so context-dependent that the loss can only keep going down by the model internalizing something that functions like the actual underlying generative process behind the text: the syntax of the programming language, the causal and physical structure of the world being described, the mental states of characters in a narrative, the rules of arithmetic. In other words, being good at next-token prediction, at the extreme scale and diversity current pretraining operates at, requires building internal representations that are functionally very close to "understanding" the content, because that is simply a more efficient (higher-compression) strategy for the optimizer to converge on than any shallower alternative. This is why the causal LM objective, despite its apparent simplicity, is not "just" pattern matching in any dismissive sense — at sufficient scale, predicting text well enough is a task whose solution space is dominated by genuinely world-model-like internal representations, because there is no shortcut that gets a comparably low loss across a sufficiently broad and demanding corpus.

This connection between prediction and compression is not just a loose analogy; it is a formal equivalence that predates LLMs by decades. Shannon's source-coding theorem says that the optimal expected code length for encoding data drawn from a distribution, under an entropy coder like arithmetic coding, equals the cross-entropy between your predictive model of that distribution and the true distribution — which means a better next-token predictor is, by construction, a better lossless compressor of the exact same data, and vice versa: you cannot improve one without improving the other, they are the same quantity viewed from two directions. This is precisely the premise behind the **Hutter Prize**, a competition (endowed by Marcus Hutter) that has run for two decades, offering a cash reward for whoever can most effectively losslessly compress a fixed 1GB snapshot of English Wikipedia. The prize's explicit justification is that since Wikipedia's text encodes an enormous amount of the world's structured knowledge, and since compressing text well requires predicting it well, and since predicting a sufficiently rich corpus well requires an internal model that captures the real structure generating that corpus (grammar, facts, causal relationships), progress on compressing Wikipedia is a legitimate, measurable proxy for progress toward general intelligence — not a cute coincidence, but the same underlying mathematical fact that motivates why LLM pretraining loss is a meaningful metric at all. Concretely, when you watch a frontier lab's pretraining loss curve descend from something like 2.5 nats per token toward 1.8 nats per token over a training run, you are watching the model become a measurably better compressor of its training corpus in a bits-per-token sense, and the entire argument of this section is that the specific way it achieves that improvement — by building richer internal representations of grammar, facts, and reasoning structure rather than by any shortcut — is what makes that same descending loss curve correlate so strongly with the qualitative capability jumps observed as models scale.

### In-context learning as an emergent behavior

One of the most striking behaviors this objective produces, never directly trained for, is **in-context learning**: the ability of a model, given nothing but a handful of examples of a task inside its prompt (with no gradient update at all), to perform that task on a new, unseen input. Nothing in the causal-LM loss explicitly rewards "learn a new task from a few examples shown once" — the model was only ever trained to predict the next token of naturally-occurring text. The leading explanation is that natural pretraining text itself contains an enormous number of implicit "few-shot task" structures — worked examples in textbooks, patterns of question-then-answer, repeated formats in structured documents, analogical reasoning across passages — and a model that has become good at next-token prediction across such text has, in the process, had to learn something that functions like a general-purpose "infer the pattern/task implied by the preceding context and continue it accordingly" skill, simply because that skill directly reduces the loss on the vast amount of pretraining text that has this few-shot-like shape. In-context learning is, on this account, not a separate capability bolted onto the model but a direct byproduct of the fact that predicting text well requires being able to rapidly infer and continue whatever local pattern or task structure a given piece of text is exhibiting.

### The emergence debate: real phase transition, or measurement artifact?

A widely discussed 2022 line of work (Wei et al., "Emergent Abilities of Large Language Models") documented that many capabilities — certain arithmetic tasks, multi-step reasoning benchmarks — appear to show a sharp, discontinuous jump in performance as model scale crosses a threshold, going from near-random performance to substantially above-random over a comparatively narrow range of scale, rather than improving smoothly. This was widely interpreted as evidence of genuine phase-transition-like emergence: qualitatively new capabilities suddenly switching on once a model becomes large enough.

A prominent 2023 rebuttal, Schaeffer, Miranda, and Koyejo's "Are Emergent Abilities of Large Language Models a Mirage?", argued that at least a substantial part of this apparent discontinuity is an artifact of the **choice of evaluation metric** rather than a genuine discontinuity in the model's underlying competence. Their argument, at a conceptual level: many of the benchmarks showing "emergent" jumps are scored with metrics that are themselves discontinuous or nonlinear functions of the model's underlying per-token accuracy — for example, an exact-match accuracy metric on a multi-step arithmetic problem requires every single digit and every intermediate step to be correct simultaneously, so even a smooth, gradual improvement in the model's per-token/per-digit accuracy will translate into a probability of getting the *entire* multi-step answer correct that stays near zero for a long time and then rises sharply once per-step accuracy crosses a threshold — purely because of how probabilities of many independent-ish correct steps compound multiplicatively, not because the model's underlying competence changed discontinuously. When the same tasks are instead scored with smoother, partial-credit metrics (token-level or per-step accuracy rather than all-or-nothing exact match), the paper shows many of these "emergent" curves become much smoother and more predictable functions of scale, consistent with the same underlying power-law-like smooth improvement that scaling laws already describe for loss itself.

The honest, currently-most-defensible position (and the one that plays well in an interview, because it shows you understand the actual disagreement rather than parroting one side) is that both things are likely partially true and not mutually exclusive: the underlying quantity the model is actually optimizing — next-token loss / perplexity — improves smoothly and predictably with scale, exactly as the scaling laws describe, with no evidence of literal discontinuity there; but *some* of the downstream, human-relevant capabilities we care about are measured with metrics (exact match, pass/fail, multi-step compounding correctness) that are nonlinear functions of that smooth underlying improvement, and nonlinear functions of smooth curves can absolutely produce sharp-looking transitions in the metric even when nothing discontinuous happened underneath. This does not fully settle whether there is *any* genuine qualitative reorganization happening inside the model at certain scales (that remains an open interpretability question), but it substantially undercuts the strongest, most surprising version of the "capabilities switch on suddenly and unpredictably" claim.

### What an interviewer is actually testing

When an interviewer asks "why does a model trained only to predict the next word learn to reason or translate or write code," they are rarely looking for a one-line answer like "it's just statistics" (which is technically true but explains nothing) or an overly mystical answer about emergent intelligence (which sounds impressive but is not falsifiable). What they are actually testing is whether you can walk through the causal chain: the objective is self-supervised next-token prediction at massive scale and diversity; achieving low loss on that objective across sufficiently broad and demanding data requires the model to internalize structure well beyond surface statistics (the compression argument); some of the resulting internal machinery generalizes into behaviors (like in-context learning) that look like new skills despite never being directly targeted; and the way we choose to *measure* those skills (benchmark metrics) can itself distort how "sudden" the resulting improvement appears to be, independent of how smoothly the underlying model competence is actually improving. Being able to lay out that whole chain — objective, scale, compression argument, generalization, and measurement effects — rather than reaching for a single slogan is what actually demonstrates you understand pretraining rather than having memorized a talking point about it.
