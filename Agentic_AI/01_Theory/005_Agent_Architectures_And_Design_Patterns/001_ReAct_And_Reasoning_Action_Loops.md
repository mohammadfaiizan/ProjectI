# ReAct and Reasoning-Action Loops

## The Problem ReAct Was Designed to Solve

By 2022, two separate lines of prompting research had each shown real gains in isolation. Chain-of-thought (CoT) prompting showed that asking a model to "think step by step" before answering improved performance on arithmetic and logical reasoning tasks, because it gave the model room to work through intermediate steps in natural language rather than jumping straight to an answer. Separately, tool-augmented models showed that letting a model call external functions — a calculator, a search engine, a database — let it get facts right that it could never reliably produce from parametric memory alone.

The catch is that these two techniques, used separately, have complementary blind spots. Pure chain-of-thought reasons entirely inside the model's own head: it never touches the outside world, so if the model's internal "facts" are wrong or stale, the reasoning chain faithfully builds an incorrect answer on top of them with no way to notice. Pure tool-use, without an accompanying reasoning trace, calls tools reactively based on the immediate prompt but has no mechanism for planning a multi-step investigation, adapting when a tool returns something unexpected, or explaining *why* it chose the tool it did — which makes both its behavior and its failures much harder to debug or correct.

ReAct — introduced by Yao et al. in "ReAct: Synergizing Reasoning and Acting in Language Models" (2022) — is the observation that these two capabilities are more powerful *interleaved* than either is alone. Instead of "think, then maybe act once," ReAct proposes: think a little, act once, observe the real-world result, think again in light of that result, act again, and repeat. The reasoning steers the acting, and — critically — the results of acting steer the *next round* of reasoning. Neither component runs open-loop for very long before being checked against the other.

## The Core Mechanism: Thought, Action, Observation

A ReAct trace is a strict repeating sequence of three labeled segments:

- **Thought**: a short piece of free-text reasoning about the current state of the problem — what is known, what is still missing, and what to try next. This is the same kind of text a chain-of-thought prompt would produce, but scoped to "what should I do right now" rather than "what is the final answer."
- **Action**: a single, structured invocation of a tool, expressed either as a natural-language pattern the surrounding code can parse (`Action: search[query]`) or, in modern implementations, as a native function call validated against a JSON schema.
- **Observation**: the actual output returned by executing that action — not generated by the model, but appended into the model's context as ground truth for the next Thought.

```
Thought 1: I need to find the current weather in London before I can answer.
Action 1: get_weather(city="London")
Observation 1: {"temp_c": 15, "conditions": "cloudy"}

Thought 2: I have the weather. The user also asked whether they need an
umbrella, so cloudy alone isn't enough — I should check the chance of rain.
Action 2: get_forecast(city="London", hours=6)
Observation 2: {"rain_probability": 0.7}

Thought 3: 70% chance of rain in the next 6 hours plus cloudy conditions
is enough information to answer confidently.
Final Answer: It's 15°C and cloudy in London, with a 70% chance of rain in
the next few hours — bring an umbrella.
```

Notice the shape of Thought 2: it is not a restatement of the observation, it is a *judgment about sufficiency* — "cloudy alone isn't enough" — followed by a decision about what additional evidence to gather. This is the mechanism by which ReAct reduces hallucination relative to plain CoT: at every step, the model is forced to check its running hypothesis against something external before it is allowed to keep reasoning forward. A pure CoT chain asked the same question would likely have guessed at rain probability from general knowledge about London's weather patterns and asserted it as fact, with no signal to the user (or to the model itself) that this was an unconfirmed guess rather than a retrieved value.

## A Minimal Working Implementation

Below is a compact but complete ReAct loop. The important structural details are: the prompt explicitly instructs the model to alternate Thought/Action, the loop stops the moment a "Final Answer" is emitted, and every Observation is appended to the conversation so the *next* Thought is generated with full knowledge of what actually happened — not what the model expected to happen.

```python
import re
import json

class ReActAgent:
    def __init__(self, llm, tools: dict, max_steps: int = 6):
        self.llm = llm
        self.tools = tools          # name -> callable
        self.max_steps = max_steps

    def run(self, question: str) -> str:
        tool_list = "\n".join(f"- {name}: {fn.__doc__}" for name, fn in self.tools.items())
        transcript = f"""Answer the question using this strict format, one step at a time:

Thought: <your reasoning about what to do next>
Action: <tool_name>[<arguments as JSON>]
(wait for an Observation before continuing)

When you have enough information, respond with:
Thought: <final reasoning>
Final Answer: <the answer>

Available tools:
{tool_list}

Question: {question}
"""

        for step in range(self.max_steps):
            completion = self.llm.generate(transcript, stop=["Observation:"])
            transcript += completion

            if "Final Answer:" in completion:
                return completion.split("Final Answer:")[-1].strip()

            action_match = re.search(r"Action:\s*(\w+)\[(.*)\]", completion, re.DOTALL)
            if not action_match:
                # Model produced a Thought with no parseable Action — nudge it.
                transcript += "\nObservation: [No valid action found. Provide an Action or a Final Answer.]\n"
                continue

            tool_name, raw_args = action_match.group(1), action_match.group(2)
            if tool_name not in self.tools:
                observation = f"Error: unknown tool '{tool_name}'."
            else:
                try:
                    args = json.loads(raw_args) if raw_args.strip() else {}
                    observation = self.tools[tool_name](**args)
                except Exception as exc:
                    observation = f"Error executing {tool_name}: {exc}"

            transcript += f"\nObservation: {observation}\n"

        return "Stopped after max_steps without reaching a final answer."
```

Two design choices in this snippet matter beyond the happy path. First, `stop=["Observation:"]` prevents the model from hallucinating its own observation — a real failure mode if you let the model free-run, because a sufficiently confident model will happily write out a plausible-looking `Observation:` line for a tool it never actually called, which reintroduces exactly the hallucination problem ReAct was built to avoid. Second, a failed parse or a tool error is fed back in as an Observation rather than crashing the loop — the model gets a chance to recover by trying a different tool or fixing its argument formatting, which mirrors how the pattern is used in production tool-calling agents.

## Why Interleaving Reduces Hallucination

It's worth being explicit about the mechanism, because "it just works better" is not a satisfying explanation on its own. There are two distinct effects at play.

The first is **grounding frequency**. In pure CoT, the model commits to a chain of claims with no external checkpoint until the very end, so an early error propagates silently through every subsequent step — the model has no opportunity to notice that step 3 contradicts a fact it could have looked up. In ReAct, every single reasoning step is followed by an opportunity to inject a verified fact before the *next* reasoning step begins. The error-propagation window shrinks from "the whole chain" to "one step," because each Thought is conditioned on the most recent real Observation rather than on the model's own prior (possibly wrong) assumption.

The second is **traceable attribution**. Because each claim in the final answer can, in principle, be traced back to a specific Observation, it becomes possible — for the model during generation, and for a human or automated evaluator afterward — to distinguish "this came from a tool" from "this was asserted from parametric memory." This is exactly the property that made the original ReAct paper report substantially lower hallucination rates on knowledge-intensive QA benchmarks (like HotpotQA and FEVER) compared to chain-of-thought-only baselines: the interleaved actions catch factual claims early, before they can be built upon.

It is important not to overstate this. ReAct reduces the *rate* of ungrounded factual claims; it does not eliminate hallucination, because the model can still misinterpret an observation, choose the wrong tool, or reason incorrectly about a correct observation. What it removes is the specific failure mode of *silently fabricating facts with no attempt to check them* — the model has been given the opportunity, and usually takes it, to check rather than guess.

## Limitations: Error Compounding and Cost

ReAct's structure is also the source of its two most important production limitations.

### Error compounding across steps

Every Thought is conditioned on the full history of prior Thoughts, Actions, and Observations. If Observation 2 is misread, or Thought 3 draws a subtly wrong inference from a correct observation, that error becomes part of the context for every subsequent step — and unlike the single-error case in CoT, a ReAct agent can *act* on a wrong inference, taking a real action based on a mistaken belief (querying the wrong record, filing a ticket against the wrong customer, retrying a search with a malformed query derived from a misparsed prior result). A wrong belief that stays purely internal to reasoning is recoverable at the next step if new evidence contradicts it; a wrong belief that has already triggered an external side effect (an email sent, a record updated, money moved) is not undone just because the agent later reasons its way to the correct answer.

This is why production ReAct agents are rarely deployed with unrestricted tool access. Two mitigations are standard: gating side-effecting actions (writes, purchases, sends) behind an explicit confirmation or a separate "propose, don't execute" step, and bounding the number of steps the agent can take before a human or a supervising process reviews the trajectory. Neither eliminates compounding, but both limit its blast radius.

### Cost and latency per step

Every Thought-Action-Observation cycle is a full round trip: at minimum one LLM call (often more, if the tool call itself requires a follow-up model call to interpret an unstructured tool result), plus the latency of the tool invocation itself (a web search or a slow API call can dominate wall-clock time). A ReAct trajectory that needs 8 steps to answer a question is paying for 8 LLM calls' worth of tokens — including the ever-growing transcript that gets re-sent as context on every single step, since each new Thought is generated conditioned on the entire history so far. This means cost grows worse than linearly with trajectory length: a naive implementation resends the whole growing transcript every time, so total tokens billed across an n-step trajectory scales roughly with n², not n.

```python
# Illustrating the quadratic cost driver: transcript grows every step,
# and the full transcript is resent on every subsequent call.
# step 1: transcript length ~ T
# step 2: transcript length ~ T + t1
# step n: transcript length ~ T + t1 + t2 + ... + t_{n-1}
# total tokens billed ~ O(n^2) in trajectory length, not O(n)
```

Production systems mitigate this with prompt caching (reusing the KV-cache for the unchanged prefix of the transcript across steps, which several model providers now support natively), summarizing or truncating older steps once the transcript exceeds a threshold, and — most importantly — setting a hard `max_steps` bound and treating "still not done at max_steps" as a legitimate failure mode to detect and escalate, not an edge case to ignore.

## When ReAct Is (and Isn't) the Right Choice

ReAct earns its cost on tasks where the right sequence of tool calls genuinely cannot be known in advance — exploratory research questions, customer support conversations where the next question depends entirely on what the last lookup revealed, debugging tasks where each diagnostic step is chosen based on the previous one's result. In these cases the alternative — a fixed, pre-written sequence of tool calls — would simply be wrong on any input that didn't match the exact case the sequence was written for.

It is a poor fit for tasks whose steps are actually fixed regardless of intermediate results (a five-step ETL pipeline doesn't need an LLM re-deciding the order of its steps every run), for latency-critical paths where several sequential LLM round-trips are unacceptable, and for tasks well-served by a single upfront plan that doesn't need to adapt mid-execution — which is precisely the case the next chapter's Plan-and-Execute pattern is built for. The general rule of thumb: reach for ReAct when you cannot write down the sequence of actions ahead of time without already knowing the answer to the question the agent is being asked to find out.

## A Longer Worked Example: Debugging a Failing Deployment

Short weather-lookup examples make the mechanics clear but understate why ReAct earns its keep on harder problems. Consider an on-call engineering agent given: "The checkout service is returning 500s intermittently. Investigate and report the likely cause." No fixed sequence of checks would reliably diagnose this, because the right second check depends entirely on what the first one reveals.

```
Thought 1: I don't know what's failing yet. Start broad — check recent
error logs for the checkout service to see what kind of exception is
actually being thrown.
Action 1: get_logs(service="checkout", level="error", minutes=60)
Observation 1: 47 entries, all "ConnectionTimeoutError: db-replica-3"

Thought 2: The errors point specifically at db-replica-3, not the whole
database tier. That's more specific than a generic overload — worth
checking whether that one replica is unhealthy rather than assuming
the whole DB is under load.
Action 2: get_service_health(component="db-replica-3")
Observation 2: {"status": "degraded", "cpu_pct": 97, "since": "58 minutes ago"}

Thought 3: db-replica-3 has been at 97% CPU for almost exactly as long
as the errors have been occurring — strong correlation. Before concluding,
I should check whether anything changed around that time (a deploy, a
config change, a traffic shift) that would explain the CPU spike itself,
since "it's degraded" isn't yet a root cause.
Action 3: get_deploy_history(service="checkout", hours=2)
Observation 3: No checkout deploys. But db-config deploy at T-62min added
a new index build on db-replica-3.

Thought 4: The timing lines up almost exactly: an index build was deployed
62 minutes ago, and errors began 58 minutes ago — the few minutes' lag is
consistent with the index build ramping up CPU usage. This is now a
well-supported causal chain rather than a guess.
Final Answer: Checkout's intermittent 500s are caused by connection
timeouts to db-replica-3, which has been at 97% CPU for the last ~58
minutes. This correlates with an index-build deploy to db-replica-3
62 minutes ago. Recommend pausing or throttling the index build and
verifying replica CPU returns to baseline.
```

Two things stand out relative to the toy weather example. First, each Thought does not just consume the previous Observation passively — it actively decides what would most efficiently narrow down the hypothesis space next, which is the reasoning half of ReAct earning its place: a tool-only agent with no interleaved reasoning would need some other mechanism to decide "check deploy history" was the right third move rather than, say, restarting the service or checking a completely unrelated component. Second, the final answer is explicitly hedged in causal language ("correlates with," "recommend") rather than stated as unconditional fact — this is a direct, if informal, consequence of the grounding effect described above: every claim in the answer can be traced to a specific Observation, so the model's own phrasing tends to reflect the actual strength of the evidence chain it built, rather than a generic confident tone detached from what was actually verified.

## Prompting Details That Determine Whether ReAct Works in Practice

The high-level Thought/Action/Observation structure is simple, but a surprising amount of ReAct's real-world reliability comes down to prompt-level details that are easy to get wrong.

**Tool descriptions need to disambiguate, not just enumerate.** If two tools could plausibly answer a similar-sounding query (`search_docs` vs. `search_web`), the model needs enough distinguishing detail in each tool's description to pick correctly without trial and error — "searches internal product documentation only, not the public internet" versus a bare `search_web: searches the web`. Vague tool descriptions are one of the most common causes of an agent calling a plausible-sounding but wrong tool repeatedly.

**The stop sequence matters more than it looks.** As shown in the implementation above, cutting generation off at `Observation:` is not a minor detail — without it, a fluent model will frequently write its own fabricated observation in the same breath as the action, especially under sampling temperature above zero, silently defeating the entire grounding mechanism ReAct relies on. This is worth testing explicitly during development: log raw completions before any parsing, and check for the model ever emitting text past the point it should have stopped.

**Malformed actions should produce an Observation, not a crash.** Treating a parse failure as terminal (raising an exception, ending the loop) throws away exactly the information a ReAct agent needs to recover — that its last action wasn't understood. Feeding "Observation: could not parse action, expected format Action: tool_name[args]" back into the transcript routinely lets the model self-correct on the very next Thought, which is often more robust than adding increasingly elaborate parsing logic to handle every format variation the model might produce.

**Few-shot examples of the Thought/Action/Observation format outperform instructions alone**, especially on smaller or less heavily RLHF'd models. Zero-shot instruction to "use this format" is often enough with a strong frontier model, but including one or two worked examples in the system prompt measurably reduces format drift over long trajectories, where models otherwise tend to gradually abbreviate their Thoughts or drop the labels entirely after several successful steps.

## Evaluating a ReAct Agent

Because a ReAct trajectory is a sequence of discrete, labeled steps rather than an opaque single output, it can be evaluated at a finer grain than just "was the final answer right" — which matters because a wrong final answer and a right final answer reached via a lucky guess after a bad step both look identical if you only score the end result.

A reasonably complete evaluation harness checks, per trajectory: **tool selection accuracy** (given the Thought at each step, was the chosen tool actually the appropriate one — this can be scored against a held-out set of tasks with known correct tool sequences); **argument correctness** (did the extracted arguments match what the Thought called for, catching a common failure mode where the reasoning is sound but the structured extraction of arguments from it introduces an error); **step efficiency** (how many steps did the trajectory take relative to a minimal reference trajectory — a working but wasteful trajectory that takes 12 steps to do what 4 should have taken is a real defect worth catching even though the final answer might be correct); and **groundedness of the final answer** (can every factual claim in the final answer be traced to a specific Observation, checked either with a separate LLM-as-judge pass or, better, with a programmatic check when the claims are structured). Tracking these four separately, rather than a single pass/fail on the end result, is what makes it possible to tell whether a regression after a prompt change is a reasoning problem, a tool-description problem, or a parsing problem — three failures that look identical from the outside but require completely different fixes.

## Variants Worth Knowing: ReWOO and Self-Consistent ReAct

Two variations on the base pattern come up often enough in both production systems and interview discussions to be worth knowing by name, because each responds to one of ReAct's two headline weaknesses directly.

**ReWOO (Reasoning WithOut Observation)**, from Xu et al. (2023), targets the cost problem head-on by restructuring when planning happens relative to tool execution. Instead of interleaving a fresh LLM call between every single action and the next Thought, ReWOO has the model produce a full multi-step plan of tool calls *up front*, in one pass, with placeholders for how each step's result should be referenced by later steps (much like the dependency-based planning from the Plan-and-Execute chapter) — then executes all the tool calls, then makes a single final LLM call to synthesize the answer from all the collected observations at once. This collapses what would have been N sequential LLM calls in classic ReAct into roughly 2 (plan, then synthesize), at the cost of losing ReAct's ability to adapt the plan mid-execution based on what an early observation reveals — which is exactly the ReAct-vs-Plan-and-Execute trade-off from the next chapter, showing up here as a variant *within* the ReAct family itself rather than as a separate architecture.

**Self-consistent ReAct** targets the reliability problem instead of the cost problem: run the same ReAct trajectory multiple times (with sampling temperature above zero, so trajectories can genuinely differ), and take a majority vote or otherwise reconcile the final answers, in direct analogy to self-consistency decoding for chain-of-thought. Because each trajectory involves real tool calls, this variant is considerably more expensive than self-consistency over pure reasoning chains — you're paying for the tool calls N times over, not just the reasoning — which limits it in practice to high-stakes decisions where the cost of being wrong clearly outweighs the cost of running the investigation multiple times, such as a diagnostic agent whose conclusion will trigger an expensive remediation action.

Neither variant replaces the base pattern; both are targeted fixes for one of ReAct's two well-known weaknesses, and recognizing which weakness a given production problem actually stems from (too slow and expensive vs. too unreliable on a specific class of question) is what determines which variant, if either, is worth the added complexity.

## Interview-Relevant Summary

If asked to explain ReAct concisely in a technical interview, the load-bearing points are: it interleaves reasoning traces with tool-calling actions and their real observations, rather than doing either in isolation; the interleaving is what reduces hallucination, because it forces frequent grounding checkpoints rather than letting an error propagate silently through an entire reasoning chain before any check occurs; its two costed weaknesses are compounding errors (a wrong belief can trigger a real, possibly irreversible action before being corrected) and per-step cost (both latency and, due to the growing transcript, worse-than-linear token cost in trajectory length); and it is the wrong tool specifically for tasks whose step sequence is knowable in advance without needing to see any intermediate results — which is the precise gap Plan-and-Execute, covered next, is designed to fill.
